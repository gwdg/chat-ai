Security front/src/e2ee · back · saia-e2ee node

End-to-end encryption for models

A model can be bound to a public X25519 key. From then on its chat requests leave the browser as ciphertext and are opened only inside the model service on the HPC side. The back proxy and the SAIA gateway route the envelope but cannot read the prompt, the answer or the parameters.

How it works

  1. The node publishes a key per model. A generator reads the deployment's /models and writes one X25519 pair per model: the private half stays on the node, the public half is published as <model>.pub plus a keys.json manifest. There is no CA; the app fetches the keys from the deployment's key directory or a chosen folder.
  2. The user binds a key to models. Settings → Encryption imports the public key and verifies it with one real sealed request before storing anything. The binding lives in user_settings.e2ee_models, next to the key entries, and travels with the settings export and the encrypted sync. An unbound model stays in cleartext as before.
  3. The transport wrapper seals the request. Every caller that speaks POST /chat/completions goes through the same fetch wrapper. If the model is bound, it takes the whole payload - messages, temperature, tool definitions - and replaces it with a v3 envelope. Only model remains readable.
  4. The proxy forwards bytes, not a request. back recognises the e2ee envelope and deliberately skips message validation, test mode and the tool gateway. It copies the body, stamps the identity headers, adds inference-service: <model> and relays the upstream status, content type and x-saia-e2ee header.
  5. SAIA routes by model id. The gateway only needs the clear model field to pick the service. The ciphertext is an opaque JSON string to every hop up to the node.
  6. The node opens and answers sealed. The E2EE connector derives the shared secret from its static private key, opens the outer envelope (which carries a random traffic password) and then the inner request. It calls the local model, and seals each response event with a key derived from the same secret.
  7. The browser decrypts incrementally. Responses are either one sealed JSON body or an SSE stream of sealed events with an authenticated final marker. A truncated stream, an out-of-order event or a cleartext 2xx body is rejected. If the binding is broken, the request never leaves the browser at all.

What the wire looks like

// the only cleartext field is the model id
{
  "model": "qwen3.8-27b",
  "e2ee": {
    "v": 3,
    "scheme": "X25519-HKDF-SHA256+AES-256-GCM",
    "kid": "…",   // fingerprint of the node key
    "epk": "…",   // ephemeral client public key
    "iv": "…",
    "nonce": "…",
    "ct": "…"    // password + inner envelope, padded
  }
}

The outer layer can only be opened with the node's private key; the inner request can only be opened with the random password it carries. The request path, key id, direction and nonce are authenticated as associated data, so a sealed body cannot be replayed against another endpoint or reordered within a stream.

Invariants worth keeping

  • Fail closed. A bound model without a usable key is blocked; there is no cleartext fallback.
  • No extra cleartext fields. After stripping the routing hints, only model and e2ee may remain; the node rejects anything else.
  • Authenticated context. Key id, model, canonical path, nonce, direction and sequence are bound into the AAD, so a blob cannot be moved to another slot.
  • Fresh secrets per attempt. Every retry re-seals with a new ephemeral key and a new random password.
  • No silent truncation. A stream without its authenticated final marker is an error, not a shorter answer.
  • One badge, one truth. The lock is derived from the same registry the wrapper uses.

Limits

  • Only chat completions are covered. Document conversion, speech, image and web-search endpoints stay cleartext and travel through the same proxy.
  • The OpenCode agent picks a model per session and does not pass through the browser wrapper, so agent turns are not covered by model keys.
  • The node sees plaintext by design; this is transport-to-node confidentiality and integrity, not at-rest encryption of the model service.
  • Key distribution is out of band (published directory or file). Nothing verifies that a published key belongs to the operator except the sealing test itself.
  • Metadata stays visible: model id, timing and ciphertext size.

How it works

  1. The generator reads the deployment's own list. The endpoint comes from --models-url / MODELS_URL, otherwise the config's modelsPath, otherwise the GWDG list. GWDG needs a bearer token, taken from --api-key, $SAIA_API_KEY, the front config's apiKey, or the back.json beside it.
  2. The file name comes from the model id, not its name. Both sides call the same function: every run of characters outside [A-Za-z0-9._-] becomes a single -. So bridge/deepseek-v4.1-flash-1017 is published as bridge-deepseek-v4.1-flash-1017.pub - an id with a slash stays one flat file, which is what a static directory can serve.
  3. Pairs are written with restrictive modes. <MODEL>.key is 0600, <MODEL>.pub is 0644. A rerun keeps an existing pair, so republishing a key does not invalidate chats that are already bound to it; --force overwrites deliberately.
  4. The manifest is the fast path. The same run writes keys.json next to the pairs: {keys:[{id,name,publicKey,models}], models:{<model>:<key id>}}. Key ids are key-<fingerprint>, the same id the app derives, so importing the directory binds every model in one action instead of one key per model.
  5. The manifest is audited. make -C encryption list reports a missing or invalid manifest, a model bound to an unknown key id, and a .pub the manifest does not list - the three ways a directory drifts away from its keys.
  6. The app fetches per model, tolerating absence. <base>/<file>.pub is downloaded for each model. A 404 is not an error: most models have no E2EE node and therefore no key, so it is reported as missing. A refused or unreadable answer is a failure, because that is a directory problem worth seeing.
  7. Every key is proven before it is stored. The sealing test sends one real request per bound model and requires a sealed answer. A wrong key, a model without the connector, or an unreachable node keeps the key out of the settings; one failing model does not block the others.

Invariants worth keeping

  • One naming function. The generator imports the browser's publishedKeyFileName(); a second implementation would silently publish keys under names the app never asks for.
  • Flat names. Slashes and spaces are collapsed, because the directory is served as static files and a model id with a path separator cannot be a file name.
  • Private halves never leave the node. The generator writes them beside the checkout; publishing copies only .pub and the manifest.
  • Ids are content-derived. key-<fingerprint> makes a re-import idempotent and lets two runs agree on the same key id.
  • 404 is a fact, not an error. Models without a connector are the normal case.

Limits

  • There is no certificate authority. The only proof that a published key belongs to the operator is the sealing test, which proves the node holds the private half.
  • Adding a model to the deployment needs a rerun of the generator; the manifest is generated, not merged by hand.
  • The generator normalises the directory: a pair whose .pub was edited by hand is not repaired, only reported by make list.
  • Republishing a key under the same name does not inform clients; a device keeps the binding it imported until the user removes and re-imports the key.

Security / Data front/src/sync · saia-fs

Encrypted sync over the SAIA filesystem

Conversations, topics, settings, workspaces and agent histories are copied to the user's own SAIA filesystem as an encrypted revision tree. Every device writes only its own index fragment and immutable record revisions, so two devices never overwrite each other; a hash-based three-way merge decides pull, push or duplicate. The archive is opt-in, and the vault key exists only while a passphrase (or a passkey) has unlocked it.

How it works

  1. Create the vault once. A passphrase of at least 10 characters is stretched with Argon2id (t=3, m=65536 KiB, p=1) into a key-encryption key. That key wraps one random 32-byte vault key, and vault.json stores the wrapped key plus the KDF parameters - a cleartext header with no key material in it.
  2. Two derived keys do the work. HKDF splits the vault key into a record key and an asset key. Every blob is AES-256-GCM with a fresh 12-byte IV inside a CASSYNC1 container (magic, flags, IV, ciphertext), optionally gzipped, and its AAD names the slot it belongs to: chatai-sync/v1/record/<ns>/<id>/<rev>, .../asset/<sha256>, .../index/<deviceId> or .../vault/<vaultId>. A blob therefore cannot be replayed into another slot.
  3. Every writer owns a file. A revision name contains its revision and the device that wrote it, an index fragment belongs to one device, and the merged view is the union of all fragments. Nothing on the remote side is ever overwritten by a second device.
  4. The engine stages its writes in the safe order. rev is max(now, remoteRev + 1), so it always increases. Record files are written first and this device's index fragment last; the local base rows are committed only after that fragment exists, so a pass interrupted halfway is repeated instead of being mistaken for an older remote revision.
  5. Merging is by hash, not by clock. With the base hash from the last pass: local unchanged means pull, remote unchanged means push, both changed means merge (settings), fast-forward (a conversation whose remote message ids are a prefix of the local ones) or duplicate plus push. A record without a base is compared the same way before it is called a conflict.
  6. Six namespaces define "the whole history". Conversations (message ids preserved, attachments rewritten into content-addressed assets), settings (per-key three-way merge, with memories, groups, MCP servers and E2EE keys merged by element id), account-wide interface preferences (theme, grouping, completed tours - but not window state, counters or the web-search consent), workspaces (row, sources, mounts, links and the shape of the tree, applied additively), agents (metadata plus a bounded cached history) and topics.
  7. Deletes are tombstones, cleanup is explicit. A local delete writes a tombstone kept for 90 days, and a remote edit newer than the deletion resurrects the record. Only "Clean up remote" deletes files: it keeps exactly the revision the merged index names and the assets the live records reference.
  8. The service serialises passes. One run at a time through navigator.locks("chatai-sync"), a five-minute timer that is a no-op while the tab is hidden or the vault is locked, and an explicit Sync now that always runs. A pull that started while visible is allowed to finish.
  9. A pull must hash back to itself. That is why conversation payloads omit lastModified, an empty feedback object is normalised away, createdAt is preserved (and accepted by createConversation), and device-local source status is excluded - otherwise every device would push forever.

The remote layout

/.chat-ai-sync/v1/vault.json                        # cleartext header, wrapped vault key
/.chat-ai-sync/v1/index/<deviceId>.bin              # one writer per fragment
/.chat-ai-sync/v1/records/<ns>/<id>.<rev>-<dev>.bin  # immutable revisions
/.chat-ai-sync/v1/assets/<sha256>.bin               # content-addressed blobs

Names come from the engine, not from the user: a record id is the conversation, folder or workspace id, and the writer suffix is the device id the vault stores.

Invariants worth keeping

  • One writer per file, immutable revisions. The merged view is a union; no device rewrites another device's revision.
  • Fragment last, base rows after. Publishing the index fragment is the commit point of a pass.
  • Slot-bound encryption. The AAD names namespace, id, revision or asset hash, so a valid blob cannot be moved into another record.
  • No silent deletion. Outside Clean up remote, a sync never removes a file it did not write.
  • Secrets stay in memory. The passphrase and vault key are never persisted; a reload locks the vault.
  • A pull hashes back. Anything that changes shape on apply would re-push on every device, forever.

Limits

  • One file is capped at 8 MiB and one record at 500 files. A skipped attachment or workspace file is named in the summary - never replaced by a placeholder, which would differ on the other device.
  • Background sync runs only in the visible tab. Several tabs share one profile and one archive, so the timer deliberately stands still in a hidden one.
  • The hidden Meta chat is excluded, exactly like the JSON export.
  • A lost passphrase cannot be recovered. Rotation re-encrypts everything and is how a device is revoked.

Where to look

  • docs/sync.md - the design document, including the merge table
  • front/src/sync/ - crypto, engine, namespaces, storage, service
  • modals/UserSettings/SyncSettings.jsx - create, unlock, rotate, cleanup
  • db/syncAdapters.ts - the raw-table writes the namespaces share
Why a revision tree instead of last-write-wins. Two devices are offline by default. A shared mutable file would let the slower device erase a chat it never saw; immutable revisions plus per-device fragments make the merge a pure function of what is on the filesystem, and a conflicting chat becomes a visible copy instead of a blocking dialog.

Encrypted backup file

One downloadable .chataibackup file holds the whole browser history - conversations with attachments, topics, settings, workspaces and agents - sealed with Argon2id and AES-256-GCM. It needs no SAIA account, and restoring it replays the same namespace writers the sync uses, so a backup and a remote copy always agree on what "the whole history" means.

How it works

  1. The package reuses the sync namespaces. createDefaultNamespaces() is the same list the engine syncs, so adding a new record type to one feature makes it appear in the other. Attachments and workspace files are deduplicated by SHA-256 into a single assets map; meta-chat stays excluded because the conversations namespace excludes it.
  2. The sync limits apply unchanged. 8 MiB per file and 500 files per record. An oversized or unreadable file is left out and listed in the package and in the UI - never replaced by a placeholder, which would make the archive differ from the live state.
  3. Crypto is its own domain. The passphrase is stretched with Argon2id (t=3, m=65536, p=1, 32-byte key) and HKDF derives the content key with the backup info under chatai-backup/v1. That is a different domain from the sync vault, so a backup blob can never be replayed as a sync record.
  4. The header is authenticated. The archive is sealed with the shared CASSYNC1 envelope, and the AAD is chatai-backup/v1/<createdAt>, so the creation time shown in the UI cannot be altered without breaking decryption.
  5. KDF values from a file are bounded. Before Argon2 runs, m is capped at 1 MiB, t at 10 and p at 4. A hostile header cannot make the browser allocate gigabytes or spin for minutes before it fails.
  6. The file name is local and readable. chat-ai-backup-YYYYMMDD-HHMMSS.chataibackup, using the user's local time, so the name matches the date the UI shows.
  7. Restore replays the write path. The container is validated, decrypted and applied namespace by namespace in a fixed order (settings, topics, workspaces, agents, conversations). A row with the same id is overwritten, nothing is deleted, and a namespace this build does not know is reported in unknownNamespaces instead of being guessed at.
  8. The UI asks before it touches anything. The Data tab splits into Manage data, Encrypted backup and Server synchronization. Backup requires an explicit confirmation checkbox, and restore opens a file dialog instead of reading the database on selection.

Passkey unlock for the sync vault

WebAuthn's PRF extension turns an authenticator into a stable 32-byte secret. That secret wraps the sync vault key, so a trusted device can unlock the archive without typing the passphrase. The binding is local, tied to one vault id, and never enters the sync archive or a backup, because no other device could use it.

How it works

  1. Enrolment creates a credential with the PRF extension. The browser passes a per-binding salt (the PRF input) and asks the authenticator for its output. Creation often returns no PRF result, so enrolment falls back to one immediate assertion - otherwise a brand-new credential could not produce a secret at all.
  2. The PRF output becomes a wrapping key. HKDF with the passkey/wrap info derives an AES-GCM key, and that key seals the vault's VaultKeys with the AAD chatai-sync/v1/passkey/<vaultId> - the shared CASSYNC1 envelope again, just for a different slot.
  3. Only the binding is stored. sync_meta keeps a passkey-binding row: credential id, salt, the sealed keys, the vault id and a label. The PRF secret, the wrapping key and the vault key are never written anywhere.
  4. One binding belongs to one vault. A binding is valid only for the vaultId it was created with. Replacing or rotating the vault clears sync_meta and drops the binding; a mismatch is refused before any authenticator prompt, so the user is not asked for a passkey that cannot help.
  5. Unlocking is attempted where it is safe. The automatic attempt runs only while the vault is locked, a local binding exists and automatic sync is on, once per mount in useSyncEngine and once per vault in the settings panel. Two concurrent callers share one in-flight promise, so only one authenticator prompt appears.
  6. An explicit lock sticks. "Lock now" sets a module flag that makes a silent attempt refuse without touching WebAuthn. The visible "Unlock with passkey" button - a user gesture, which credentials.get() may require - still works, and every successful unlock or a sync off/on cycle clears the flag. A reload is a fresh module, so the passkey is asked again - that is the point of enrolling one.
  7. The passphrase remains the fallback. A cancelled prompt, an authenticator without PRF or a refused assertion leaves the vault locked and the sidebar button blue; the Data tab's Server synchronization section is where the passphrase is typed.

How it works

  1. Two suites, two kinds of failure. The Playwright specs click explicit selectors and mock their upstream; they catch regressions. The playbooks are manual and non-deterministic: they run against a real front and back, so answers come from whatever model that stack is configured with, and the model judges them.
  2. Frontmatter is the entire machine contract. title, start, viewports, language and max_steps; everything after the second --- is passed to the model verbatim. Desktop is 1366×900, mobile 390×844, en maps to en-US and de-de to de-DE, and the step budget defaults to 25.
  3. Each viewport starts from nothing. The runner creates a fresh browser context per scenario and viewport, so IndexedDB and localStorage are empty: welcome dialogs, theme defaults and first-visit behaviour are part of the run, and one run cannot inherit state from another.
  4. The model points at numbers, not pixels. browser.ts numbers every visible, enabled interactive element, draws a red label on each and screenshots exactly that, then removes the labels from the page. Open popovers and dialogs get their labels in the top layer, so a label is never hidden behind an overlay.
  5. One stateless call per step. The model receives only the current screenshot as an image; the past is a text log of actions, thoughts and Playwright errors. That bounds cost and forces the log to carry context, which is also why a failed click is reported back with its reason instead of ending the run.
  6. The action vocabulary is small. click, type (optionally with Enter), press, scroll, goto, wait (capped at 30 s) and done. A malformed reply costs one step, not the run.
  7. The verdict can fail on its own. done carries passed, reason and a defect list; any listed defect fails the run even when the model marked it passed. Reaching the step budget without a verdict is also a failure.
  8. Every screenshot is checked against checks.md. Unrendered Markdown or LaTeX, mixed UI languages, untranslated keys and placeholders, error toasts, spinners that never resolve, clipping and missing assets fail the scenario even when they are outside its own steps.
  9. The report is the debugging tool. results/<timestamp>/index.html shows, per step, the labelled screenshot the model saw, its thought, the parsed action, any error, the full prompt and the raw reply. Every screenshot is also written next to it.

How it works

  1. Creating an agent creates a service row. POST /agents answers with an id; the app stores it as serviceAgentId and uses /agents/<id>/opencode as the server URL. No basic-auth password is stored: the proxy adds the backend credentials.
  2. The URL is derived, not remembered. baseUrl() rebuilds the proxy prefix from serviceAgentId and the fixed AGENT_SERVICE_PATH, so an agent follows the current deployment instead of pinning a host it was created on.
  3. Entitlement comes from the model list. The service is registered in the engine as the model saia-agent inside an access group, so /models lists it only for a user who was granted it. The add dialog asks hooks/useAgentServiceAccess.js, which answers checking, granted, denied or unknown; denied disables the service fields and points at the support address, unknown (an empty or refused list) fails open because a broken model fetch says nothing about grants.
  4. A direct server is local-only. Everything outside a loopback hostname goes through the service. apis/agentAccess.js decides that, rawRequest enforces it for every call, and the add dialog mirrors it by forcing the service mode and hiding the URL and password fields - so an old direct agent is migrated when it is saved.
  5. Tunnel mode moves the request into the body. With agentServiceMode: "tunnel", every /agents call becomes POST <backend>/chat/completions for saia-agent with the real request under chat_ai_http. The service answers with status, headers and body boxed in chat_ai_http, and the client rebuilds a real Response so conflict and error handling stay identical.
  6. Streams survive the box. A streaming call sets stream: true and the service returns base64 deltas, which the client feeds into a ReadableStream. An engine read timeout of 600 s bounds the whole exchange; the bridge's long poll holds 20 s, well inside it.
  7. A dead row is removed, not retried. A 409 with code: "conflict" means the service will not serve that row. The client emits chatai:agent-service-conflict, AgentConflictWatcher deletes the service agent and the local entry, leaves /agent/<id> and explains why. Direct agents and proxied OpenCode 409s without that field are ignored.
  8. Removing an agent frees the container. DELETE /agents/<id> drops the row and its conversation-to-session mappings; a 404 counts as already gone. The workdir is kept.

Gateway forwards /agents

The normal case: the browser calls the service directly on its own origin, and both legs - the OpenCode API and the bridge WebSocket - are ordinary HTTP and WS routes. The gateway must forward the Upgrade header.

Gateway forwards only the model

The tunnel case: no /agents route exists, so every call rides a completion. Header and query string are dropped on that hop - the engine rebuilds the request from content-type and the body - which is why the payload has to be a body field. 

// what the browser sends instead of GET /agents/<id>/opencode/api/session
{
  "model": "saia-agent",
  "messages": [],
  "chat_ai_http": {
    "method": "GET",
    "path": "/api/session",
    "body": null,
    "headers": {},
    "stream": false
  }
}

The service replays that request against the backend it spawned and answers {chat_ai_http: {status, headers, body | text, encoding}}. From the caller's point of view nothing changed: it still gets a Response.

How it works

  1. A session is created, then two legs attach. POST .../bridge/sessions returns a browser token, an agent token, both URLs and - for a service-managed agent - the sidecarCommand. The page connects with the token as the bridge-token.<token> subprotocol; the sidecar sends it as an Authorization header. No token appears in a URL, so proxy logs stay clean.
  2. The per-chat key pairs the halves. The page generates 32 random bytes per agent and session, keeps them under chatai.bridge.keys (bounded to 200 entries) and puts them into every stdio entry's environment. An agent socket that does not present the same key is closed. The deployment-wide shared secret (BRIDGE_SHARED_SECRET / bridgeKey) is a separate, optional gate on session creation - it ships in the bundle, so it is not the pairing mechanism.
  3. One browser leg, several agent sockets. Every wrapped MCP server owns its own process, so a new socket joins the session instead of replacing the previous one (cap 32). They share the browser leg and the request map, and request ids are unique, so an answer always reaches the socket that asked.
  4. Workspace tools go through the same VFS as the chat. workspace_list, workspace_stat and workspace_read are always offered; workspace_write, workspace_mkdir and workspace_remove only while the agent's write toggle is on. Provider capabilities, mount paths and read-only flags stay authoritative, so the bridge cannot write something the UI would refuse.
  5. MCP is either relayed or handed over. The relay exposes mcp_list_servers, mcp_list_tools and mcp_call, and the browser keeps URL and headers. With the injection option, servers without stored headers are registered in OpenCode itself (PUT /api/experimental/mcp/...) so their tools work with the tab closed. A server with headers is wrapped instead: its own stdio proxy carries only a server id, and the browser resolves the URL and headers at call time.
  6. Entries are scoped to a session. OpenCode's registry is instance-wide, so every name this app registers ends with the session id: the bridge is chatai-bridge-<session>, an injected server chatai-ext-<label>-<session>, a wrapped one chatai-auth-<server>-<session>. agentMcpScope then patches the permissions of every session of that agent: deny chatai-*, then allow exactly the entries of that session or one of its ancestors. The last matching rule wins, which is why the allow comes after the deny.
  7. Resources are a read-only view of one workspace. resources/list enumerates the attached workspace as chatai-workspace:///<path>, bounded to 40 directories, depth 3 and 200 files; text is returned as text and binary as a base64 blob. Answering with an error would show up as "no MCP resources", so it never does.
  8. A missing browser is an answer, not a hang. If the page is disconnected, the sidecar still lists its tools and every call returns an isError result with BRIDGE_OFFLINE; a browser that does not answer within the timeout returns BRIDGE_TIMEOUT. The agent continues with OpenCode's own tools.
  9. A deployment without a bridge says so. 404 or 405 on /bridge/sessions means this base has no bridge route (a direct engine, or an old agent service). The hook reports unavailable with the URL and status, the popover disables the switch and names the endpoint instead of retrying forever.

How it works

  1. Adding an agent verifies the server, then creates a session. The dialog takes a URL and an optional HTTP-basic password, calls GET /api/info, then POST /api/session. The resulting session id is stored on the local agent entry, and from then on the entry is the only place the page looks for its current session.
  2. Direct access is loopback-only, and enforced per request. apis/agentAccess.js asks whether the page's hostname is localhost, 127.0.0.1 or ::1; rawRequest refuses every call from any other origin with DIRECT_AGENT_BLOCKED before touching the network, and the add dialog hides the external mode. The reason is the flow above: this API runs commands and reads the project directory, so exposing it to a browser page on the internet is not a feature.
  3. A session is the chat, and subagents are child sessions. Session children come from GET /api/session?parentID=…&limit=200, with the older /session/:id/children route as a fallback; they render nested under the parent and open in the same page. A session switch changes a pointer, not the agent: the agent entry, its workspace links and its OpenCode instance are shared by every session.
  4. A turn posts the prompt and follows the stream. POST /api/session/:id/prompt carries the text and any inline files; GET /api/event refreshes messages and permissions as OpenCode works. Assistant text renders through the same Markdown renderer as a chat answer, while tool calls and reasoning render as expandable cards in the timeline.
  5. The composer has two more input modes. A ! prefix or the yellow Shell toggle sends the text to POST /api/session/:id/shell, and the output appears inline in the conversation, abortable from its card. Slash commands come from GET /api/command plus the built-in compact, and are sent to POST /api/session/:id/command.
  6. Permissions and forms keep the turn interactive. A permission request is answered through POST /api/session/:id/permission/:request/reply with a decision and optional message; saved permissions and local policies can answer automatically. OpenCode's form API - including its question tool - renders inline, and a field that carries options is treated as a choice list with a free-form answer, never collapsed into a plain text input.
  7. The left panel is the agent's own filesystem. It reads /api/fs/list and /api/fs/read/<path>, searches with /api/fs/find and writes to /api/experimental/fs/write, polling the open directory every five seconds while the page is visible. A read or write card in the timeline opens that file in the same right-hand preview; a folder with .git gets a Git button, and the log is fetched through the OpenCode shell with an internal tag that the chat filters out. A server that answers with an HTML page, a 502 or nothing at all is reported as unavailable, and the panel renders nothing instead of a JSON parse error.
  8. History is cached so a session opens instantly. The conversation renders the cached timeline first, then syncSessionHistory pages the server newest-first and stops at the cached tail. The server is authoritative: a cached anchor that is gone means the history was cleared, reverted or compacted and the cache is replaced; a page that ends before the anchor leaves the cache alone and triggers a full read; an empty page is confirmed by a full read before anything is dropped, and an unreachable server never touches the cache.
  9. A server that lost its sessions offers to restore them. When the listing succeeds but cached histories are missing, the page shows a restore banner. restoreCachedSessions creates one session per cached history, writes a bounded transcript (100k characters, newest kept) into a new session's instructions, copies the cache under the new id, and moves workspace session links and summaries. Messages are never replayed as chat turns.
  10. Unsent text and small histories survive a reload. Drafts, sent-prompt recall (ArrowUp and ArrowDown, capped at 50, with the first ArrowUp remembering the draft), shell output and form cards are stored per agent and session in localStorage. The tools modal exposes the live plan, diffs and revert, saved permissions, local policies, connection diagnostics, usage, MCP servers and the recovery tab, and its transcript export falls back to the cache when the server is down.
  11. Closing the session is a deliberate sequence. The header X confirms, interrupts a running turn, deletes the OpenCode session, creates a replacement, stores its id on the agent and clears the remembered shell history. Removing the agent interrupts first and deletes the session before the local entry, so an unreachable server never strands a running process.

Invariants worth keeping

  • Direct means loopback. The check is in the request path, not only in the dialog, so no component can bypass it.
  • The server is authoritative. The cache accelerates a session; it never keeps a message the server deleted.
  • A rewrite is re-read, not merged. Clear, revert, revert-commit and compaction change the timeline in place, so they force a full sync.
  • An empty answer is not a deletion. A single empty page is confirmed by a full read before the cache is dropped.
  • One agent, one instance. MCP entries, permissions and the workspace bridge belong to the OpenCode instance, which every session of that agent shares.
  • Unsent text is per agent and session. A switch must not leak one conversation's draft into another.
  • Restored history is instructions. It is text in a new session, never a replay of turns that would run tools again.

Limits

  • The shell is the host's shell. There is no sandbox beyond what the OpenCode process was given, which is why direct mode is local-only.
  • The browser talks to the server directly, so OpenCode must allow the app origin through CORS; a server that is only reachable from another machine is not a direct agent.
  • The model selector is the intersection of OpenCode's list and the deployment's models; a model the deployment does not offer cannot be chosen for a session.
  • A session that an agent creates after the last MCP scope run carries no rules until the next run; the same applies to the workspace bridge.
  • Export falls back to the cache when the server is unreachable and marks the file source: "cache", so an old export can look current.
  • Compaction is irreversible from the UI; the local cache keeps the pre-compaction copy only until the next full sync replaces it.

How it works

  1. It is a service, not a model. Listing a filesystem in /v1/models would offer it to every granted user as something to chat with. The selector filters an old saia-fs row out for deployments that still publish one, and availability is decided by GET <base>/health: HTTP 200 with {"status":"alive"}. A 404 (no route), 503 (no instance), 502 (unreachable), a timeout or a network failure all mean "no drive" - the probe never throws, so the source list fails closed instead of offering a dead card.
  2. The base URL is a deployment path. By default it is <backend>/saia-fs; saiaFsEndpoint (VITE_SAIA_FS_ENDPOINT) replaces it with an absolute or same-origin URL for a stack where the service listens on its own port. Chat AI's own back proxies nothing there, so the default path has to be forwarded by the deployment and must add the caller's identity.
  3. Identity is the whole authorization. The service reads x-auth-claim-uid only, and an unhandled identity error is answered as a bare "Error executing tool ..." - MCP does not forward the exception text, so the folder simply looked empty. A deployment maps oidc_claim_uid to that header; a direct local stack sends it through fakeAuthHeaders. The provider now calls exists("/") once after the handshake, so a refused session becomes a visible connect error instead of an empty listing.
  4. A fresh account is an empty folder, not "not found". The service ensures the user's namespace on every tool call: a local backend creates <root>/<user>, an object store already lists an unknown prefix as empty. Listing, exists and info therefore work for a user who has never written anything; the provider's "missing root means empty page" fallback only covers an older service.
  5. Capabilities are read from the tool list. append is offered when the instance has append or write, rename when it has rename or move. The workspace UI only shows what the provider reports, so an older instance degrades instead of failing at the click.
  6. Rename is in place, never overwriting. The native tool takes a plain name and refuses an existing destination (destination already exists becomes CONFLICT) and the storage root. Where only move exists, the shared helper pre-checks the target first, because that move would otherwise overwrite.
  7. Append is text, or a whole-file rewrite. The native append takes UTF-8 text and creates the file and its parents. Bytes that the text tool would mangle go through read_base64 plus write_base64 as a full rewrite, because there is no binary append and a partial write would corrupt the file.
  8. Mounting keeps it live. Choosing a folder adds a mount at /<name>; the workspace reads through the service every time. Nothing is copied, so an edit made elsewhere shows up on the next listing - and an unreachable source reports its reason on the row instead of pretending to be empty.

How it works

  2. Each source keeps its own nature.   3. The root is local entries plus mounts. A normalized browser tree provides the workspace root; workspace_mounts overlays folders from other sources at /<name>. A local entry wins over a mount at the same path, which is why the mount dialog refuses a destination that already holds an entry or would sit inside one.
  4. One row per path, per source. workspace_nodes is keyed by a random id, so a restored backup could add a second row for the same path. The sync adapter reuses the row it finds, the VFS deduplicates at read time (lowest id, the one a write would also pick) and Dexie v19 repairs existing databases: keep the copy with the bytes, delete the rest and repoint file references.
  5. A move is copy, verify, delete. planTransfer refuses read-only targets, a folder into its own descendant, and an over-quota target, then runTransfer streams the bytes, verifies SHA-256, and only then deletes the source. Progress is journaled in workspace_transfers. The order is never reversed, so an interrupted move leaves the source intact.
  6. Dragging carries a set. A selection is a set of rows; dragging it plans one batch, asks once for a cross-source move, then runs one transfer per item. Mounts, the synthetic /chats parent and read-only rows are neither draggable nor drop targets. A drop lands at <target>/<name>/** and a name collision is refused, never merged or auto-renamed.
  7. The toolbar is the row action. Rename (one real entry, rename capability, writable), Download (reads the whole content before saving, so a still-connecting provider cannot produce an empty file), Delete (asks once for a set, deletes sequentially, keeps failed rows selected). A / row above the list is the workspace root drop target and the anchor for New file and Upload.
  8. Preview is shared, not per host. One FilePreviewPanel renders chat attachments, workspace files and agent files: Markdown through the normal renderer, HTML in an opaque-origin iframe with Strict/Relaxed, images with Describe, and a 20-80 % split that is remembered per viewer. Describing an image writes <name>-description.md through the same provider when the host can write beside it.
  9. A failure is shown where it happened. A folder whose listing fails prints the provider's reason under its row and is not retried until it is reopened or the tree refreshes, because the row's auto-load would otherwise ask an unavailable source forever.

How it works

  1. Two modes, independent of each other. In saia mode the user comes from x-auth-claim-uid on every request and the embedded connector registers the instance with the registry. In mcp mode one configured user (--user or SAIA_FS_USER) owns everything, no header is read and nothing is registered. The second mode is for a single-user client, not a deployment.
  2. The browser is the MCP client, and in a deployment it calls its own origin. apis/saiaFs.js#saiaFsBaseUrl returns <backendPath>/saia-fs unless saiaFsEndpoint is set; the workspace provider speaks streamable HTTP to …/mcp and the availability probe reads …/health. Nothing in this repository serves that path: back has no /saia-fs route and the engine does not forward it either, so the deployment in front has to rewrite <backendPath>/saia-fs/<rest> to the registry's /services/saia-fs/<rest> and add x-auth-claim-uid. That hop is where the user is established; everything after it treats the header as given.
  3. An agent does not dial saia-fs by itself. When the OpenCode bridge exposes a workspace, the agent calls workspace_* tools and the browser answers them through the same provider, so the request takes the same path. There is no second client and no second credential.
  4. Two shapes of that path. A deployment keeps the derived URL, so the browser never learns a service address and the identity comes from the hop. A stack without the hop - the local test stack, where the service listens on :8003 - sets saiaFsEndpoint and the browser talks to the service directly; the identity then has to arrive another way, which local testing does with fakeAuthHeaders. Leaving the override unset in a deployment is not cosmetic: a direct endpoint would have to authenticate the caller itself.
  5. One folder, ensured on first contact. Every path becomes <storage root>/<username>/<path>. The backend's ensure_namespace runs on every tool call, so a local backend creates the folder for a user who has never written anything and an S3 prefix already lists as empty. A fresh account is an empty folder, never not found.
  6. Paths are relative and cannot escape. / and the empty string are the user's root; leading, trailing and repeated slashes are ignored; \ is a separator; . segments are dropped; .. raises path traversal blocked and NUL bytes are rejected. The local backend additionally resolves symlinks and checks the real path, so a file can never leave the namespace.
  7. The tools are the whole API. list, list_json, read, read_base64, write, write_base64, append, delete, mkdir, exists, move, rename, info. Failures come back as tool results - not found: <path> or error: <message> for text, a JSON object with error for the JSON tools - never as an exception, because MCP does not forward the exception text.
  8. Text and binary are separate pairs. read decodes UTF-8 with replacement, so binary data is not preserved; images and PDFs go through read_base64 and write_base64. write_base64 with an offset behaves like pwrite: it overwrites from that byte and keeps the rest, zero-filling a gap past the end.
  9. rename stays in its directory and never overwrites. It takes a plain name, refuses /, \, . and .., answers destination already exists instead of replacing, and cannot rename the namespace root. Changing a directory is move, which on the local backend uses mv semantics and may overwrite the destination.
  10. Two transports, one port. Streamable HTTP lives at /mcp (what Chat AI and the agent use), SSE at /sse with messages on /messages/, GET / is a JSON index and GET /health answers {"status":"alive"}. Both transports expose the same tools.
  11. The connector is embedded in the service process. make saia-fs waits for /health, then opens pooled TCP tunnels to the registry's connector port (9999) and registers SERVICE_NAME/INSTANCE_ID - saia-fs/naruto-1 by default. It re-registers after a registry restart without a restart of its own. The pool holds at most 32 idle tunnels; an unused tunnel that the registry closes is replaced after a growing backoff rather than immediately, because two sides reopening in a loop reach ulimit -n. A run of drops is reported once.
  12. HTTP/2 cleartext is a hard requirement. The registry dials connected services with http2=True, http1=False, so the service runs on Hypercorn, not uvicorn. A plain HTTP/1.1 server answers Invalid HTTP request and the engine reports a 502 - the same reason the local stack's example model uses Hypercorn.
  13. No model row, on purpose. /v1/models is the chat catalogue: every row is offered as a selectable model and a chat request for it goes to /v1/chat/completions. saia-fs serves /mcp and has no chat route, so such a row would be listed ready and every request against it would fail. MCP needs no engine record: the registry's /services/<name>/<path> proxy consults its own connection table, never the engine database.
  14. Identity is the whole authorization. A bare instance on a non-loopback port trusts the header it is given, so it may only be exposed where a proxy guarantees that header. CORS defaults to loopback origins; a browser deployment must name its origins in ALLOWED_ORIGINS.

  • Errors are results. A missing file or a refused path must reach the client as text it can read, not as a protocol error it cannot see.
  • rename never overwrites. Replacing a file is a write, not a rename.
  • No engine row. The moment saia-fs appears in /v1/models, the UI offers it as a chat model that cannot answer.
  • One namespace per user. Saia mode has no fallback user and no cross-user path.
  • The browser never dials the registry. It knows one path on its own origin; the registry port and the connector socket stay server-side.
  • The hop is the authenticator. The identity saia-fs acts on is the one that hop stamped. A deployment that skips it either serves no drive (the probe gets a 404) or trusts whatever header arrives.
  • Descriptors stay bounded. The tunnel pool is capped and refills after a backoff.
  • Binary is base64. A text read is a lossy UTF-8 view and must never be used to round-trip a file.

Limits

  • No copy, glob/search, permissions (chmod, chown) or symlink creation. There is no locking or transaction either: concurrent writers overwrite each other.
  • S3 append and offset writes read, splice and rewrite the whole object, so their cost grows with file size and concurrent appends can lose data.
  • mcp mode has no authentication at all. saia mode is only as strong as the proxy that sets x-auth-claim-uid.
  • A deployment without the /saia-fs hop simply shows no drive: the probe gets 404 and no source row is created. That is fail-closed on purpose, but it looks like a missing feature rather than a routing mistake, so check the hop before the service.
  • The pool holds 32 idle tunnels; a registry that keeps evicting them costs reconnect latency, not correctness.
  • A registry outage is retried in the background and reported at most once a minute, so a long outage looks quiet until it recovers.
  • The unit tests do not start a registry or Docker; the end-to-end path is local-testing/smoke.py.

How it works

  1. One command builds, starts and seeds.   2. The seed creates the identity the examples assume. It is idempotent: user tester, a fixed API key, the example-local-model service, the local access group and its grants. The bridge group is not the seed's: the first successful catalog sync creates it, and the seed waits up to two minutes for it before granting tester - which is why a local-only stack may leave that grant unwritten. The key must stay 32 characters, because the engine's inference routes reject any other length while /v1/models still answers - an asymmetry that looks like a routing bug.
  3. The bridge path pulls another engine's catalogue. bridge.yml defines the GWDG upstream (priority 10) and the fake local one (priority 20); every model arrives as bridge/<id> with an (External) description, is placed in the bridge group and is deduplicated by upstream id with the lower priority as the primary. The fake upstream accepts new models at runtime: POST /admin/models and DELETE /admin/models/<id> with Bearer local. Here the catalog refreshes every 10 seconds; a removed model is marked unavailable, not deleted, and pruning stays off while any upstream is unhealthy.
  4. The registry path tunnels one service. registry-model is a fake OpenAI-compatible server, saia-connector registers it at :9999 and keeps the tunnel open. A connector alone is not enough: the seed creates the Service row, and demand-updater flips its status from offline once the registry reports a live connection. Without that worker the row exists but /v1/models shows it unavailable.
  5. HTTP/2 cleartext is not optional. The registry dials with http2=True, http1=False, so registry-model runs on Hypercorn. The runtime engine image does not include Hypercorn, which is why the fake model is built from its own Dockerfile.model instead of the engine image. A plain HTTP/1.1 server fails with Invalid HTTP request and chat answers 502.
  6. saia-fs runs on the host and is not a model. In saia/saia-fs/local-testing, make brings this stack up, serves saia-fs on :8003 with ROOT=./data/fs and registers saia-fs/local-1 at 127.0.0.1:9999; make smoke there calls :5000/services/saia-fs/mcp as tester, writes and reads a file, and checks it under data/fs/tester/. From the parent saia/saia-fs, make local-up starts the stack and make saia-fs serves with that directory's own defaults (ROOT=data, instance <hostname>-1). No engine row is created: the registry proxy uses its connection table, and a row would only advertise a chat model that cannot answer.
  7. The agent service can register the same way. Run it natively on 0.0.0.0:8090 with --server hypercorn (it spawns OpenCode containers, so it cannot live in this compose project). Then agent-service/local-registry/compose.yml up -d plus its one-shot seed create the saia-agent row, the agent group and the tester grant; the connector reaches the host through host.docker.internal. A registry request carries no user identity, so every call shares the service's default user.

Chat AI points at the stack with one config file. secrets/front-local-conf.json already sets backendPath and modelsPath to http://localhost:10000/public/v1, saiaFsEndpoint to http://localhost:8003, the fixed key, the x-auth-claim-uid: tester header and agentServiceMode: "tunnel". The README lists the five processes - fake upstream, registry plus engine, bridge, registry model plus connector, demand updater - with the exact environment for a native run. That path is how the setup itself is verified without Docker; for a native run, replace the compose hostnames in bridge.yml with 127.0.0.1.

saia-bridge: model federation

Chat AI talks to one SAIA engine, and that engine is the only boundary that knows users, keys, limits and billing. saia-bridge sits behind it and turns several upstream SAIA engines into extra model sources: it merges their catalogues, pushes the union back as ordinary Service rows, and forwards each request to an engine that can serve the model. Nothing on the user's side changes, because a federated model is a normal row with a bridge/ prefix.

How it works

  1. Three credentials, one user. Client to front engine: the user's SAIA key. Front engine to bridge: SAIA_BRIDGE_API_KEY. Bridge to upstream: the key in that upstream's config block. The bridge never sees an end user and never bills anyone; it authenticates the front engine, not a person. The two shared secrets must be byte-identical on both sides - a mismatch presents as 401 and a catalogue that never syncs, which reads like a dead bridge.
  2. Public ids are namespaced once. public id = engine.model_prefix + upstream model id, so Qwen3-30B-A3B becomes bridge/Qwen3-30B-A3B. The prefix in config.yml must equal the engine's SAIA_BRIDGE_MODEL_PREFIX; that equality is how the engine recognises a model it must forward instead of serving.
  3. Deduplication keeps one entry and many candidates. Upstreams are merged by upstream model id; the lowest priority becomes the primary and the rest stay as failover targets in ascending order. Metadata is not duplicated, so a model that two engines both serve appears once. enabled: false drops a block before the catalogue is built, so a configured but inactive upstream cannot make the catalogue look unhealthy and block pruning.
  4. The catalogue is pushed, not pulled. The bridge calls POST /admin/bridge/catalog with x-saia-bridge-token. The endpoint upserts one Service per public id, names the description … (External), and puts the rows into the configured access group (created if missing). No database migration is involved: bridge models are ordinary service rows, which is why prices, limits, groups and accounting keep working.
  5. (External) is a routing marker, not a description. It tells the engine's demand updater to skip these rows: they are not in the registry, so it would otherwise mark them offline after its first pass. It is also not a tool-capability signal - Chat AI deliberately keeps bridge models tool-capable, because the engine forwards their tools in the request body.
  6. Pruning waits for full health. Rows that vanished from the catalogue are marked status = 2 (offline) only when the sync carries prune: true, which the bridge sends only after every upstream answered the latest refresh. One briefly unreachable upstream therefore keeps its last known state instead of taking its models offline. An empty catalogue is never pushed.
  7. Sync is fingerprint-driven. A push happens when the catalogue's fingerprint changes, at most every engine.sync_interval_seconds (default 120 s), and a full resync runs hourly so a missed change cannot persist. Prices are not sent unless engine.pricing is configured, so an admin's manual prices survive a resync.
  8. Forwarding is protocol-preserving. /v1/chat/completions, /v1/completions, /v1/responses, /v1/messages, /v1/messages/count_tokens and /v1/embeddings are proxied without translation, SSE included (decoded and re-chunked, not re-parsed). Only the model field is rewritten to the upstream id, because the upstream knows its own name for the model, not the prefixed one.
  9. Failover happens before the first byte. A connect/DNS/TLS error or an upstream 408, 429, 500, 502, 503, 504, 529 moves to the next candidate. Any other 4xx is returned unchanged, because the request is wrong and repeating it elsewhere is pointless. A stream that breaks after it started is propagated, never retried, since the caller already has half an answer. Non-streaming responses are read with streaming internally for the same reason: a bad candidate can still be replaced invisibly.
  10. A chain cannot loop. Every hop increments x-saia-bridge-depth; the front engine refuses to send at SAIA_BRIDGE_MAX_DEPTH and the bridge refuses to forward at its own max_depth (both default 3), answering 508. That covers a misconfigured chain and a bridge pointed at its own engine.
  11. It is an internal service. In a deployment the bridge runs behind the bridge compose profile on the engine's own network, with no published port and a container name the engine can resolve. Its optional standalone compose.yml exists for another host and must not run beside the bundled one, because both would claim the same container name.

Invariants worth keeping

  • The front engine stays the boundary. A bridge that authenticated users or counted tokens would be a second truth about access and cost, in a process that has no user table.
  • The prefix is a contract. The engine decides to forward by it and the bridge recognises its own ids by it. A public id must be a Service row in the engine before traffic for it means anything.
  • One public id per model. Overlaps become candidates, never duplicate rows.
  • Failed 4xx is not a failover. Only the listed retryable statuses and transport errors move on; anything else is the caller's problem and must be reported.
  • Never retry a started stream. Half an answer was already delivered.
  • No prune on partial health. Losing an upstream must not look like losing its models.
  • Prices belong to one owner. Send them from the bridge or set them in the engine, not both; default pricing overwrites manual edits on every sync.
  • An empty catalogue is not pushed. A stack that lost all upstreams keeps its rows.

Limits

  • It federates engines, not arbitrary providers: every upstream is a SAIA API with /v1/models and the same route shapes.
  • It adds a hop, so first-byte latency grows and the front engine's read timeout must cover the upstream's generation time. The bridge's own read timeout defaults to null for that reason.
  • Streaming is relayed, so per-token accounting still happens in the front engine; the bridge never sees a usage total it could bill.
  • Retrying a non-streaming request means the upstream may already have generated it; a clone of the answer at the upstream is possible, which is why failover is limited to failures before output.
  • A per-upstream headers block exists for extra routing, and whatever it carries is configuration, not a user credential.
  • /v1/models reports ready/unavailable from the last refresh, so it can lag a status change by one interval.
  • Chat AI's own model configs are keyed by file name, so a bridge/<id> model cannot have a per-model JSON file; per-model defaults for a federated model have to arrive through the catalog row.

Deployment profiles and brands

Two tiers with different lifetimes. A deployment is chosen at build time and decides which modules, feature switches and guides exist. A brand is resolved at runtime, per user, and is almost entirely presentation: name, logo, colours, footer, the disclaimers the institution wrote and its default system prompt. The one thing a brand may also do is narrow - switch modules or features off, fix or allowlist the models, forbid the four capabilities that leave the institution's boundary. It can never widen anything the deployment disabled.

Build time · deployment

"deployment": "chat-ai" in front.json becomes VITE_DEPLOYMENT and selects config/deployments/<id>/index.json. The profile holds module switches, the features map (Meta chat, workspaces, MCP, E2EE, tutorials, Git import) and brand defaults. It is compiled in, so changing it needs a rebuild.

Every profile is inlined in every bundle, deliberately: it keeps useBrand() synchronous. Profiles therefore hold no secrets.

Runtime · brand

The brand is resolved per visit: ?brand= (test override, kept for the session) → the profile response's brand field → the first matching claim rule (group, entitlement, OU, e-mail suffix) → the deployment's default. Nothing brand-related is written to Redux or localStorage.

Logout clears the override so it cannot follow the next user into the same tab.

Brand · presentation

Name, logo variant, colours, surface tint, footer links, favicon, disclaimers, help PDF and the default system prompt. A brand is one folder, so nothing about an institution is spread over a profile or a defaults module.

Brand · restriction

restrictions.modules, .features, .models (fixed / allowed) and .external (web search, external models, MCP, external references). Only false, "false" or null is honoured, so the direction cannot flip.

How it works

  1. An unknown deployment id is silent. The loader falls back to chat-ai without failing the build, so a typo shows up only if you read the Deployment: line that Vite logs at startup. That is the first thing to check when a profile "does not apply".
  2. Modules have one accessor. utils/modules.js answers isToolsEnabled(), isAgentsEnabled(), isArcanasEnabled(), isSpeechEnabled(), isSyncEnabled() and the rest, and each one asks the profile first and the env var second. A component must never read import.meta.env.VITE_MODULE_*, or it will disagree with the profile.
  3. Defaults are preserved per key. tools, feedback and choices are opt-in; agent, agents and arcanas are opt-out; speech carries a value ("browser" or {model, voice}), not a boolean.
  4. A switch needs three wirings. The route, the entry point (sidebar section, prompt button, settings tab) and the behaviour. Miss one and the user sees a dead entry point; the minimal profile is the regression that catches it: every module off, every feature off except the Meta chat, /workspace/* and /agent/* redirect to /chat.
  5. A gated guide is hidden, not broken. FEATURE_GUIDE_AVAILABILITY and USE_CASE_AVAILABILITY name one predicate per gated entry; the catalogue, the Meta chat's tour tools, [[GUIDE:…]] markers and deep links all use the same reader. npm run validate:guides fails on an entry that names an unknown guide or a tools or Meta-chat guide without a gate.
  6. Brand CSS is emitted at runtime. Only values matching a hex pattern reach <style id="brand-theme">, and the dark block targets body.dark, because index.css re-declares the daisyUI colours there. A new CSS variable has to be added to THEME_TOKENS, or no profile can set it.
  7. A surface repaints a subtree. SURFACE_TOKENS maps sidebar background, hover, border, content and accent onto the base variables for .brand-sidebar only. A new surface needs the class on its root and an entry in the map.
  8. A brand is one folder. config/branding/<folder>/ holds brand.json plus every file it names - logo variants, disclaimer HTML, system prompt, help PDF, favicon. The loader resolves those names with ?url&no-inline, so they become hashed assets and are service-worker cached; the brand's favicon replaces the pre-boot one on mount.
  9. The footer is data, not code. CollapsibleFooter iterates brand.footer.links (imprint, privacy, terms, docs by default), following url and visible. footer.isoCertified: false removes the ISO 27001 line, because that certificate is one institution's and must not appear under another brand.
  10. A brand may narrow, never widen. config/brandPolicy.js is the only path from a brand into behaviour. It can switch modules and features off, fix or allowlist the models, and forbid the four external capabilities - and that is all, because only a value that explicitly disables something is read. A brand cannot enable a module the deployment turned off, add a model the deployment does not list, or change a layout or a route. The guarantee survives because deployment.js and utils/modules.js consult the brand, so isFeatureEnabled() and moduleValue() already return the effective value; enforcement then lives in the request and UI paths, not in a second checker.
  11. The policy is read from module state. BrandProvider calls setCurrentBrand() during render and App consumes useBrand(), so a late claim-resolved brand re-renders the tree. Non-React accessors read currentBrand(), which is why a new request path that must honour a restriction imports brandPolicy.js instead of reading VITE_MODULE_*.
  12. A restriction is stated, not silent. Profile → Institute names the institute and every narrowing it applies, and the Meta chat reports the same lines through brandRestrictionLines(), so a user who cannot find a model or a module can read why. When a policy matches nothing (a pinned id the deployment does not serve), the unfiltered list is kept so the app stays usable - and the section still says the brand restricts it.
  13. One deliberate content exception. A brand may own its own disclaimers and its default system prompt; those are the institution's words, not a feature switch. Everything else it carries is presentation, or the narrowing above.

Invariants worth keeping

  • One reader per module. A component that reads the env var directly breaks the profile.
  • Profiles hold no secrets. They are inlined into every bundle.
  • A brand only narrows. It cannot enable a module, a feature or a model the deployment disabled, and it cannot change layout or routes. Only an explicit false counts.
  • Narrowing goes through one file. brandPolicy.js - not a second check in a component, or the two disagree.
  • Every narrowing is visible. Profile → Institute and the Meta chat report it, so a missing model has a stated reason.
  • Only hex colours reach the theme tag. An arbitrary CSS value from a brand file would be an injection point.
  • minimal must work. A feature that only works with every module on is not finished.
  • A new gated guide gets an availability entry. Otherwise a tour points at an element a deployment does not render.

Limits

  • A deployment is a build input: changing it means a rebuild and a redeploy. Every VITE_* value is compiled into the bundle.
  • Locally, back returns a hard-coded sample user with no group claims, so the UGOE rule cannot fire; test with ?brand=UGOE.
  • A very wide lockup (UGOE is about 5.6:1) is illegible in the 40 px sidebar slot, so the brand sets a mark variant for the header.
  • A model restriction fails open: when the pinned or allowlisted ids match nothing on this deployment, the unfiltered list is kept so the app stays usable, and the Institute section carries the statement instead of the list enforcing it.
  • Restrictions reach the request paths one by one: a new feature that talks to the outside world is only as gated as the code that consults isBrandExternalAllowed().
  • Brand CSS cannot invent a token; the variable must exist in THEME_TOKENS or SURFACE_TOKENS first.

Why the split. Which features a site may run is an operational decision that should be reviewed and rebuilt, not toggled at runtime by whoever hits the app. What a site looks like, however, depends on who is signed in - and that has to change without a deployment. The one grey area is a consortium that has to serve several institutions from one build: those differ not only in colour but in what they may offer, so a brand is allowed to take features away. Taking them away only keeps the rule that makes a rebrand safe: nothing a brand says can add capability.
