# AGENTS.md

Guide for AI coding agents working in this repository. Read this before touching code.
Every statement here was checked against the code; see §8 before adding to it.
Human-facing docs: [README.md](README.md) (install/config), [CONTRIBUTING.md](CONTRIBUTING.md), [CHANGELOG.md](CHANGELOG.md).

## 1. What this repo is

The stand-alone **web interface of Chat AI** (GWDG / SAIA) — a browser chat client for any
OpenAI-compatible API endpoint. It is one of three repos in the wider architecture:

| Repo | Contents |
| --- | --- |
| **this one** (`gwdg/chat-ai`) | web interface: `front` + `back` |
| `gwdg/saia-hub` | API gateway, SSH proxy |
| `gwdg/saia-hpc` | Slurm scheduler + HPC scripts |

Two services, no monorepo tooling — each has its own `package.json` and is installed separately:

- **`front/`** — React 19 SPA, Vite 8, runs entirely in the user's browser. All chat data is local.
- **`back/`** — single-file Express 5 proxy (`back/service.mjs`, 412 lines). Per README it exists to
  hold the API key server-side and to prevent CORS errors in the user's browser.

## 3. Setup and commands

**Config is mandatory before anything runs.** Copy the samples first:

```bash
cp secrets/front.json.sample secrets/front.json
cp secrets/back.json.sample  secrets/back.json   # put a real apiKey in this one
```

`front/vite.config.js` calls `process.exit(1)` if `secrets/front.json` is missing or unparseable —
a front end that refuses to boot is almost always this.

### Native (preferred while iterating)

```bash
cd back  && npm i && npm run start   # :8081
cd front && npm i && npm run dev     # :8080
```

Both default `CONFIG_LOCATION` to `../secrets/<name>.json` and `path.resolve` it against the
**current working directory**, so run them from inside `front/` and `back/`, or set
`CONFIG_LOCATION` explicitly. The two services fail differently when the path is wrong: `front`
exits, while `back` only logs `Failed to read back.json. Using default values.` and keeps running
**with an empty `apiKey`** — so every upstream call comes back unauthorized. If requests are
rejected, check that log line first.

### Docker

```bash
docker compose build front back
docker compose up front back -d
docker compose restart front   # picks up config/source changes; rebuild if deps changed
```

Each Dockerfile sets `ENV CONFIG_LOCATION=/run/secrets/{front,back}`, fed by the docker secrets
declared in `docker-compose.yml`. Both services use `network_mode: host`, so ports are as
configured. `front/entrypoint.sh` greps `"mode"` out of `front.json` and runs `npm run dev` for
`dev`, `npm run prod` (`vite build && vite preview`) for `prod`, or `npm run build` for `build`;
anything else exits 1.

**`mode: "build"` is a one-shot static build, not a server.** `npm run build` is plain
`vite build`; Vite's default `outDir` is `dist`, and `docker-compose.yml` bind-mounts `./front` to
`/usr/src/app`, so the bundle lands at `front/dist/` **on the host**. The container then exits 0
(`restart: on-failure` does not restart it) and nothing is listening — serve that directory with
your own web server (README has nginx/Apache examples). A failed build exits non-zero and is
retried by that restart policy. `port` is unused in this mode. Every `VITE_*` value is compiled
into the bundle, so `front.json` is a build-time input: after changing it, rerun the build
(`docker compose up front` and `docker compose restart front` both re-run `entrypoint.sh`, so both
rebuild) and redeploy `front/dist`; an already-copied bundle does not change. The same holds
natively (`cd front && npm run build` with `CONFIG_LOCATION` pointing at `../secrets/front.json`).
`base` is hard-coded to `"/"` in `front/vite.config.js`, so the output assumes the domain root — a
sub-path deployment needs `base` changed plus a rebuild.

### Checks

```bash
cd front && npm run build    # vite build — works, ~6s
cd front && npm test         # vitest run — unit/component tests (jsdom + Testing Library)
cd front && npm run test:live       # starts a real `opencode serve` and drives the client
cd front && npm run test:watch
cd front && npm run test:coverage   # v8 text coverage report
```

**Live tests** are the `*.live.test.*` files, excluded from `npm test` because they spawn a real
process. `src/apis/__tests__/opencodeAgents.live.test.js` picks a free port, starts
`opencode serve` in a temporary HOME/XDG tree with `OPENCODE_SERVER_PASSWORD`, and runs the client
against it (info, auth, sessions, files, catalogues, shell, SSE, delete), then kills it and removes
the tree. It never prompts a model, so it needs no credentials or network, and it skips itself when
no `opencode` binary is on `PATH` (`OPENCODE_BIN` overrides the lookup). The live config
(`vitest.live.config.js`) reuses the unit-test setup and only changes `include` and the timeouts.

**`npm run lint` does not currently run.** The script invokes `eslint`, but neither `eslint` nor the
plugins `.eslintrc.cjs` extends are in `front/devDependencies`, so a clean `npm i` gives
`sh: eslint: command not found`. (`.eslintrc.cjs` is also the pre-flat-config format.) Don't put
lint in your verification loop until that is fixed, and don't report it as passing.

**Tests:** `front` uses Vitest with jsdom, fake-indexeddb, and Testing Library (`vitest.config.js`,
`src/test/setup.js`). Put tests next to the code as `*.test.js|jsx|ts|tsx`. `back` still has no
test suite (`npm test` is `exit 1`), and `.github/` contains only issue templates, so there is no
CI. A passing build or unit test is not evidence that the full UI works; exercise changes in a
browser when behaviour matters. **Include tests with new features:** add at least one focused
`*.test.js|jsx|ts|tsx` covering the new behavior, plus regression coverage for bugs you fix.

**Scope your test runs.** A change confined to one component or util needs only the spec next to
it, e.g. `npx vitest run src/components/Sidebar/__tests__/TopicList.test.jsx` (add
`npm run build` when JSX or exports changed). Keep the full `npm test` for the end of a task, or
for edits to shared code that many specs import (`Redux/reducers/`, `db/`, `utils/`). Vitest builds
a jsdom environment per test file, so a full run costs seconds after every small edit and rarely
reports anything the adjacent spec would miss. The reverse still holds: a green targeted spec is
not evidence that the whole suite is green.

**Extended tests (Playwright, `e2e/`).** `e2e/` is a separate npm package that starts the app
itself and drives a real browser; `e2e/README.md` is the full matrix and env-var reference.

```bash
cd e2e && npm i && npm run setup:e2e   # dependencies + Playwright browsers (+ Chrome for chrome-*)
cd e2e && npm run test:e2e             # deterministic suite against the mocked model
cd e2e && npm run test:opencode        # opt-in: local OpenCode agent, both specs
cd e2e && npm run test:opencode:agentic # opt-in: only the agentic scenario
cd e2e && npm run test:real            # opt-in: real model behind a back service you started
```

The default suite mocks `/models`, `/user` and `/chat/completions`, and every documented step
writes a screenshot and narrative to `e2e/results/documentation/<scenario>/<project>/` (`N.png`,
`N.md`, `index.md`; gitignored). With SAIA credentials (`SAIA_API_ENDPOINT`/`SAIA_API_KEY`, or the
`apiEndpoint`/`apiKey` of `secrets/back.json`), a vision model also checks each screenshot against
the step's expected `shows` text and a mismatch fails the test (`E2E_VISION=auto`; `1` requires
credentials, `0` disables the checks).

The opt-in agent scenarios are the extended tests for agent work. `tests/agent-opencode.spec.ts`
proves session creation, prompt delivery, streaming and a `!` shell turn without a model provider.
`tests/agent-agentic-tasks.spec.ts` is the full agentic task: it sends a prompt, so OpenCode runs a
real tool loop — `write hello.py`, `shell python3 hello.py`, `read hello.py`, then `edit` and run it
again — and the spec asserts the file on disk, the rendered tool cards and the docked preview.
`scripts/scripted-model.mjs` is the deterministic OpenAI-compatible model server and
`scripts/opencode-server.mjs` registers it as the project's `scripted` provider (the tool choices
are fixed; the execution, files and output are genuine). The two specs skip unless
`E2E_OPENCODE=1`, which the npm scripts set. They also skip when `E2E_OPENCODE_URL` points at a
server you started, because that server has to configure the `scripted` provider itself. Each mode
starts its own app instance, so combining `test:e2e`, `test:real` and `test:opencode` in one run is
refused by the config instead of silently sharing ports.

`npm i` can rewrite `package-lock.json`. Check `git status` afterwards and keep unrelated lockfile
churn out of your commit.

## 4. Architecture invariants

These are the things that are not guessable from the file tree.

### 4.1 Two stores, strictly separated

| Store | Holds | Where |
| --- | --- | --- |
| **Dexie / IndexedDB** (`app-conversations-db`) | conversations, messages, content items, files, folders | `front/src/db/` |
| **Redux + redux-persist** (localStorage) | `interface_settings`, `user_settings`, `last_conversation`, `migration_data` | `front/src/Redux/` |

`version` is in the root reducer but is not in the persist whitelist.

Redux is persisted with a `version` + `migrations` map (`Redux/store/migrations.jsx`). Which actions
are mirrored across tabs is decided by `Redux/store/stateSync.js`: every `user_settings/*` action
plus `SET_ADV`, `RESET_ALL`, `MIGRATE` and `SET_COUNT`. This is not optional book-keeping:
redux-persist rewrites the whole persisted state from every tab on every action, so a tab that does
not receive a `user_settings` mutation keeps a stale copy and writes it back. A server added in one
tab then disappears on the next reload of the other (the regression test is
`e2e/tests/mcp-persistence.spec.ts`), and the same holds for memories, memory groups and E2EE keys.
`interface_settings/*` is not synced, so its persisted keys still have that stale-tab exposure.
Adding a persisted key means adding it to `persistConfig.whitelist` **and** `getDefaultState()` in
`Redux/store/store.jsx`.

### 4.2 The conversation data flow

`ChatPage.tsx` holds the whole hydrated conversation in one `localState` object and passes
`localState` / `setLocalState` down the tree. `useSyncConversation` reconciles that object with
IndexedDB. Writes go through `updateConversation(id, data)` in `db/index.ts`, which:

- replaces title + settings + the **entire** message list in a single Dexie transaction, and
- enforces optimistic concurrency: unless `force` is passed it compares `data.lastModified`
  against the row in the DB and **returns `-1` without writing** on mismatch. `-1` means another
  tab changed this conversation, and surfaces as `modals/Chat/ConversationConflict.jsx`.

So: thread the `lastModified` you read through to the write, and handle `-1`.

Data is normalised across `conversations → messages → content_items`, with `files_meta` /
`files_data` holding attachment bytes keyed by `fileId`; `hydrateConversation()` joins them back
into the nested shape the UI uses. Raw table access (`db.messages`, `db.content_items`, …) appears
**only** inside `front/src/db/` — everywhere else uses the functions it exports.

### 4.3 Dexie migrations

`db/index.ts` is at **version 17**. A new *indexed* field needs a new `this.version(n).stores({...})`
block plus an `.upgrade()` that backfills existing rows — this is how `folderId` (v3),
`hasFirstPrompt` (v4), `lastOpenedAt` (v5), the workspace tables (v6-v8),
`workspace_file_references` (v9), the default Arcana filesystem source (v10), the default
browser source with the shared browser tree (v11), the `arcana_v2` → `arcana_tools` tool-toggle
rename (v15), the per-workspace browser tree (v16), and the `tools.browser_storage` default flip
(v17) were added. A field that is only stored and never
queried needs **no** version bump; Dexie keeps unindexed properties on the row as-is. A version
bump and `.upgrade()` are still appropriate when existing rows need a backfill. Never edit an
existing version block: users have live databases.

"Access storage" is `tools.browser_storage`, kept under that name for existing chats, exports and
the Meta chat, and it is **on by default** (`agent/storageAccess.ts`). v17 rewrites the old opt-in
`false` of existing conversations to `true`, so after that upgrade an explicit `false` always means
the user switched it off. With it off the model gets no data-access tools at all, even when a
folder is mounted or the chat is attached to a workspace; Arcana and MCP keep their own toggles.
The Browser agent's `codemode` tool is always offered, not a toggle. Writing is always on in the
chat's own storage; only an attached workspace has a `workspace_write_access` switch, on by default.

### 4.4 "folder" in code == "topic" in the UI

v1.0.0 renamed this feature for user-facing copy only. The `folders` table, `folderId`, and every
`*Folder*` function keep the old name. Don't rename them, and don't introduce "topic" identifiers
inside `db/`. UI strings and i18n keys say topic.

### 4.5 Config reaches the front end through vite.config.js

`secrets/front.json` is read **at Vite startup** and hand-mapped into `process.env.VITE_*`:
`VITE_BACKEND_ENDPOINT`, `VITE_MODELS_ENDPOINT`, `VITE_USERDATA_ENDPOINT`, `VITE_API_KEY`,
`VITE_DEFAULT_SETTINGS`, `VITE_TITLE_GENERATION_MODEL`, `VITE_MEMORY_GENERATION_MODEL`,
`VITE_PROPOSAL_GENERATION_MODEL`, `VITE_ANNOUNCEMENT`, `VITE_USE_OPENAI_SDK`,
`VITE_E2EE_KEY_URL`, `VITE_OPENCODE_SERVER_URL`, `VITE_OPENCODE_SERVER_USERNAME`,
`VITE_OPENCODE_SERVER_PASSWORD`, `VITE_FAKE_AUTH_HEADERS`, `VITE_MODULE_*`. Consequences: **a new
config key requires editing `front/vite.config.js` too**, and a config change requires a dev-server
restart. Read values via `import.meta.env.VITE_*`; they arrive as strings, hence the
`=== "true"` comparisons.

`apiKey` is optional and maps to `VITE_API_KEY`. When it is empty the app sends **no** Authorization
header and the OIDC proxy authenticates the user, as before. When it is set, `apis/authHeaders.js`
adds `Authorization: Bearer <key>` to the chat client (`fetchClient.js`), the SDK path in
`openaiClient.js`, the direct `fetch` calls (`getModelsData`, `getUserData`, `processFile`,
`generateAudio`), and the browser agent's model calls and tool requests (`agentApiKey` /
`agentRequestHeaders` in `apis/agentEndpoints.ts`, used by `agent/runAgent.ts`,
`agent/arcanaTools.ts` and the agent tools). That is only for endpoints without the OIDC proxy, e.g.
a SAIA engine's `/public/v1`; the key ships inside the bundle. Without a key the agent still sends
its `set-by-backend` placeholder, which `back` ignores but a direct endpoint rejects with
`Invalid API key` (it checks for a 32-character token). `getUserData` returns `null` when
`userDataPath` is unset instead of calling an undefined URL. `secrets/front-local-conf.json` is the
config for the local stack in `saia/saia-engine/local-testing`; run
`CONFIG_LOCATION=../secrets/front-local-conf.json npm run dev` from `front/` to use it. Direct mode
has no `/bridge/*`, no MCP gateway and no Arcana Tools: those routes exist only in `back`. The agent
bridge is the exception: a service-managed agent uses the agent service under `/agents/<id>/bridge`
(§4.27).

`fakeAuthHeaders` maps to `VITE_FAKE_AUTH_HEADERS` (a JSON string) and is merged into every
`authHeaders()` result; the SDK path passes the same object as `defaultHeaders` with
`Authorization: null` when no API key is set, because the SDK otherwise always sends one. It exists
for a direct engine whose Chat AI compatibility routes
under `/assumes_behind_oidc` expect the `oidc_claim_*` headers that Apache/`auth_openidc` injects.
The browser is then impersonating that user, so the key must stay out of a deployment. When
`backendPath` is absolute, `vite.config.js` proxies `/assumes_behind_oidc` to its origin in dev and
preview, so a relative `userDataPath` such as `/assumes_behind_oidc/user` stays same-origin and needs
no engine CORS change.

Feature modules are gated this way — `VITE_MODULE_TOOLS`, `VITE_MODULE_FEEDBACK`,
`VITE_MODULE_CHOICES`, `VITE_MODULE_AGENT` (the browser agent), `VITE_MODULE_AGENTS` (the sidebar
Agents section, on by default), `VITE_MODULE_ARCANAS` (Arcana and Arcana Tools, on by default), `VITE_MODULE_SPEECH` (`"browser"` — or the older `true` — enables speech with the browser's own voices and no backend TTS; a JSON object with `model` and `voice` uses an engine TTS model — read it through `utils/speechAudio.js#getSpeechModule`, not by parsing the env var). A deployment can
switch these parts of the UI off, so new code in those areas must still behave with the flag off.

### 4.6 Model capabilities are data, not code

`front/src/config/models/<model-id>.json` is auto-globbed by `getModelDefaults.jsx` via
`import.meta.glob`, keyed on the filename. To give a model reasoning-effort support or other
per-model defaults, add or edit the JSON named exactly after the model id — no code change and no
registry to update. A model id containing `/` (e.g. `bridge/local-echo-1`) cannot have a config file,
because the keys are file names.

`modelSupportsTools()` (`apis/agentEndpoints.ts`) takes tool support from data, not from the display
name: the `external` field of the extended `/models` response, `"tools": true|false` in the model
config, or a rejection learned at runtime (`markToolless`, retried by `runAgent`). **"(External)" in
a name is not a tool-capability signal.** Bridge models carry it so the engine's demand updater
skips them, while `saia-engine` keeps their tools in the request body; reading the marker as "no
tools" leaves every bridge model without tools, workspace tools included.

### 4.7 Secrets

The API key is read only by `back/service.mjs` from `secrets/back.json`. `secrets/.gitignore`
ignores everything in that directory except itself, so real config files there are invisible to
git. Never move a key into front-end code or into a `.sample`.

### 4.8 The back service's responses can mislead you

Verified in `back/service.mjs`:

- **`/models` always returns HTTP 200**, even when the upstream rejects the request — the handler is
  `res.status(200).json(await response.json())`, so an upstream `{"message":"Unauthorized"}` arrives
  as a 200. Check the response body, never the status.
- **If `apiKey` is empty, `Authorization` falls back to the `inference-id` request header** rather
  than erroring — that is how the deployed setup passes per-user credentials through.
- **`/chat/completions` rebuilds the request from a fixed set of fields.** Anything else the client
  sends is dropped. `function` tools and `tool_choice` (the browser agent's) are forwarded only
  when `enable_tools` is unset; with `enable_tools` the request goes to the tool gateway instead.
- **`/user` is a hard-coded placeholder** in this repo: it always returns the same `sample-user`
  object. Real user data comes from the gateway in a full deployment, so don't debug user/usage
  features against this response.

### 4.9 Typst rendering is client-side, from fenced code blocks

**Entry point.** `rendererComponents.code` in `MarkdownRenderer.jsx` handles fenced blocks:
` ```mermaid ` goes to `MermaidDiagram.jsx`, ` ```latex ` / ` ```tex ` goes to `LatexBlock.jsx`
(§4.10), ` ```typst ` / ` ```typ ` goes to `TypstBlock.jsx` (rendering defaults to off via the
preference), and every other language also goes to `TypstBlock.jsx` with `defaultRender={false}`.
Inline code is returned directly and never rendered.

**Pipeline.** `TypstBlock.jsx` lazily imports `@myriaddreamin/typst.ts` on the first render. Its
compiler and renderer WASM files are imported with Vite's `?url` (`TypstBlock.jsx:6-7`), so Vite
emits them as app assets; nothing is fetched from a Typst server. The first render calls
`$typst.svg({ mainContent })`, which runs the Typst compiler and renderer WASM in the browser and
returns an SVG string. That SVG is sanitised, cached by source text (max 50 entries), and inserted
into a shadow root attached to the block's container. The shadow root is required because Typst's
SVG carries its own `<style>` with global selectors such as `svg { fill: none; }`; in the light DOM
that silently strips the fill from unrelated app icons. After mounting, full-page page-background
shapes (Typst emits one for `#set page(fill: ...)`) are ignored for measurement, then the viewBox is
rewritten to the rendered content's `getBBox()` plus 6 pt padding, so the unused page canvas is
cropped away. The back service and API endpoint are not involved.

**Scheduling.** Rendering is debounced by 400 ms, so streaming code blocks are not recompiled on
every keystroke. `$typst` is a single shared, stateful instance, so `TypstBlock` serialises all
compilations through a module-level promise queue; a cancelled render is ignored when it finishes.
Compile errors fall back to the raw source.

**Per-block UI.** ` ```typst ` / ` ```typ ` blocks start rendered or as code according to the
`user_settings.render_typst` flag (Chat preferences → Rendering). All other code blocks start as
code. Every block keeps a "Render as Typst" / "Show code" toggle regardless of the preference; the
preference only selects the default view. The selector defaults the flag to `false`, so blocks are
shown as code unless rendering is enabled.

**Resources and security.** The WASM modules are served from the app's own build output. The
default text fonts are vendored in `front/public/typst-assets/` (from
`typst/typst-assets@v0.13.1`, with its LICENSE/NOTICE) and `TypstBlock.jsx` passes
`loadFonts([], { assets: ["text"], assetUrlPrefix: ... })` so typst.ts does not add its jsDelivr
font loader. The `assets` option must stay set, otherwise typst.ts appends its own remote loader.
Model output is untrusted: the SVG is
sanitised with DOMPurify's SVG profile plus `ADD_TAGS: ["use"]` (the profile otherwise drops
`<use>`, which Typst uses to reuse glyphs), and `data_selection.js` is disabled.

### 4.10 LaTeX document blocks render client-side with faster-latex

`rendererComponents.code` routes ` ```latex ` / ` ```tex ` fences to `LatexBlock.jsx`; other code
blocks still go to `TypstBlock.jsx` with `defaultRender={false}`. `LatexBlock` lazily imports the
`faster-latex/web` build, initializes its WASM (emitted as a Vite asset), and calls
`render(source, { fullDocument: false })`. The WASM is imported via the `faster-latex-wasm` alias
in `vite.config.js`, which maps to the package's `web/faster_latex_bg.wasm`; this is required
because the package's own `new URL(..., import.meta.url)` path works in the production build but
not in the dev server. faster-latex is a Rust→WASM LaTeX subset that emits HTML
with MathML; it is **not** a full TeX distribution — `\usepackage`, TikZ and other primitives are
unsupported, and unsupported constructs produce warnings and visible fallbacks rather than failing.
The HTML is sanitised with DOMPurify's `html` + `mathMl` profiles, then inserted into a shadow root
with the shipped article CSS plus a small override, so the stylesheet cannot leak into the app.
Rendering is debounced by 400 ms and cached by source text. `user_settings.render_latex` only
selects the default view; every block keeps a "Render as LaTeX" / "Show code" toggle. No back
service or API endpoint is involved.

### 4.11 TikZ inside LaTeX blocks renders with self-hosted TikZJax

TikZ is **not** a separate code-block type. `LatexBlock` preprocesses every ` ```latex ` / ` ```tex `
block: `tikzRenderer.js` extracts `tikzpicture`/`tikzcd` environments, strips
`\usetikzlibrary` and known `\usepackage` declarations from the text, and replaces each environment
with a `TIKZPLACEHOLDER<n>END` token. The extracted snippets are rendered off-screen through
TikZJax (a hidden `<pre class="language-tikz">`) to SVG strings, while the cleaned source is
rendered with faster-latex. The tokens are then replaced with
`<span class="latex-tikz">…SVG…</span>`, and the combined HTML is sanitized with DOMPurify's
`html` + `svg` + `mathMl` profiles (plus `ADD_TAGS: ["use"]`).

TikZJax's dist and its ~7.7 MB of TeX/font assets are copied from `@rod2ik/tikzjax` into
`public/tikzjax` by `scripts/copy-tikzjax.mjs`, which runs as `predev` / `prebuild` / `preprod`;
that directory is gitignored. `vite.config.js` serves `/tikzjax/*.gz` with
`Content-Encoding: identity`: otherwise Vite marks the `.gz` files as gzip-encoded, the browser
transparently decompresses them, and TikZJax's own gunzip fails with "incorrect header check".
`tikzRenderer.js` sets `workerMode: "direct"` and disables `workerPool`; the pool path wraps the
worker in a blob and loads it with `importScripts`, which can fail under some deployments/CSPs.
Only packages in the loader's known set are forwarded; TikZ libraries from
`\usetikzlibrary` and preamble commands such as `\tikzset` are forwarded via the pre's data
attributes. `user_settings.render_latex` controls the LaTeX block's default view. The TikZJax
package is GPL-3.0+.

### 4.12 Two model-selector variants, chosen from the data

`Header/ModelSelectorWrapper.tsx` renders one of two selectors for all three call sites (header,
prompt-box `ModelButton`, settings `DefaultModelSelector`). The choice is
`modelsData?.[0]?.description !== undefined`: SAIA / Chat AI returns `description` (plus
`releaseDate`, `company`, `contextLength`, `external`, …), so it gets `ModelSelectorExtended`;
a plain OpenAI-compatible `/models` response does not, so it gets `ModelSelectorSimple`. Only the
**first** model is inspected, so a mixed or reordered response silently selects the wrong variant.
Both are data-tolerant (optional chaining), but the simple selector has no metadata columns or
view modes. Add new model fields to `types/models.ts` and both selectors if they affect both
variants. When a conversation's stored model id is not in `modelsData` (for example an imported
persona references a model this deployment does not offer), the wrapper replaces it with the user's
default model and only falls back to `modelsData[0]` if that default is unavailable too.

### 4.13 Document conversion can run in the browser or on the server

`utils/browserDocumentConversion.js` converts `pdf` (PDFium WASM via `@hyzyla/pdfium`) and `docx`
(`mammoth`) locally. `user_settings.document_conversion_mode` is `"server"`, `"browser"`, or
`"choice"` (default). `Prompt/Attachment.jsx` renders one Process button for the fixed modes and
two for `"choice"`; the browser path is only used when that file type is supported, otherwise it
calls the `back` `/documents/convert/file` endpoint. Redux migration 5 maps the previous boolean
`browser_document_conversion` flag (`false` → `"server"`, otherwise `"choice"`). PDF text extraction
runs in the package's blob worker first; if the worker cannot be created (for example under a strict
CSP) it retries on the main thread. The PDFium WASM is imported with `?url` so Vite emits it as an
app asset.

A model can accept binary documents directly instead of requiring conversion.
`utils/modelCapabilities.js#modelSupportsFileType` treats a specific `pdf`/`docx` as supported when
`input` (or `capabilities`) contains a generic `file`, `files`, `binary`, `document` or `documents`
modality, or the matching type (`pdf`; `docx`/`word`/`wordprocessingml`), or when the model object /
`config/models/<id>.json` sets `supports_binary`, `supports_binary_data`, `supports_binary_input` or
`supports_file_input`. In that case an unprocessed file of that type is sent as an OpenAI `file`
content part (`{ type: "file", file: { file_data, filename } }`), `Prompt.jsx` does not block the
send, and `Attachment.jsx` still offers the Process buttons but without the "must process" warning.
Without the capability the previous behaviour applies: `Prompt.jsx` blocks, and
`processContentItems` drops an unprocessed PDF (and falls back to text for DOCX).

### 4.14 Prompt submission key is a user setting

`user_settings.send_with_enter` controls whether plain Enter or Shift+Enter submits the prompt:
`true` = Enter sends, `false` = Shift+Enter sends, `null` = device default. The default is
resolved by `hooks/useSendWithEnter.ts`: Enter on desktop, Shift+Enter on mobile. `PromptTextArea`
implements the key handling, and `SendButton` uses the same hook for its shortcut tooltip. Alt with
Enter always inserts a newline. When adding another user setting, update
`userSettingsReducer`'s `initialState`, the `getDefaultState()` fallback in `Redux/store/store.jsx`,
both i18n files, and the export/import path.

### 4.15 Sidebar conversation grouping is a persisted interface setting

`interface_settings.conversation_grouping` is `"topic"` (default), `"date"`, `"created"`, or
`"size"`. The sort menu in `SidebarContent` dispatches `setConversationGrouping`, and `TopicList`
receives the value as `grouping` to render either topic rows or a date-bucket tree. `size` bypasses
`TopicList` and renders all chats as a flat list sorted by their OPFS browser-workspace size.
`date` uses
`groupConversationsByDate` (modified time); `created` uses `groupConversationsByCreationDate`. Both
date-like modes show a non-collapsible parent label; their date buckets sit at the top level and are
collapsible. Collapse state reuses `collapsed_topics` with `__by_date__` / `__by_created__`
prefixes; the pinned section uses `__pinned__`. Created-mode rows also show the
creation date beside the title. The date/created labels
only appear in their own mode; the topic-creation/unsorted rows only appear in topic mode.
Pinned items are a top-level section (`Sidebar/PinnedSection.tsx`) above the sticky Chats band,
outside the `chatsCollapsed` conditional, with its own `__pinned__` collapse id. It holds pinned
chats and topics (rendered by `TopicList` with `variant="pinned"`, which renders only those rows and
no header, collapse logic or create-topic row) plus pinned workspaces and agents. Those two lists
are the real components rendered a second time with `variant="pinned"`, so a pinned row is the whole
subtree (attached chats, agents and sessions) with its own options menu, not a link row. Pinned chats
are not groups, so they are marked with a leading
dash in the slot where a topic shows its collapse chevron, and never with a vertical connector line.
`SidebarContent` builds one `topicListProps` object and spreads it into both `TopicList` instances.
Pinned workspaces and agents stay in `WorkspaceList` / `AgentList` as well, so the pinned row is a
second view, not a move; they are unpinned from the pinned row's options menu or their own row's
menu. The two copies fold independently: the pinned copy keys its `collapsed_topics` /
`expanded_agents` ids through `Sidebar/pinnedState.ts` (`__pinned__:` prefix), so expanding or
collapsing the pinned row leaves the same row in its own section untouched. `setWorkspacePinned`
writes `WorkspaceRow.pinned` (unindexed, no Dexie bump) and
`setAgentPinned` writes the localStorage agent entry. The new-chat row sits directly below the Chats
band, above the search panel and the list.
It is in `interfaceSettingsSlice`'s `initialState` and `getDefaultState()`; an old persisted state
without the key falls back to `"topic"` in the selector, so no migration is needed.

A colored group (topic or workspace) tints its name row with a light wash of the group color, and the
chats, agents and sessions below it are bracketed left and right in the same color. The alphas live
in `groupRowTint` / `groupRule` (`Sidebar/topicColors.ts`) and differ by theme and by whether the
group is open. The wash is applied through the `--group-tint` / `--group-tint-hover` CSS variables
with `bg-[var(--group-tint)]` and `hover:bg-[var(--group-tint-hover)]`, not as an inline
`backgroundColor`, because inline styles beat the hover utility.

The new-topic row in `TopicList` carries a collapse-all control on the right. It acts on the topic
ids only — pinned topics, regular topics, and the unsorted bucket once it holds chats — through
`collapseTopics` / `expandTopics` (`expandTopics` is the counterpart added for it), and turns into
expand-all once every one of those ids is collapsed. Sections, date buckets, workspaces and agents
share the same `collapsed_topics` list and must stay untouched.

The Pinned, Chats, Workspace, Agents and MCP Servers sections share one header style: an uppercase
semibold label row on a `bg-base-200/70` band, with `mx-2 my-1.5 border-t border-base-300` rules
between the sections in `SidebarContent`. Every header starts with the collapse chevron and then a
12 px section icon (chat bubble, workspace grid, robot, server; Pinned uses its pin there), so the
sections stay distinguishable while collapsed. A new sidebar section should reuse that pattern,
icon included. The Workspace section header and the workspace rows, and the topic rows in
`TopicList`, are the exception the admin asked for: their disclosure chevron sits at the trailing
edge of the row, after the label (and after the per-row actions), never before the icon.
Chat rows nested under a workspace reuse the topic chat row's chrome exactly — `rounded-xl
border border-transparent px-2 py-1`, active `bg-base-200 shadow-sm`, title `text-xs
leading-relaxed`, and a trailing control in the same 28 px slot (`Workspace/WorkspaceList.tsx`
against `renderConversationRow` in `Sidebar/SidebarContent.tsx`) — so the two lists read at the same
size; the admin asked for that on 2026-11-17, so keep them in step. The topic row additionally shows
its "modified" metadata line when selected; the workspace row does not.
Agents and MCP Servers are advanced sections: both, with their dividers and pinned agent rows, are
rendered only while `user_settings.advanced_mode` is on (`selectAdvancedMode`, default off). The
switch lives in one place only — the profile modal's Chat tab
(`modals/UserSettings/ChatPreferences.jsx`, `data-guide="profile-advanced-mode-preference"`). It was
removed from the prompt box's chat settings panel at the admin's request (2026-11-17) so the prompt
panel stays to model/temperature; with it off the sidebar is chats, topics and workspaces.

The chat's close control is a circle X (`Conversation/CloseChatButton.jsx`, `data-guide="close-chat"`)
rendered in normal flow at the top of the messages area, directly below `HallucinationWarning` and any
persona banner — never floating over the conversation, and never stacked above the undo button, which
alone stays in the bottom-right cluster.

### 4.16 Meta chat works from conversation summaries, not messages

The AI icon in the sidebar header navigates to `/meta`, rendered by
`Pages/MetaChatPage.jsx`. The page reuses the normal chat shell (`Header`, `SidebarWrapper`,
`Conversation`, `Prompt`) and provides `MetaChatSendContext`, which `useSendMessage` delegates to
`useMetaChatSend` while inside the page. A banner above the conversation labels it as the Meta chat
and shows an example question.

The Meta chat does not embed the chat list, topics, settings, personas, tutorials, use cases, or
message excerpts in its system prompt. It runs a function-tool loop: `utils/metaTools.js` defines
`list_chats`, `list_topics`, `get_chat`, `search_messages`, `list_memories`, `get_user_settings`,
`list_models`, `list_personas`, `list_tutorials`, `start_tutorial`, and `start_use_case`.
`useMetaChatSend` sends them as `settings.function_tools`; `apis/chatCompletions.jsx` forwards them,
and `back/service.mjs` passes function tools through when `enable_tools` is false. The model must
call the relevant tool for current data because the interface state can change between user
messages. `list_chats` returns summaries and per-chat settings (model, temperature, top_p, reasoning
effort, memory-mode override, enabled tools, Arcana, MCP); missing summaries fall back to the title.

The meta chat is stored as a hidden conversation row (`id: "meta-chat"`, `isMetaChat: true`),
excluded from the sidebar, last-conversation lookup, and its own summary context. `getExportData()`
emits it as `meta_chat` and `useImportConversation` recreates it silently. Do not make it summarize
full conversations on the fly without accounting for the extra model calls.

Personas come from `list_personas` (`gwdg/chat-ai-personas` via `utils/personaCatalog.js`, cached in
memory and `sessionStorage`). The model links to one inline with `[label](/persona/<path>)`;
`MarkdownRenderer` routes that link to `PersonaStartLink`, which fetches the persona JSON and starts
a new chat through `useImportConversation`. The legacy `[[PERSONA:<path>]]` marker still renders a
`PersonaCard` below the message. The catalog is metadata only: the full persona JSON is fetched when
the user clicks, and the Meta chat must keep working if GitHub’s tree API fails or is rate-limited.

For navigation and message search, the model calls `search_messages`; results include exact
conversation and message ids. It cites messages as
`/chat/<conversation id>?message=<message id>`; `Conversation` reads that query parameter, scrolls
to the message, and highlights it briefly. `MarkdownLink` routes `/chat/...`, `/topic/...`, and
`/settings/<tab>` internally; settings links dispatch `chatai:open-settings`, handled by
`useSettingsDeepLink` in `ChatPage`/`MetaChatPage`, and `UserSettingsModal` opens the requested tab
with a brief highlight. `get_user_settings` returns the module flags and global preferences.

Tutorials and use cases start through the `start_tutorial` / `start_use_case` tools, which dispatch
`chatai:start-feature-guide` / `chatai:start-use-case`, or through inline links
`[Start tutorial](/tutorial/<feature id>)` / `[Start use case](/use-case/<use case id>)` handled by
`MarkdownLink`. The legacy `[[GUIDE:...]]` and `[[USE_CASE:...]]` markers still start them when no
tool already did, and `[[PERSONA:...]]` remains supported.

Mutating chat actions are proposals, never applied by the model. It emits `CREATE_CHAT`, which
creates a new conversation with validated settings and text-only initial messages, plus `RENAME_CHAT` /
`MOVE_CHAT`, `PIN_CHAT`, `PIN_TOPIC`, `PIN_WORKSPACE`, `PIN_AGENT`, `SET_SETTING`, `MCP_SERVER`, and memory markers
(`utils/metaActions.js`), which `MetaActionCard` renders below the message with a warning icon and
an explicit Accept button. `MCP_SERVER` adds, updates, or removes per-chat MCP servers (local URL
entries or remote gateway ids), and with `target: "global"` it changes the sidebar MCP server list
in `user_settings.mcp_servers`; the Meta chat reads the entry ids from `get_user_settings`.
`test_mcp_server` tests a configured local server by id, name, or URL. Stateful "what's new" uses
`get_whats_new`, which checks every session and subagent session of every agent (status and
`time.updated` since the last check), and stores the last check in localStorage
(`chatai.meta.last-check`). The same report is rendered by `MetaChangesPanel`: the Meta chat shows
it globally, while the panel inside a workspace chat (`ChatAgentSidebar`) passes a `scope` of that
chat's workspace ids, so `getWhatsNew` only reports the workspace's chats, agents and the sessions
attached to them (subagents of an attached session are kept; an active session outside the scope is
not named). That panel shows only the report: connected agents and their sessions are listed in the
sidebar, not repeated below the report. The same panel carries two more tabs besides the report —
**Workspace** (`files_tab`, a read-only `WorkspaceFilesPanel` tree of the workspace root, chat
folders labelled by chat title) and **Sessions** (`sessions_tab`, a `WorkspaceSessionsPanel` list of
the workspace's chats whose rows look like the sidebar's workspace chat rows and navigate to
`/chat/<id>`) — through `MetaChangesPanel.tabs` (`{id,label,content}[]`, default none, so the Meta
chat's global panel has no strip). "Check now" sits in its own row under the strip and only on the
report tab. The panel follows the left sidebar's conventions: it defaults to 240 px (the sidebar's
`15rem`, clamp 200–1024 after a drag; a dragged width is saved in `chatai.meta.changes-width-v2`
and reopened at that width), starts collapsed below 1280 px to the same 64 px rail as the
sidebar, and an explicit collapse/expand (localStorage `chatai.meta.changes-collapsed`) overrides
the viewport on every later load. Its tab strip is compact (11 px, `whitespace-nowrap`) so three
tabs and the chevron fit in 240 px. A scoped report shows a topic only when one of those chats
is in it and omits memories,
which belong to the account rather than to a workspace; agent files stay agent-level because they
have no session link. Scoped results are stored under
`chatai.meta.last-check*:<workspaceIds>` so they never mix with the Meta chat's global result.
`search_all`
searches chats, messages, topics, memories, agent histories, and agent file names/contents.
`agent_health` combines agent connectivity with local MCP tests; `list_mcp_tools` exposes tool names.
`list_workspaces` plus `WORKSPACE_LINK` proposals attach/detach workspaces to agents or chats.
`AGENT_ACTION` proposals can prompt or interrupt an agent and are not revertible.
`list_agents`, `list_agent_sessions`, `check_agents`, `get_agent_history`, `list_agent_files`,
`list_recent_agent_files`, `read_agent_file`, and `fetch_agent_file` use the existing direct
OpenCode connection to inspect agents, their messages, and project files. `list_agent_sessions`
returns top-level and subagent sessions with the active one marked; `get_agent_history` accepts an
optional session id or title. The `AGENT_SESSION` proposal creates, switches, or deletes sessions;
creating is revertible by returning to the previous session and deleting the created one, while
deleting is not revertible. Normal chats expose the same access only for workspace-connected
agents through `connected_agent_list_sessions`, `connected_agent_switch_session`,
`connected_agent_remove_session`, and the `session` argument of `connected_agent_history`.
Those chat tools are scoped to the workspace: `connectedAgentTools.ts` resolves the chat's
workspaces, then filters each agent's session tree with the `workspace_agent_sessions` links of the
workspaces that link that agent (`filterSessionTree`), so a chat can only list, read, switch to or
delete sessions attached to its own workspace. `connected_agent_history` uses the active session by
default and refuses when that session is not itself attached, instead of reading it anyway, while the
names lookup resolves titles inside the filtered tree. An agent attached only through
`bridgeWorkspaceId` (whole-workspace bridge, no session links) keeps access to all of its sessions.
A chat attached to a workspace always receives the `connected_agent_*` tools, even when no agent is
attached: `connected_agents_status` then answers "no agents attached", and the system prompt lists
the attached agents by name so the model does not have to guess from a generic tool description.
The tools' file operations read the agent's own (possibly remote) OpenCode filesystem over HTTP, so
they work without a bridge or an attached workspace mount.

File listings preserve modification/access timestamps when the server returns them;
recent-file queries sort by modification time and, because `/fs/list` may omit timestamps, run a
fixed Node `fs.stat` listing through the OpenCode shell tagged `CHATAI_FILE_STAT`. Internal shell
commands carrying `CHATAI_GIT_LOG` or `CHATAI_FILE_STAT` are filtered from the agent chat. `fetch_agent_file`
attaches the file to the Meta chat through `saveFileReady`, so images and other binaries render as
normal attachments. Agent links use `/agent/<id>` so `MarkdownLink` renders them as internal cards. Reverting a created chat deletes it only if its title,
settings, and messages still match what was created. Only that click calls `updateConversationMeta` /
`assignConversationToFolder` / `setConversationPinned` / `setFolderPinned` or dispatches
`importUserSettings`; markers
are stripped from rendered markdown and from Meta-chat history. Memory indices come from the
`list_memories` tool. After applying, the card stores a snapshot and
offers a revert action; it only reverts if the current chats/settings/memories still match the
values that were applied. A successful revert returns the card to the unapplied state, so the same
proposal can be accepted again. Accept (or no decision) is stored as `meta.actionDecision` on the
assistant message; reverting stores `rejected`. `useMetaChatSend` prefixes the next user message
with “I accepted the change.” / “I rejected the change.” / “I cannot decide.” so the model sees the
outcome.

**Every new setting must be reachable from the Meta chat.** When adding a global, per-chat, or
feature-specific setting, expose its current value through a Meta-chat read tool (or an existing
tool’s output) and add a confirmable mutation marker with `MetaActionCard` apply/revert support. Do
not ship a setting that the Meta chat cannot read or propose to change.

The Meta chat honors the conversation's effective memory mode and group for memory learning: in
Learn mode it runs the same memory update path as normal chat and writes learned/replaced memories
to the effective group.

### 4.17 Per-conversation memory mode overrides the global preference

`ConversationSettings.memory_mode_override` is `"default"`, `0` (off), `1` (recall), or `2`
(learn). `getDefaultSettings()` defaults it to `"default"`, and `useSendMessage` resolves it at send
time: `"default"` uses `user_settings.memory_mode`; a numeric value overrides it for that chat. The
control is `SettingsPanel/MemoryModeContainer.jsx`; the global preference remains in
`UserSettings/ChatPreferences.jsx`. The value is stored with the conversation settings (no Dexie
version bump) and restored by `useImportConversation`.

### 4.18 Tutorials and use cases are static config; only completion is persisted

The UI's "tutorials" are the code's **feature guides**. Both tutorials and use cases are plain
JavaScript object literals, not database rows or JSON files:

- `front/src/config/featureGuides.js` exports `featureGuides`, keyed by feature id
  (`upload_file`, `select_model`, …). Each entry has `titleKey`, a model-facing `prompt`,
  `keywords`, and `steps`. Steps carry `target` selector(s), `textKey`, and optional tour logic
  (`prepare`, `check`, `completeOnTargetClick`, `completeOnEvent`). `FEATURE_CATEGORIES` groups the
  ids, and `buildFeatureGuidePrompt()` feeds the ids and prompts to the Meta chat.
- `front/src/config/useCases.js` exports `useCases`, keyed by use-case id. Entries have `category`,
  `prompt`, `keywords`, and `steps`; a step may reference a `tutorialId` to launch one of the
  feature guides. `USE_CASE_CATEGORIES` groups them, and `buildUseCaseGuide()` turns a use case into
  a custom tour.

Visible copy is not stored in these objects: titles and step texts are i18n keys resolved from
`front/src/i18n/en.js` and `de.js`. Element preparation lives in
`front/src/config/featureGuideActions.js`, and the tour runtime is `FeatureGuideContext` +
`SettingsPanel/TourManager.jsx`.

The only persisted part is progress, in the Redux `interface_settings` slice:
`completed_tutorials`, `completed_use_cases`, and `suppressed_tutorials` are id arrays, dispatched by
`markTutorialCompleted` / `markUseCaseCompleted` / `suppressTutorial` and persisted to localStorage
by redux-persist. The code's `featureGuides`/`useCases` definitions are never written to Dexie.

When adding one, edit the relevant config file **and** its category list, add every `titleKey` /
`textKey` to both i18n files, and target an existing `data-guide` attribute or class. Run
`cd front && npm run validate:guides`; `front/scripts/validate-feature-guides.mjs` checks ids,
categories, tour targets, and the en/de keys.

**Every new proper user-facing feature should ship with at least one feature guide (tutorial).**
Use cases are optional and compose existing tutorials into longer workflows; they do not replace
the tutorial for the feature itself.

### 4.19 Chat requests use a fetch client; the openai SDK is opt-in

`apis/openaiClient.js` `createBackendClient()` returns `{ chat: { completions: { create } } }`
from `apis/fetchClient.js`, a small fetch + SSE client that mirrors openai v6 behaviour the app
relies on: `APIError` with `status` / `error` / `code` / `type` and a `"<status> <msg>"`
message (read by `sendMessage.jsx`), a timeout that only covers waiting for response headers, two
retries on 408/409/429/5xx and connection errors, `"Request was aborted."` when aborted before
the response, and a stream that **ends quietly** when aborted mid-stream. Gateway chunks with
`object: "error"` pass through as data (`chatCompletions.jsx` throws on them); a chunk with an
`error` key throws. `"useOpenAISdk": true` in `front.json` switches back to the SDK, which is then
dynamically imported. The browser agent does not use either: it talks to the API through pi-ai's
own `openai-completions` client (`agent/runAgent.ts`).

### 4.20 Heavy renderers and libraries load on demand

Keep these out of the entry chunk; a static import of any of them undoes it:

- **KaTeX**: `SafeMarkdown` imports `rehype-katex` + `katex.min.css` only once some content
  matches `MATH_HINT` (`$`, `\(`, `\[`, `\begin{`); until then math renders through the plain
  `math` / `inlineMath` components.
- **Mermaid**: `MermaidDiagram.jsx` `loadMermaid()`.
- **Syntax highlighting**: `Code.jsx` uses `PrismAsyncLight`, which fetches the Prism core and
  each grammar on first use. Its loader map only knows canonical names, so aliases (`js`, `py`,
  `sh`, `html`, …) go through `LANGUAGE_ALIASES`; add one there when a fence name renders unhighlighted.
- **jsPDF** (PDF export) and **Joyride** (tour) are imported when used. The agent
  (`agent/runAgent`) is dynamically imported on send and **prefetched on idle** by `ChatPage` when
  `VITE_MODULE_AGENT` is on.

### 4.21 The build precompresses assets and emits a service worker

`vite-plugins/staticAssets.js`: `staticAssetsBuild()` writes `dist/sw.js` and then a `.br` + `.gz`
next to every compressible file (one plugin on purpose: Rollup runs `closeBundle` hooks of
different plugins in parallel). Brotli quality is tiered by size and type to keep this at ~10 s;
q11 on fonts/WASM tripled the build time for little gain. `servePrecompressed()` serves those in
`vite preview` with immutable caching for `/assets/`; Vite's own preview compression gzips on the
fly and never compresses `application/wasm`. `sw.js` is registered only in production builds
(`main.jsx`). It caches on first use, never precaches, handles only paths in its build manifest
(hashed `assets/` and the vendored `typst-assets/` / `tikzjax/`, the latter keyed by content
hash), and prunes stale entries on activate. TikZJax's own `.gz` files are real payloads, not
precompressed siblings: never serve them with `Content-Encoding` (see §4.11).

### 4.22 Arcana Tools and remote files are proxy-backed by saia-rag-web

The GWDG tool `arcana_tools` and the agent's `arcana_*` tools call the back service's `/arcana-tools/*`
routes, which proxy the saia-rag-web Arcana API at `remoteFilesEndpoint` (default
`http://localhost:8000/arcanas/api/v1`). The tool was previously called `arcana_v2`, and that name is
still an external contract in two places: the gateway's tool type is emitted as `arcana_v2`, and the
old `/arcana-v2/*` routes are aliased to `/arcana-tools/*`. Front-end settings accept
`arcana_v2`/`remote_file_access` as legacy keys. The alias must be a path-less `app.use`
middleware: Express restores `req.url` when a mounted path is trimmed, which undoes a rewrite done
inside `app.use("/arcana-v2", …)`. They cover creating and listing Arcanas and files,
reading/uploading/replacing/deleting files, starting/checking/deleting indexes, and
listing/adding/removing members.
The user identity is read from the incoming `x-auth-claim-uid` header (falling back to
`x-consumer-custom-id`, `oidc_claim_uid`, then `inference-id`) and forwarded as `x-auth-claim-uid`.

The legacy `/remote-files` routes use the same backend but store generic files in the dedicated
Arcana `remoteFilesArcana` (default `remote-files`), which is created on first write. Remote paths
are encoded into flat Arcana filenames (`rf_` + base64url), so the same path lists, reads, writes
and deletes through the saia-rag-web file endpoints.

### 4.23 Memories can be grouped; conversations choose a group

`user_settings.memory_groups` holds custom groups (`{id, name}`) and `user_settings.default_memory_group`
selects the group used by default. The implicit id `"default"` is the normal/ungrouped memory group.
Each memory's optional `groupId` defaults to `"default"`. `UserMemoryContainer` shows the groups
directly under User Memories and manages the default group; clicking a group opens
`UserMemoryModal` filtered to that group, where memories can be reassigned.

`ConversationSettings.memory_group_override` is `"default"` (follow the global default group) or a
group id. `useSendMessage` resolves the effective group, filters the memories passed to
`sendMessage`, and passes `memoryGroupId` so learned/replaced memories stay in that group. Deleting a
group moves its memories to `"default"` and resets the global default if needed. Selecting a specific
(non-default) group in the per-chat control also switches the per-chat mode from off to recall so
the selection takes effect. Groups live inside `user_settings`, so they are exported/imported with
settings; the conversation override is part of
the conversation settings. Redux persist migration 8 initializes `memory_groups` /
`default_memory_group` and assigns every existing memory to `"default"`; old conversations without
`memory_group_override` follow the global default group. No Dexie version bump is needed (all fields
are unindexed). The Meta chat exposes the grouping through `list_memories` (default group, available
groups, and each memory's group) and `get_user_settings` (group list and default group). Its
`ADD_MEMORY` / `UPDATE_MEMORY` proposals accept an optional `group` name; additions without one use
the Meta conversation's effective group.

### 4.24 Workspaces group sources behind one file-provider contract

The sidebar's Workspace section (`components/Workspace/WorkspaceList.tsx`) sits below the Chats subpanel;
`/workspace/:workspaceId` renders `Pages/WorkspacePage.tsx`. Workspace and Chats are separate

Browsing lives inside that same Sources card, next to the rail
(`components/Workspace/WorkspaceSourceBrowser.tsx`, `data-guide="workspace-source-pane"`): the page

`workspace/addSelectionToWorkspace.ts` is what Add to Workspace runs: a folder from `local`,
`arcana` or `arcana-filesystem` becomes a **mount** at `/<name>` (never a copy, so it stays live;
collisions get " (2)", " (3)", …), a chat **root** calls `attachWorkspaceChat`, which is what writes
the `workspace_chats` link — calling only `ensureChatStorageSource` there would let
`syncChatStorageSources` delete the folder on the next reconcile — and every **file**, plus anything
below a chat's root, is copied into the workspace root with `runTransfer`. Failures are collected per
item and the batch continues. `listRoot("/")` synthesises a `chats` directory even when no chat is
attached, so the root always has `/chats`, and `workspace/chatFolderName.ts#chatFolderLabel` feeds
`displayName` on `WorkspaceRootBrowser`/`WorkspaceRootTree` so `/chats/<id>` rows show the chat title
while navigation keeps using the id. i18n note: `workspace.sources` and
`workspace.source_browser_label` are strings used by the create modal and the DB labels; the panel's
own keys live under `workspace.source_browser.*`.

Attaching a file from a workspace to a chat records a `workspace_file_references` row for the
browser node; deleting a chat removes its reference rows. A workspace root and its browser sources
share one tree per workspace (`workspaceBrowserStorageId` in `workspace/browserStorage.ts`), never
another workspace's, so deleting a workspace removes its own tree (files still referenced by a chat
stay) and leaves other workspaces untouched. Removing a browser source keeps the files because the
workspace root still shows the same tree.

Every source kind is a `FileProvider` (`workspace/providers/`) built from its `WorkspaceSourceRow`:
Every new workspace automatically gets a `browser` source and, unless the Arcanas module is off, an
`arcana-filesystem` source; Dexie v10/v11 backfill them into existing workspaces.

browser = the workspace's own IndexedDB tree in `workspace_nodes` / `workspace_blobs`, local = a
`FileSystemDirectoryHandle` in `workspace_handles`, arcana = one Arcana Tools collection through
`agent/arcanaTools.ts`, arcana-filesystem = every Arcana as a folder with its files, mcp = file tools exposed
by a configured local MCP server (the option only appears when `tools.mcp` is on and a local URL is
configured), agent = a read-only view of a local agent's OpenCode project filesystem. A local agent
attached to a workspace gets one deterministic `agent` source per workspace through
`syncAgentFilesSources()`; the workspace page calls it on show and whenever the agent list or its
links change. It reads the `workspace_agents` links itself, so a live query that still holds its
empty placeholder cannot prune sources, and it deletes the derived source when the agent is detached
or no longer exists (a source for a bridged-only agent is kept). It uses the same `/fs/list` and
`/fs/read` endpoints as the agent file panel. Providers declare `capabilities`, and the UI must offer
only what a provider reports.
`WorkspaceSourceRow.readOnly` wraps the provider in `ReadOnlyProvider` (writes, deletes, mkdir,
move and copy throw `PERMISSION_DENIED`), and `WorkspaceMountRow.readOnly` blocks writes/moves
through that mount while still allowing reads and copies out. A read-only row is also passed to
`LocalProvider`, which then queries and requests only `read` permission, and `AddSourceModal` asks
the picker for `mode: "read"`; otherwise a browser write guard blocks a folder that is never
written to. `AddSourceModal` surfaces the picker's `AbortError` in the dialog instead of treating it
as a silent cancel, because Chrome reports the same error when its file dialog cannot open or
refuses a folder. Since `showDirectoryPicker` only exists in a secure context, the dialog reports a
missing API or an insecure page up front and disables its action, rather than failing after the
click; that is why a LAN IP over plain `http://` cannot add a local folder. The source kind is a
selector, not an action: with only one kind available it is a plain heading. The local folder is
picked by a "Choose folder…" button inside the local section, above the label field, and the dialog
only creates the source from the footer's OK, so the chosen folder is visible before anything is
written; OK stays disabled while no folder is chosen.
The Local tools panel was removed;
GWDG Tools now contains the document-creation and image-analysis toggles, while the tool-call limit
moved to the Workspace popover.
GWDG Tools renders one row per tool in a list (`data-guide="tools-grid"` is the `<ul>`): icon and
label on the left, an on/off `toggle` on the right, warning triangles kept for web search and MCP.
The Browser agent is the default and only workflow, so codemode is
always on. When a chat has a workspace link, `runAgent` uses
`workspace/agentVfs.ts` over that workspace's root and mounts for the file tools.
`agent/workspaceTools.ts` adds the workspace-scoped tools that the plain file tools cannot cover:
`workspace_list` (sources, mounts and attached agents of every workspace linked to the chat),
`workspace_list_agents` (agents attached to a workspace, with session counts, plus the configured
agents that are not attached and therefore inaccessible), and `workspace_files` /
`workspace_read_file` / `workspace_write_file` / `workspace_fetch_file`. Those accept a workspace
id or name plus a `source` id, label or mount path, so they reach sources that are not mounted and
workspaces other than the first `workspace_chats` link, which is the only one `getChatWorkspaceBundle`
puts into the chat VFS. They are registered whenever the chat has a `workspace_chats` link and the
model supports tools, even while no agent is attached.
`agent/prepare.ts` writes attachments and their converted variants under `/artefacts` in the
attached workspace root (or the conversation OPFS when no workspace is linked); the agent VFS keeps
`/uploads` routed to the conversation OPFS for legacy paths. `agent/writtenFiles.ts` turns every
other file the agent writes during a turn into a conversation file and reports it as a
`{ type: "file", fileId }` content item of the assistant message, so a "create a png and show me"
turn renders a clickable attachment. Image blocks in tool results (pi's `read`, MCP tools) are
attached the same way, which is why the tool call shows only its text and no `[image]` placeholder;
an image whose path is already attached, or that is an upload below `/artefacts`, is skipped.
`/artefacts` writes are the user's inputs and never attached back; a path written twice keeps one
attachment.

**A chat's files always live in its own OPFS tree at `chats/<conversation id>**
(`workspace/chatStorage.ts`). Attaching a chat to a workspace never copies or moves them: the
workspace gets one derived `chat` source plus a mount at `/chats/<conversation id>`
(`workspaceDb.ts#ensureChatStorageSource`), so the folder appears in the workspace browser and in
the agent VFS at that path. `attachWorkspaceChat` creates the link, `detachWorkspaceChat` removes
only the source and mount (the files stay with the chat), and `WorkspacePage` reconciles it through
`syncChatStorageSources`. The source is driven by the chat link, so the UI shows no per-row rename,
unmount or read-only switch for it, and `listCloneTargets` excludes it. The folder under `chats/` is
named by its conversation id, not the title, so a rename never changes the path; the derived
source's own label keeps the title for the storage list. The tree
used to be `conversations/<id>`; `chatStorageDir` copies an old tree over on first access and
removes it, so there is no startup migration.
A chat without file access (no workspace/mount and `tools.browser_storage` off, or a model without
tool support) gets no file tools, so `agent/attachmentContext.ts` inlines the text of text-like
attachments and of documents with a converted `.md`/`.txt` variant into the user message; images,
audio and unconvertible files stay path-only. Without that, a perfectly readable `.md` attachment
would be unusable in a default chat.

Every workspace also has an implicit browser-backed root: files and directories created there are
stored in `workspace_nodes` / `workspace_blobs` under the synthetic source id
`workspace-root:<workspaceId>`. The root browser lists those local entries and overlays mounted
source folders, so normalized local directories/files and mounts coexist. The workspace page's left
column is three independent cards: **Storage** (a collapsible "Available storage" source list, whose add
button sits in that subheader, plus a flat top-level listing of the workspace root), **Attached
Chats**, and **Attached Agents**. The left root list never
expands; clicking a folder opens it in the centre browser, whose breadcrumbs show the hierarchy.

`workspace_mounts` maps a folder inside a source (`sourcePath`) to a workspace path (`path`), so
several sources can appear side by side in one workspace; the workspace browser starts at that
mount list. `AddMountModal` (the Storage panel's "Add folder") has no path inputs at all: both paths
are chosen in two always-expanded `FolderPickerPanel` lists, one per section, with no browse button
and no confirm step. A panel lists only directories of its `path`, follows provider pagination, and
clicking a folder selects it and descends into it; the up button selects the parent. The source
panel lists directories of the selected source through `createProvider(source)` (connect, paged
list, `close?.()`); the workspace panel lists the workspace root plus the virtual mount folders. The
workspace panel chooses the *parent*, and the mount path is `<parent>/<leaf>` where the leaf is the
source folder's name (or the source label when the source root is picked), previewed as
"Mounts at …" under that list. The dialog opens on the workspace's own `browser` source rather than
`sources[0]`, whose order is not stable; an Arcana source can be unreachable. A destination is
refused with a message (and a disabled Add button) when its path already holds an entry, sits inside
a mounted folder, or would contain one: `mountTarget.ts#inspectMountTarget` asks the workspace root
provider (`stat`, then the first page of `list`) and the root listing shows a local entry before a
mount at the same path, so the mount would be shadowed and silently invisible. A mounted folder is
therefore not offered as the parent either. Switching the source resets the source folder to `/`
because a path only exists inside its own source; the chosen parent is kept. A source that cannot be
listed shows the reason under its panel, and `arcanaTools.ts` reduces an upstream
`{"detail": "Not Found"}` error body to its message instead of printing the JSON. `workspace_chats` is the
many-to-many chat link: a chat can be attached to any number of workspaces, shown under the
workspace in the sidebar and in the workspace's Chats panel, and toggled from the `Workspace` icon
left of the Local tools icon in the prompt box. The `+` on a workspace row in the sidebar and the
`+` in the workspace page's Chats panel both start a new chat that is linked right away; an
existing chat is linked with the link control in the workspace page's Chats panel, not from the
sidebar row. `workspace_agents` is the matching many-to-many link
between workspaces and localStorage-backed agent entries; the workspace page's Agents panel attaches
or detaches them, and links whose agent no longer exists are removed when that page loads.
Files still come in through one paperclip: when the chat has at least one workspace it opens a small
menu with **From device** and **From workspace** (`conversation.prompt.attach_device` /
`attach_workspace`), and the workspace tree is a second view of that same panel; with no workspace
the paperclip goes straight to the file picker. The separate workspace-attach icon is gone.
`workspace_agent_sessions` (Dexie v13) is the session-level link: it stores
`{workspaceId, agentId, sessionId}`, so a workspace shows only the sessions attached to it instead
of every session of an agent. The workspace page's Agents panel, the sidebar's Workspace section
(each attached agent has its own expand/collapse toggle for the sessions of that workspace, kept per
workspace and agent) and the chat sidebar list those
sessions; the sidebar agent list groups an agent's sessions by workspace and keeps sessions that
belong to no workspace under "Not in a workspace". Creating a session from a workspace attaches it
there, opening one from an attached workspace attaches it, and `AppDB` version 13 adds the table.
`workspace_agents.sessionsSeeded` records that the agent's active session was copied into the
workspace once (`seedWorkspaceAgentSessions`), so existing data upgrades without duplicating
sessions and a detached session is not re-added. Detaching an agent, deleting a workspace, removing
an agent, and closing a session all delete the matching session links. Every source in Storage's
"Available storage" list is shown, including the agent-files source of an attached agent, so its
filesystem is browsable like any other source. The row actions come from
`workspace/sources.ts#sourceRowActions`. The `browser` row offers no add-folder, no delete and — unless
an older build already set it — no read-only toggle: its tree *is* the workspace root, so the row
cannot be recreated (`ensureBrowserSource` runs only at creation), its folders are already at the
root and a mount of one is refused, and its `readOnly` never reaches `createWorkspaceRootProvider`,
where it would only pretend to protect files the root still writes. The derived `chat` and `agent`
rows offer no delete or read-only toggle either; only `agent` keeps add-folder.

Transfers are orchestrated in the browser: `workspace/transferPlanner.ts` always moves on drag and
drop, regardless of source; an explicit "copy" intent is the only copy path. It blocks read-only
targets, folder-into-descendant moves and over-quota transfers. The workspace root
browser uses the same drag-and-drop flow as source folders, but mounted folder rows are not
draggable (the workspace root provider is resolved by `providerFor` for both drag source and drop
target). `workspace/transfer.ts` streams the copy, verifies SHA-256, then deletes the source for a
move, and journals progress in `workspace_transfers`. Arcana quota is read through the
`/arcana-tools/arcanas/:name/quota` proxy; local and MCP quota is shown as `—` because browsers cannot
read disk free space.

The file browser's Upload file action writes files from the computer into the folder currently
shown (workspace root or the selected source) through `workspace/upload.ts`; it is disabled for
read-only sources and mounts. Entries can be downloaded, renamed through the shared create-entry
modal, and deleted recursively after confirmation; sources with the matching capabilities also
offer new file/folder creation. A download reads the complete content before the browser saves it:
`workspace/download.ts#downloadProviderEntry` connects the provider, drains its stream, and hands a
`Blob` to `utils/download.js#downloadBlob`, which refuses anything that is not a blob. The same
holds for chat attachments: they open in the docked preview (`context/FilePreviewContext.jsx`)
rather than a modal, and the panel loads the file by id instead of using `useFile`'s `data`, which
is written to state separately from the metadata and produced an empty download when the button was
clicked before the bytes arrived. `ChatPage` and `MetaChatPage` render the panel beside their
content column and hide their own side panel while it is open.
Clicking the same attachment again closes it: `Attachment` calls `toggleFilePreview`.

All three previews — workspace browser, agent file list/panel and chat attachments — render the same
`components/DocumentPanel/FilePreviewPanel.jsx`, whose body is
`DocumentPanel/FilePreviewContent.jsx`. Callers pass `{ entry: { name, mime, size }, url?, text?,
data?, loading?, error?, onOpenPath? }`; `hooks/useConversationFilePreview.js` builds that shape for a
stored conversation file (media from `useFileBase64`, text from `useFileContent`). A new file type
belongs in `FilePreviewContent`, not in one of the call sites: otherwise the same file would look
different in a workspace and in a chat. A `.md` file is rendered with `MarkdownRenderer`
(`isLoading={false}`), the same component as a chat message, so headings, tables, KaTeX and the
fence renderers (mermaid, typst, latex, highlighted code) look identical; empty text keeps the
`<pre>` fallback. Because it reads Redux and uses `useNavigate` for internal links, tests that
preview markdown need a `react-redux` mock and a router (`MemoryRouter`).

Switching to another file must not reuse the previous one's bytes: `FilePreviewPanel` keys the
content by the preview's own key (`fileId` for chat), media is only rendered once `url` belongs to
the current file, and `useFileMeta` / `useFile` / `useFileBase64` / `useFileContent` reset their
state when the id changes — otherwise the old data URL is rendered inside an `<img>` and shows
"Failed to load image".
A tree folder that contains a
`.git` directory gets a Git button; the workspace preview parses `.git/logs/HEAD` (falling back to
the branch reflog) without a shell,
while the agent file panel runs `git log --stat` through the OpenCode shell and falls back to the
same reflog parsing. That internal command is tagged `CHATAI_GIT_LOG`, and agent chat/state filters
it out so the log appears only in the preview panel. HTML previews render in `SandboxedHtmlPreview`: an
iframe with an opaque origin and a Strict/Relaxed switch at the top. Strict (the start mode unless
`user_settings.html_sanitization` is `"relaxed"`) removes scripts, forms and frames but keeps the
document's own CSS; relaxed adds `allow-scripts` so an interactive file behaves like an interactive
HTML block. Both modes take the CSP from `utils/htmlPreview.js#buildHtmlCsp` — the same policy the
fenced HTML block uses — and drop external references according to `html_load_external`.

The browser supports multi-select: `WorkspacePage` owns `selectedPaths` and clears it when the
source or folder changes, while `WorkspaceRootBrowser` only renders the per-row checkboxes, the
toolbar select-all and the selection bar from props. An entry is selectable when it can also be
deleted — local entries in the root view (`entry.local && !entry.mount`, so mounts are never
selectable) and `canDeleteSourceEntry` entries in a source view — and select-all only covers those.
Bulk delete confirms once and removes each entry with `provider.remove`, reporting per-entry
failures. Bulk move opens `MoveToModal` with the entries and then the transfer confirmation with an
aggregated `planTransfer`; it always uses the move strategy and reuses `runTransfer` per entry.
A drag or the row-level "Move to…" action that starts on an entry of the current selection carries
the whole selection (`workspace/selection.ts#entriesForAction`); an entry outside the selection acts
on itself. `requestTransfer` therefore takes `entries[]` and checks every entry before confirming.
`MoveToModal` must call `onClose` before `onSelect`, because `onSelect` opens that confirmation
modal and closing afterwards dismissed it again.

The prompt box's Workspace popover (`WorkspaceAttachButton`) is ordered storage → attachment →
settings: the "Access storage" master switch, the "Manage data" row directly under it, the
attachment hint with the workspace list, then the tool-call limit under "Local agent". A chat with
at least one attached workspace shows an `Allow write` switch (`tools.workspace_write_access`,
default on) directly under "Access storage". A chat without a workspace has no write switch:
writing in its own storage is always allowed. The switch is disabled while "Access storage" is off,
because then no file tool is offered at all.
The attachment hint is dynamic: unattached it invites attaching, attached it names the workspaces and
says the chat can use all files there. GWDG Tools no longer renders the call limit.

The Browser agent is the default workflow (`utils/sendMessage.jsx#shouldUseBrowserAgent`). A model
without tool support (`apis/agentEndpoints.ts#modelSupportsTools`) falls back to the plain chat path
with no tools, and the prompt shows a warning above the input. `runAgent` also refuses to attach any
tool to such a model, including workspace and connected-agent tools.

"Manage data" is the per-chat view of the same files. With exactly one attached workspace it opens
that workspace page directly (the workspace owns the file system, so the popover does not repeat
it in a second view); with several it opens `modals/Chat/ManageDataModal.jsx`, which asks which
one; with none it browses the chat's own OPFS tree
(`chats/<conversationId>`) through `ConversationStorageProvider`
(`workspace/providers/conversation.ts`), rendered with the shared `WorkspaceRootBrowser`. The
"Access storage" switch is the first row of that popover, not of the modal: it writes
`tools.browser_storage` through the live `Prompt` state, and the modal only reports its result
(with a warning when it is off), because the modal gets a snapshot of `localState` when it opens.
Both paths are independent of `VITE_MODULE_AGENT`.

The `workspace_overview` feature guide targets `[data-guide="workspace-add-source"]`,
`workspace-sources` and `workspace-files`.

A public HTTPS Git repository is cloned with a selected local OpenCode agent in two places, both
through `workspace/cloneIntoWorkspace.ts`: the Storage card's `+` on the workspace page opens
`modals/Workspace/AddSourceModal.tsx`, whose source-type select offers Local folder, Git repository
and MCP server; Create Workspace is a two-column dialog (source actions on the left, the resulting
workspace tree on the right) where a Git row is cloned at Create time. `workspace/importProject.js`
runs `git clone` through the agent's shell into `.chat-ai-clones/<id>/repo`, and the complete
repository tree (including `.git`) is copied into the workspace's browser storage at a folder named
after the repository. Flat Arcana sources are excluded because they cannot represent a directory
tree. `chat-ai-manifest.json` is validated by `utils/workspaceManifest.js` and never provides
commands, scripts, credentials, or server URLs. Only the Create dialog applies a manifest
(`workspace/applyWorkspaceManifest.ts`), which can create an agent using the clone connection and
import full chats attached to the new workspace; cloning from an existing workspace copies files
only. An agent's optional
`initialMessage` is stored on the local agent entry and displayed above the session; it is also
written to the session's OpenCode instruction entries so the agent sees it without executing a
prompt. The local example repository is
`remote-example/` (ignored by the main repo); a public reference example, including a working
`chat-ai-manifest.json`, is
[`hpc-team-public/gaia-teaching-example`](https://gitlab-ce.gwdg.de/hpc-team-public/gaia-teaching-example.git).
The schema is documented in `docs/workspace-manifests.md`.


### 4.25 MCP servers are configured globally and selected per chat

`user_settings.mcp_servers` holds the global definitions (`{id, name, kind: "local" | "remote",
url?, serverId?, headers?}`), managed by the sidebar's `McpServerList` and `McpServerModal`
(including the connection test). Local servers show a status light: amber until tested, red on a
failed test, green when reachable; clicking the light runs `testMcpServer`. Per-chat settings store only the selected ids in
`mcp_local_server_ids` / `mcp_remote_server_ids`; `agent/mcp.ts#resolveMcpServers` expands them for
the agent, gateway request and prefetch, and still merges legacy full entries from
`settings.mcp_servers`. GWDG Tools has one MCP Servers tool that switches every configured
server on or off; enabling it reveals the selector, which lists every configured server and
badges it local or GWDG and never shows URL/id/auth fields. `remoteMcpEnabled` also treats selected
remote ids as a value.


### 4.26 Sidebar agents connect to a local opencode server

`Sidebar/AgentList.tsx` lists remote agents like conversation rows and polls
`GET /api/session/status` every 5 s for the status dot (green idle, yellow working, red connection
error). Each agent row expands into its OpenCode sessions grouped by the workspaces the agent is
attached to, with the sessions attached to each workspace and a final "Not in a workspace" group for
the rest; the active `sessionId` is stored on the
local agent entry, while the session list is read from `GET /api/session` by
`agents/agentSessions.js`. Children are fetched with
`GET /api/session?parentID=<id>&limit=200`; current OpenCode (2.3) no longer serves
`/api/session/:id/children` and answers it with 404, so that endpoint is only the fallback for
older servers. Child sessions are the subagent
sessions OpenCode creates; they are shown nested in the same list and can be opened like a
top-level session. The + action creates a new session and makes it active. `AgentList` and the
workspace Agents panel refetch every 10s (or immediately on the
`chatai:agent-sessions-changed` / `chatai:agent-session-changed` events) so a subagent spawned by
OpenCode appears without a reload. Leaving an agent session summarizes its messages with
`generateConversationSummary`, stores the summary under that session in the agent entry's
`sessionSummaries`, and shows it in the session row tooltip. Clicking one navigates to
`Pages/AgentPage.tsx` (`/agent/:agentId`), whose `components/Agent/AgentConversation.jsx` is the
chat pane; assistant text renders through `SafeMarkdown` with `rendererComponents`, and tool or
reasoning parts render as inline expandable cards (`AgentAssistantParts`).

Session history is cached in IndexedDB by `db/agentSessionCache.ts` (Dexie v14 `agent_sessions` for
metadata, `agent_session_messages` for one row per message). Re-opening a session does not download
it again: `AgentConversation` renders the cache first and then calls `syncSessionHistory()` in
`agents/agentSessions.js`, which pages newest-first with
`listOpencodeMessagesPage(agent, sessionId, { newestId })` and stops at the cached tail. Only the
changed rows are written back; `listOpencodeMessages` remains the full-history call.

The server is authoritative once it answers, and the cache follows it:

- The cached anchor is still on the server: `mergeMessageHistory()` keeps the cached prefix,
  replaces the anchor message (it can still be streaming) and appends the new tail.
- The anchor is gone: the history was cleared, reverted or compacted. The download **replaces** the
  cached history instead of being stitched onto it, so reverted or cleared messages do not survive.
- The page window ends before the anchor (more messages than the 20×200 page cap): the cache is left
  alone and the full history is re-read, rather than appending across the gap.
- The page came back empty: a full read confirms the empty session before the cache is dropped, so a
  single flaky empty page cannot wipe the history.
- An unreachable server never touches the cache; `AgentConversation` keeps the cached timeline and
  shows a warning banner with the cache time and a Refresh button instead of a bare error.

A reachable server that lost its sessions is handled separately from an unreachable one.
`agents/agentRecovery.js#inspectAgentRecovery` compares the server's session list with every cached
session id (metadata or messages), and `AgentConversation` shows a restore banner when cached
histories are missing. `restoreCachedSessions` creates one new session per cached history, writes the
size-capped transcript into `chat-ai-restored-history`, copies the cache under the new id with
`restoredFrom`, moves workspace session links and session summaries, and drops the old cache entry so
the same session is not offered twice. Restored caches are shown even though the server timeline is
empty: `syncSessionHistory` is called with `keepWhenEmpty` while `restoredFrom` is set, and an empty
full read is never allowed to wipe a cached history when the session itself is missing. An empty
session listing no longer prunes the cache, because that cache is the only copy left.

A cache older than `CACHE_REVALIDATE_MS` (24 h) is re-read in full once on entry and reconciled by
id, which also drops messages removed by another client (TUI, compaction elsewhere). Running
`compact` from the app forces that same full sync because compaction rewrites the timeline in place.
Reverting a message or clearing a revert in the tools modal dispatches `chatai:agent-history-changed`
(`notifyAgentHistoryChanged`), which makes the open conversation re-read the whole history and
rewrite the cache, because those actions rewrite the timeline rather than append to it. Full reads
reconcile from an empty cache on purpose: a prefix merge would keep messages the server no longer
has. `fetchAgentSessions` caches session metadata, prunes sessions a complete listing no longer
reports (together with their messages), and falls back to the cache when the listing fails, so the
sidebar and the agent page still list sessions while the server is down.

The offline state is shown, not hidden: the conversation keeps the cached timeline under a warning
banner with the cache time and a Refresh button (`agents.offline_cached`), or says that nothing has
been cached yet (`agents.offline_no_cache`); both are driven by `reportSyncFailure`, which never
writes to the cache. A session list that came from the cache carries `offline: true` through
`fetchAgentSessions` and `filterSessionTree`, and `AgentSessionList` plus
`AttachAgentSessionModal` mark it with a "cached" warning. Shell output stays in its localStorage
history and is merged in for display only. Closing a session, clearing the history and removing an
agent delete the matching cache rows. The left
`AgentFilesPanel` reuses the central `WorkspaceRootBrowser` (the same component used for the
workspace root file browser) and reads/writes the OpenCode project filesystem through
`GET /api/fs/list`, `GET /api/fs/read/<path>`, `POST /api/experimental/fs/write` and

searches through `/api/fs/find`, and refreshes on navigation, upload, new file, or an explicit

(also with status 200), 502/503/504 or a network failure — `rawRequest` reports
`AGENT_SERVER_UNAVAILABLE` and the panel renders nothing instead of printing a JSON parse error;
the 5 s poll brings it back once the server answers again. The

other tools get no card. The sidebar's `+` opens
`modals/Agent/AddAgentModal`, which offers a name and one connection choice: the GWDG HPC agentic

to the selected mode. An agent created either way stores `local: true` (a service agent keeps the
flag it already had), because `CreateWorkspaceModal` and `db/workspaceDb.ts` gate the agent-files
source on `local !== false`. The row's
vertical menu edits (`agentEdit`, all creation fields; changing the server or password opens a new
session) or removes the agent. Adding an agent calls the local `opencode serve` HTTP API through
`apis/opencodeAgents.js`: `GET /api/info` verifies the server, `POST /api/session` creates the chat
session, and `AgentConversation` sends `POST /api/session/:id/prompt` and polls
`GET /api/session/:id/message?order=asc` until an `idle` message appears. It also exposes the
control API: interrupt (`/interrupt`), slash commands (`/command`), `!` shell input (`/shell`), and
permission replies (`/permission/{requestID}/reply`). The composer's command dropdown is populated
from `GET /api/command` (plus the built-in `compact`). The composer has a yellow Shell toggle that sends the input directly to
`/api/session/:id/shell`; shell output is rendered inline in the conversation, and the Tools modal
no longer has a terminal tab. Shell messages are persisted per agent/session in localStorage
(`agents/agentShellHistory.js`) and merged with the server timeline by creation time. The header X
confirms, interrupts and deletes the OpenCode session, creates a replacement session, updates the

accepts file attachments and sends them inline to the prompt API. The

renders the field/option descriptions, and offers the custom answer; it must not key that
behaviour on `type === "select"`, or question forms collapse to a bare text input.
`AgentToolsModal` exposes a live step/todo timeline, session
diff/revert with VCS and tracked-file status, saved permissions, local permission policies
(`agents/agentPermissionPolicies.js`, auto-answered by `AgentConversation`), usage stats, MCP

(`buildAgentHistoryRestoreText`, 100k characters, newest messages kept) into the instructions of a
new session under the key `chat-ai-restored-history`; messages are never replayed as chat turns.

refreshes messages and permissions from the `/api/event` stream. The composer reuses `SendButton` and

(non-hidden primary agents) and switches with `POST /api/session/:id/agent`. The server URL and
HTTP-basic credentials default from `opencodeServerUrl` / `opencodeServerUsername` /
`opencodeServerPassword` in `front.json` (mapped to `VITE_OPENCODE_SERVER_*`) and stay editable per
agent. The browser talks to the server directly (opencode allows the app origin via CORS), so the
back service is not involved.

**A direct OpenCode server is a local-only affordance.** Everything else must go through the agent
service, which in a deployment sits behind SAIA. `apis/agentAccess.js` is the policy:
`directAgentAccessAllowed()` is true only for a loopback hostname (`localhost`, `127.0.0.1`, `::1`,
bracketed or not), and `isServiceManagedAgent()` is "the agent carries a `serviceAgentId`".
`apis/opencodeAgents.js#rawRequest` enforces it for every request, so a direct agent outside local
access throws `DIRECT_AGENT_BLOCKED` without touching the network. `AddAgentModal` mirrors the policy
outside local access: it replaces the connection choice with `agents.service_forced_hint`, forces the
service mode and hides the server URL/password fields, so an existing direct agent is migrated when
it is saved (creates the service agent, stores its proxy prefix, drops the basic-auth password).
There is no config flag that bypasses this; a LAN/IP deployment counts as
deployment.

The SAIA agent service, which lives in its own repository, has **no config key**: the browser always calls it
at `/agents` on the app's own origin, which the SAIA gateway routes to the service. `AddAgentModal`
defaults to a service-managed agent: it `POST`s `/agents`, stores the returned id as
`serviceAgentId` and `/agents/<id>/opencode` as `serverUrl`, and stores no basic-auth password (the
proxy adds the backend credentials). A service-managed agent is not pinned to the `serverUrl` stored
when it was created: `opencodeAgents.js#baseUrl()` derives it from `serviceAgentId` via
`agentService.js#serviceOpencodeUrl()` (fixed `AGENT_SERVICE_PATH` `/agents`), so an existing agent
follows the current deployment. Because no gateway runs locally, `vite.config.js` proxies `/agents`
to `AGENT_SERVICE_DEV_PROXY` in `development` mode, and only when that variable is set: there is no
default port, so the app never assumes a local service. A production build and a gateway-fronted
preview never contain the proxy. The
connection choice in the add-agent window only appears with local access, where its external-server
mode is the way back to a direct server.

The service is also registered in the engine as the model `saia-agent`, inside an access group, so
`/models` lists it only for users that were granted the service. That list is the entitlement check
in the add-agent dialog: `hooks/useAgentServiceAccess.js` fetches it when the dialog opens and
answers `checking`, `granted`, `denied` or `unknown`. `denied` (a readable list without the model)
disables the name, the HPC project and the submit button and shows that eligible HPC users can
request access at support@gwdg.de; `unknown` (an empty list or a refused `/models`) fails open,
because a broken model fetch says nothing about the user's grants. The external tab is never gated
by it, since a direct server needs no entitlement.
`AgentList`'s remove action also calls `DELETE /agents/<id>` when `serviceAgentId` is set, so
removing the row frees the container/process; a `404` counts as already removed. The rest of the
OpenCode client (`apis/opencodeAgents.js`) is unchanged because the proxy forwards `/api/*`
verbatim, which is why `serviceOpencodeUrl()` is the whole integration. The browser sends no
identity header (`apis/agentService.js`), so the service resolves every call to its configured
`DEFAULT_USER_ID`: that is the single-user local setup, not per-user isolation. A deployment needs a
gateway in front of `/agents/*` that authenticates and forwards `inference-id` (or another trusted
header) before one user's agent can be separated from another's. The service keeps its rows
across restarts, so an agent id survives one; if its database is reset or the row is deleted, the
saved `serverUrl` points at a missing id and the agent must be recreated (the edit window does that).
`agents/agentStore.js` persists the agent metadata in localStorage.
Every agent carries `createdAt`, `updatedAt` and an optional `pinned` flag. `load()` backfills the
timestamps of agents created before they existed and persists them once. `updateAgent` bumps
`updatedAt` for metadata changes but not for session tracking (`sessionId`, `sessionSummaries`);
`setAgentPinned` adds the agent to the top-level pinned section; `AgentList` still lists it. The agent
conversation header shows both timestamps. A custom per-agent
password is persisted with it; agents left on the configured default re-read that
password from `front.json` on load. `modules.agents: false` in
`front.json` sets `VITE_MODULE_AGENTS=false`, hiding the sidebar section and its route. Removing an
agent interrupts its running session first, then deletes the OpenCode session; the local agent is
dropped only after that succeeds; if the server is unreachable or rejects authentication, the local
agent entry can still be removed.

A service-managed agent is removed when the service answers `409` with `code: "conflict"`: that row
cannot be served, and no retry repairs it. `apis/opencodeAgents.js` reports it through
`chatai:agent-service-conflict` (service-managed agents only), and
`components/Others/AgentConflictWatcher.jsx` deletes the service agent, removes the local entry,
leaves `/agent/<id>` for `/chat` and shows a longer-lived toast. Direct agents (no `serviceAgentId`)
and proxied OpenCode 409s without the service's `code`/`agent_id` are ignored, as is a
`starting`/`stopping` status: the service revives a `failed` row on the next request, and deleting a
healthy agent during a transition would be worse. `DELETE /agents/<id>` keeps the agent's workdir;
only the row and its conversation→session mappings go away.


### 4.27 The browser-to-OpenCode bridge keeps workspace data in the browser

The agent workspace bridge lets OpenCode read the user's selected workspace and bridged local MCP
servers without uploading files. The browser is the data plane: `hooks/useAgentBridge.ts` opens an
outbound WebSocket to the bridge host. The agent side is a local stdio MCP sidecar
(`back/bridge-sidecar.mjs`) started by OpenCode from `opencodeBridgeSidecarCommand`; it opens its own
outbound WebSocket to the bridge host. The host pairs browser and sidecar by run id, so OpenCode
never needs an inbound endpoint. If no sidecar command is configured, the hook falls back to the
remote-MCP endpoint (`mcpUrl`).

The sidecar is a **direct-agent** transport only (`wantsSidecar()`): its command is a path next to
the browser's own OpenCode, and a service-managed agent runs OpenCode in the agent service, where
that path does not exist. Service agents therefore always use `mcpUrl` over HTTP, so one
`opencodeBridgeSidecarCommand` in `front.json` cannot break a SAIA deployment. `mcpUrl` and
`agentWsUrl` are absolute and built from the request base URL, so the address the agent process must
reach is `AGENT_SERVICE_BRIDGE_AGENT_URL` when the gateway's public URL is not reachable from inside
the agent service.

Two hosts speak the same protocol. `back` serves it at `/bridge/*`. A service-managed agent
(`serviceAgentId`, §4.26) uses the SAIA agent service instead, at `/agents/<id>/bridge/*` on the app
origin, because a SAIA deployment has no `back`. The agent service is a single process that already
owns the user's OpenCode, which is what the pairing needs: **`saia-engine` cannot host it** — its
uvicorn runs `cpu_count() + 1` workers, so the browser and agent sockets land in different processes
and every call times out. Do not move the registry there without shared state.

Routes (both hosts): `POST .../bridge/sessions` creates a session and returns browser/agent tokens
and URLs, `WS .../bridge/ws` attaches the browser, `WS .../bridge/agent` attaches the sidecar,
`POST .../bridge/mcp/:id` is the fallback MCP endpoint, and `DELETE .../bridge/sessions/:id` tears it
down. Tool calls are relayed to the browser and answered over the browser WebSocket. If the browser
is disconnected, the sidecar still lists tools but calls return an `isError` content result with
`BRIDGE_OFFLINE` so the agent can continue with OpenCode's own tools. The agent service returns the
browser leg as a path (the page origin completes it) and the agent leg plus `mcpUrl` as absolute
URLs, since the agent process must reach them; they default to the request base URL and
`AGENT_SERVICE_BRIDGE_AGENT_URL` overrides them.

The bridge exposes `workspace_list`, `workspace_stat`, `workspace_read`, and, only when the agent's
write toggle is on, `workspace_write`, `workspace_mkdir`, `workspace_remove`. Local MCP tools are
exposed as `mcp_list_servers`, `mcp_list_tools`, and `mcp_call` only when its toggle is on; headers
and tokens stay in the browser. Workspace operations go through `WorkspaceAgentVfs`, so provider
capabilities, source/mount read-only flags, and IndexedDB/local/Arcana behavior stay authoritative.
The agent page's workspace access is an explicit switch (`bridgeEnabled`) in the composer's
workspace popover (`components/Agent/AgentWorkspaceButton.jsx`, through
`agents/agentBridgeAccess.js`); the left file panel is only the file browser and shows no bridge
section. The popover starts with a live status row: green "Agent bridge working" while the socket is
online, red while it is offline or failed, and a muted "off" while access is switched off. The bridge
settings stay together under it — hint, write and MCP toggles, keep-open warning — and the attached
workspaces with the "Use for the bridge" choice are the last section, because they are what the
options apply to. Without the switch no bridge starts and the agent gets no tool, and the bridge only
ever exposes an **attached** workspace: with none attached the switch and the write/MCP options are
disabled, a remembered `bridgeWorkspaceId` does not count on its own, and detaching the last
workspace switches access off. Turning it on exposes `bridgeWorkspaceId` while that workspace is
still attached, otherwise the first attached one. A bridge start failure is reported as a toast
because no panel prints it any more, and `AgentPage` then switches access off
(`disableAgentBridgeAfterFailure`) so an enabled switch never sits in front of a dead bridge; a
dropped socket does not do that, because `useAgentBridge` retries it after 3 s. Existing agents keep
access on only because the reader falls back to `!!bridgeWorkspaceId`. The same entry stores
`bridgeWorkspaceId`, `bridgeWritable`, and `bridgeMcp` in localStorage; `bridgeWorkspaceId` is per
agent, not per session. While a
bridge is active the page warns that the tab must stay open, sets a warning title when hidden,
shows a toast on return, and registers `beforeunload`. In production, the initial invocation must be
able to spawn the sidecar and open the outbound WebSocket; the bridge host must be reachable from the
agent host (through `AGENT_SERVICE_BRIDGE_AGENT_URL` for the agent service, `bridgePublicUrl` in
`back.json` for `back`).

`back`'s own bridge is authenticated and bounded. `POST /bridge/sessions` requires the `x-bridge-key`
header to equal `BRIDGE_SHARED_SECRET`, and the route answers 503 when that variable is unset rather
than minting tokens for whoever can reach the port; `BRIDGE_ALLOW_ANON=1` restores the old anonymous
behaviour and exists for local testing only. The browser's key comes from `VITE_BRIDGE_KEY` at build
time, so it ships in the bundle: it keeps a client that reaches the backend directly from opening a
session, and the OIDC gateway remains the real boundary. A session expires after
`BRIDGE_SESSION_TTL_MS` (default 15 minutes) and is refreshed by tool calls and socket traffic, at
most `BRIDGE_MAX_SESSIONS` (32) exist at once, and one client IP may create ten per minute. Neither
WebSocket carries its token in the URL any more — the browser sends it as the `bridge-token.<token>`
subprotocol, the sidecar as an `Authorization: Bearer` header — so proxy and access logs no longer
record credentials. `cors()` answers only the origins in `CORS_ORIGINS` (comma-separated) or the
request's own host, and still allows requests without an `Origin` header so server-to-server calls
work.

The first call is `POST <bridge base>/bridge/sessions`, where the base is `/agents/<serviceAgentId>`
for a service-managed agent and `VITE_BACKEND_ENDPOINT` for a direct one. A 404 or 405 means that
base has no bridge route (a direct engine such as the `saia/saia-engine/local-testing` stack answers
404, and so does an agent service older than the bridge), so the hook sets `unavailable` with the URL
and status instead of retrying: the popover shows "Agent bridge not available", the endpoint, and
disables the switch. Any other non-OK status stays a normal failure. Direct mode therefore cannot
use the bridge, and the UI says so rather than reporting a broken bridge. The gateway must forward
the `Upgrade` header on `/agents/*`; this is the only WebSocket the UI opens.

### 4.28 The local-files skill is documentation, not installation

`.opencode/skills/local-files/SKILL.md` describes the read-only
`local-folder-mcp` server in `chat-ai-tools/tools/local-folder-mcp/`. The skill is bundled through

### 4.29 Keyed models are sealed in the browser, as a transport wrapper

End-to-end encryption is a **fetch wrapper**, not a second chat implementation. A model is "keyed"
when `user_settings.e2ee_models[modelId]` names an entry in `user_settings.e2ee_keys`; the key entry
holds only the node's published **X25519 public key** (plus a name/id/fingerprint/import source).
`src/e2ee/registry.js` resolves that binding and `src/e2ee/fetch.js` (`createE2eeFetch`, shared as
`e2eeFetch`) rewrites a keyed `/chat/completions` request into the sealed envelope and decrypts the
answer. Because it sits at the transport layer, every caller is covered without changing its
request code: `apis/fetchClient.js` (via `fetchImpl`), the opt-in OpenAI SDK (`fetch` option),
`agent/gateway.ts#gatewayFetch` (the E2EE wrapper is its `baseFetch`, so the gateway only sees the
decrypted stream), `agent/runAgent.ts`, and `apis/agentEndpoints.ts#post` (which covers
`explainImage`). The wrapper is a no-op for every other path; only `/chat/completions` (and
`/completions`) is in the protocol, so `/documents/convert/file`, `/audio/*`, `/images/*` and
`/websearch` stay cleartext.

**Fail closed.** A keyed model whose key is missing or does not parse as a 32-byte X25519 key throws
before any network call. `openRequest` stays strict like the Python reference: after the node strips
the cleartext `stream`/`stream_options` routing hints, the only allowed top-level fields are `model`
and `e2ee`. On the response side a keyed request accepts a sealed JSON body or a sealed SSE stream;
a 2xx JSON body without `e2ee` is refused unless it is an error object, non-2xx statuses pass
through, SSE may carry cleartext `usage`/`error` chunks but never cleartext `choices`, and the
stream must end with the authenticated final marker. Retries are safe because the caller keeps the
cleartext body and the wrapper re-seals (fresh ephemeral key and random password) on every attempt.

`src/e2ee/protocol.js` is a direct port of `saia/saia-e2ee/e2ee_connector/saia_e2ee/protocol.py`
(protocol v3). `canonicalPath()` maps every `*/chat/completions` to `/v1/chat/completions`, so the
backend path, an engine `/public/v1/...` and a proxy share one AAD. `back/service.mjs` detects an
`e2ee` envelope at `/chat/completions` and forwards the raw `{model,e2ee,stream}` body upstream — it
skips `messages` validation, testMode and the tool gateway, because the payload is ciphertext.

**Green lock.** `components/Others/E2eeLock.jsx` reads the same registry and renders a green
(`text-success`) lock only while the binding resolves to a usable key, so the badge and the actual
sealing cannot disagree. It is rendered everywhere a model is listed: both model selectors
(list/extended/grid/trigger), the prompt-box `ModelButton`, the default-model row, and the
Encryption settings model rows. It renders nothing for an unkeyed model. Any new model list must
include it.

**Blue safety lock.** `components/Header/WarningExternalModel.tsx` is the data-safety indicator in
the header and the prompt box, not a model badge. For safe settings on a keyed model it keeps the
lock but paints it blue (`text-info`) and overlays a small Carbon `Link` icon at the lower right;
the notice then uses `alert.data_security_notice_e2ee`, which adds that the model is additionally
end-to-end encrypted, instead of `alert.data_security_notice`. The blue state requires
`isSafeSettings()` first, so a warning (external model, web search, MCP) still wins and stays
yellow. Both states read the registry through `isModelKeyed` in the same way as `E2eeLock`
(§4.29).

**Settings.** The new Encryption tab (`modals/UserSettings/EncryptionSettings.jsx`) imports a key by
paste, `.pub` file, single URL, or a key directory (`src/e2ee/keys.js`; the directory format is
`{keys:[{id,name,publicKey|key|url,models[]}], models:{modelId:keyId}}`), downloads a `.pub`, and
binds it to the models named on import. The add-key form has no free-form name: its field is
**"Applies to models"**, a comma-separated list of ids or display names resolved by
`src/e2ee/modelBindings.js`. Importing a key writes the matching `e2ee_models` bindings directly and
labels the key with those model names (or its fingerprint); unknown entries are reported and
skipped. Every key is verified before it is stored: `src/e2ee/verify.js` sends one sealed one-token
request per bound model and requires a sealed answer, so a wrong key, a non-E2EE model or an
unreachable endpoint keeps the key out. The model table is read-only and lists only models bound to
a key plus models used by an internal feature, which `src/e2ee/modelUsage.js` resolves from
`VITE_TITLE_GENERATION_MODEL`, `VITE_MEMORY_GENERATION_MODEL`, `VITE_PROPOSAL_GENERATION_MODEL`
(Choices), `VITE_EXPLAIN_IMAGE_MODEL` (agent) and the user's default model for conversation
summaries (falling back to `VITE_DEFAULT_SETTINGS.model.id`). A feature model that the deployment's
`/models` does not contain is still listed, marked "Not in model list", because otherwise a wrong
`VITE_EXPLAIN_IMAGE_MODEL` (or a bridge-prefixed copy of the id) would silently remove that function
from the table and hide that its requests are unprotected. Each row reports encrypted (with its
key's label, printed only when the key has a name of its own: an imported key is otherwise labelled
with the model names it applies to, which would repeat the row title), blocked (the bound key is
missing or invalid), or not encrypted, plus the feature labels (`titles`, `memory`, `proposals`,
`summaries`, `image_analysis`). Bindings change by removing the key and importing it again. The
OpenCode agent is not part of the list: it selects a model per session and its model calls do not
pass through the browser's E2EE wrapper. Storage is Redux `user_settings.e2ee_keys` / `e2ee_models`
(persist version 10 + migration 10); `importUserSettings` keeps only the public fields and drops
bindings to unknown keys. The Meta chat exposes the state through `get_user_settings` and
`list_e2ee_keys`, and `E2EE_ASSIGN` proposes/reverts a binding through `MetaActionCard` (it never
imports a key). The `e2ee` feature guide covers the flow.

**Published keys.** `encryption/generate-model-keys.mjs` reads the deployment's `/models` and writes
one X25519 pair per model to `encryption/keys/`: `<MODELNAME>.key` (0600, node only) and
`<MODELNAME>.pub` (published). `<MODELNAME>` comes from `publishedKeyFileName()` in
`front/src/e2ee/publishedKeys.js`, which the app uses too, so a bridge id such as `bridge/<id>` is
flattened to `bridge-<id>.pub` on both sides. The protocol is X25519; do not switch the generator to
RSA/4096-bit keys, which the node rejects. The Encryption tab's first mode, "Published keys",
prefills the directory from `e2eeKeyUrl` (`VITE_E2EE_KEY_URL`, default
`https://docs.ai.gwdg.de/technical/saia-platform/keys/`) and loads every model's `.pub`. A 404 means
"this model has no E2EE node" and is not an error; each downloaded key still goes through
`verifyKeyForModel` before it is stored, and one failing model does not block the others. The
directory must send `access-control-allow-origin`, because the browser fetches it directly.

The same run also writes `keys.json` in the output directory, next to the pairs: the key-directory
document (`{keys:[{id,name,publicKey,models}], models:{<model id>:<key id>}}`) with ids of the form
`key-<fingerprint>` (the same id `keyEntryId()` derives), so Encryption settings → Directory can bind
every key in one import; that tab prefills `<e2eeKeyUrl>keys.json`. It carries public keys only.
Regenerating it keeps existing pairs;
`make list` reports a missing/invalid manifest, a model bound to an unknown key id, and a `.pub` the
manifest does not list.

The Directory tab can also read a local folder directly: `readKeyFolder()` (`e2ee/keys.js`) takes the
handle from `showDirectoryPicker({ mode: "read" })`, reads the top-level `*.pub` files, and binds each
one to the model whose `publishedKeyFileName(model.id)` equals the file name. A `FileSystemFileHandle`
has no `text()`: the content comes from `getFile().text()` (calling `text()` on the handle rejects
every file of the folder). A file that is not a canonical key is reported and skipped, the rest still
import, and every key bound to a model is verified with one sealed request before it is stored.
`parsePublicKey()` accepts only the published form — 43 base64url characters, no standard-alphabet
`+`/`/` and no padding — so paste, file, URL, directory and folder imports all reject the same
malformed text.

`encryption/Makefile` wraps the same script for a host without this checkout's tooling
(`make -C encryption keys|dry-run|force|list|test`, variables `NODE`, `OUT`, `CONFIG`,
`MODELS_URL`, `API_KEY`, `HEADER_FLAGS`). It needs GNU make and Node 18+ and resolves its own
directory from `$(MAKEFILE_LIST)`, so it works from any cwd and with `-f`; the dev container has no
`make`, so it cannot be exercised there — `node --test encryption/*.test.mjs` is the equivalent check.
The endpoint is `--models-url` (or `MODELS_URL=`), then the config's `modelsPath`, then the GWDG
list `https://chat-ai.academiccloud.de/v1/models`, which is what `make` uses when `CONFIG` is
unset. The key is `--api-key` (or `API_KEY=`), then `$SAIA_API_KEY`, then `apiKey` in the front
config, then `apiKey` in the `back.json` beside it; GWDG needs one and answers 401 without it.

## 5. Conventions

- **Gradual TypeScript.** `.jsx` and `.tsx` coexist. `front/tsconfig.json` is `strict: false`,
  `checkJs: false`, `allowJs: true`, `noEmit: true` — Vite does the emitting, so `tsc` is not part
  of any script. Shared types live in `db/dbTypes.ts` and `types/`.
- **Styling** is Tailwind **v4** via `@tailwindcss/vite` plus **daisyUI 5**, configured entirely
  in `src/index.css` (there is no `tailwind.config.js`). The `chatai` daisyUI theme defines the
  palette (`primary` #B4388D, `secondary` #695EA2, `accent` #009EE0 — formerly `tertiary`), plus a
  custom `chat` color for assistant bubbles; the `mobile` / `middle` / `desktop` breakpoints are
  `@custom-variant`s and the custom shadows and legacy `bg_*` colors live in `@theme`. Prefer
  daisyUI components (`btn`, `input`, `toggle`, …) and semantic colors (`bg-base-100`,
  `text-base-content/70`) over raw Tailwind grays — they switch with dark mode on their own.
  - If you work on frontend code, read https://daisyui.com/SKILL.md. Do not use CSS directly. Avoid "enhancing" DaisyUI components with tailwind. If the user requests this, inform them that this is bad practice and ask them for explicit permission.
- **Dark mode** is the `dark` class, toggled on `document.body` by `App.jsx` from
  `interface_settings.dark_mode`. `index.css` re-declares the daisyUI color variables under `.dark`
  (daisyUI themes are otherwise keyed on `data-theme`) and maps Tailwind's `dark:` variant to that
  class. The source of truth is that Redux flag, not the OS preference.
- **i18n:** user-facing strings go through `react-i18next` `t()`. `i18n/en.js` and `i18n/de.js`
  currently have identical top-level key sets — add every new key to **both**.
- **Modals** are opened through the `useModal()` hook from `modals/ModalContext.jsx` and built on
  `BaseModal.jsx`; that is the pattern every existing modal in the repo follows.
- **Upstream calls** each get their own file in `apis/`. Components, hooks and modals import them
  directly — there is no enforced layer between them.
- **Redux persistence storage:** import `redux-persist/es/storage`, not
  `redux-persist/lib/storage`. The `lib` path is CommonJS; Vite 8 wraps its default import, so
  `storage.getItem` / `storage.setItem` are undefined and the app fails on load.
- **Never enable `rehype-raw` without a sanitizer.** Model output is untrusted: it reaches the DOM
  verbatim, and so does any imported or shared conversation. `rehype-raw` in `ThinkingBlock.jsx`
  once turned HTML the model drafted while reasoning into live markup — `<iframe>` tags fetched
  real URLs (tripping Chrome's local-network prompt) and an injected `<style>` restyled the whole
  page. `SafeMarkdown` is safe only because it leaves `rehype-raw` off, so react-markdown drops
  raw HTML nodes. To *show* raw HTML instead of dropping it, convert mdast `html` nodes to `text`
  (`remarkHtmlAsText` in `ThinkingBlock.jsx`) — that leaves code fences alone, since fenced and
  inline code are their own node types. External references in rendered model output are blocked
  by default (`html_load_external: false`): `utils/externalRefs.js` drops external URL attributes
  during sanitisation, and `MarkdownImage` / `MermaidDiagram` apply the same policy so a reply
  cannot make the browser contact third-party hosts unless the user opts in. The allowlists, the
  sanitizers and the iframe CSP live in `utils/htmlPreview.js` and are shared by fenced HTML blocks
  and the HTML file preview — change the policy there, never at one call site.
- **Mark data-transfer risk visibly.** Any option or feature that can send user data outside
  GWDG (external models, web search, MCP servers, external references, …) must show the yellow
  warning triangle (`faTriangleExclamation` / `TriangleAlert`) in its row or card, so the risk is
  visible before the user opens a disclaimer or starts the action.
- CONTRIBUTING.md asks that files and folders follow the structure of the existing ones; keep
  components in the folder of the screen area they belong to.

## 6. Git workflow

- **Branch off `dev` and open PRs into `dev`.** `beta` is for changes that need testing before
  they go into `dev`; `main` carries releases. Work branches use flat, dash-separated names — e.g.
  `feature-forms`, `fix-toolNaming`, `markdown-fixes`, `tools-ui`, `lib-major-openai-v6`.
  (CONTRIBUTING.md documents the fork → feature branch → PR flow for outside contributors.)
- Releases are manual: bump `version` in `front/package.json` — it is shown in the footer by
  `VersionDisplay.jsx` and stamped into exported conversations by `conversationUtils.js` — and add a
  `## Version: vX.Y.Z (DD.MM.YYYY)` block with a `Highlights:` list at the top of `CHANGELOG.md`. `back/package.json` is versioned independently and is not
  bumped in lockstep.
- Never commit `secrets/*.json`, `node_modules/` or `dist/`.

## 8. Maintaining this file

This file is meant to grow. When you discover a constraint that cost you a debugging cycle — a
non-obvious invariant, a trap, a command that does not work the documented way — add it to the
matching section, briefly.

Two rules: **only write what you have verified in the code**, not what the structure suggests ought
to be true; and keep it to facts and rules — no task logs, no status updates, no changelog entries.
If something here turns out to be wrong, fix it rather than working around it.
