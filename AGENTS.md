# AGENTS.md

Guide for AI coding agents working in this repository. Read this before touching code.
Every statement here was checked against the code; see §8 before adding to it.
Human-facing docs: [README.md](README.md) (install/config), [CONTRIBUTING.md](CONTRIBUTING.md), [CHANGELOG.md](CHANGELOG.md).

## 1. What this repo is

The stand-alone **web interface of Chat AI** (GWDG / SAIA) — a browser chat client for any
OpenAI-compatible API endpoint. It is one of three repos in the wider architecture:

| Repo | Contents |
| --- | --- |
| **this one** (`gwdg/chat-ai`) | web interface: `front` + `back` |
| `gwdg/saia-hub` | API gateway, SSH proxy |
| `gwdg/saia-hpc` | Slurm scheduler + HPC scripts |

Two services, no monorepo tooling — each has its own `package.json` and is installed separately:

- **`front/`** — React 19 SPA, Vite 8, runs entirely in the user's browser. All chat data is local.
- **`back/`** — single-file Express 5 proxy (`back/service.mjs`, 412 lines). Per README it exists to
  hold the API key server-side and to prevent CORS errors in the user's browser.

## 3. Setup and commands

**Config is mandatory before anything runs.** Copy the samples first:

```bash
cp secrets/front.json.sample secrets/front.json
cp secrets/back.json.sample  secrets/back.json   # put a real apiKey in this one
```

`front/vite.config.js` calls `process.exit(1)` if `secrets/front.json` is missing or unparseable —
a front end that refuses to boot is almost always this.

### Native (preferred while iterating)

```bash
cd back  && npm i && npm run start   # :8081
cd front && npm i && npm run dev     # :8080
```

Both default `CONFIG_LOCATION` to `../secrets/<name>.json` and `path.resolve` it against the
**current working directory**, so run them from inside `front/` and `back/`, or set
`CONFIG_LOCATION` explicitly. The two services fail differently when the path is wrong: `front`
exits, while `back` only logs `Failed to read back.json. Using default values.` and keeps running
**with an empty `apiKey`** — so every upstream call comes back unauthorized. If requests are
rejected, check that log line first.

### Docker

```bash
docker compose build front back
docker compose up front back -d
docker compose restart front   # picks up config/source changes; rebuild if deps changed
```

Each Dockerfile sets `ENV CONFIG_LOCATION=/run/secrets/{front,back}`, fed by the docker secrets
declared in `docker-compose.yml`. Both services use `network_mode: host`, so ports are as
configured. `front/entrypoint.sh` greps `"mode"` out of `front.json` and runs `npm run dev` for
`dev`, `npm run prod` (`vite build && vite preview`) for `prod`, or `npm run build` for `build`;
anything else exits 1.

**`mode: "build"` is a one-shot static build, not a server.** `npm run build` is plain
`vite build`; Vite's default `outDir` is `dist`, and `docker-compose.yml` bind-mounts `./front` to
`/usr/src/app`, so the bundle lands at `front/dist/` **on the host**. The container then exits 0
(`restart: on-failure` does not restart it) and nothing is listening — serve that directory with
your own web server (README has nginx/Apache examples). A failed build exits non-zero and is
retried by that restart policy. `port` is unused in this mode. Every `VITE_*` value is compiled
into the bundle, so `front.json` is a build-time input: after changing it, rerun the build
(`docker compose up front` and `docker compose restart front` both re-run `entrypoint.sh`, so both
rebuild) and redeploy `front/dist`; an already-copied bundle does not change. The same holds
natively (`cd front && npm run build` with `CONFIG_LOCATION` pointing at `../secrets/front.json`).
`base` is hard-coded to `"/"` in `front/vite.config.js`, so the output assumes the domain root — a
sub-path deployment needs `base` changed plus a rebuild.

### Checks

```bash
cd front && npm run build    # vite build — works, ~6s
cd front && npm test         # vitest run — unit/component tests (jsdom + Testing Library)
cd front && npm run test:watch
cd front && npm run test:coverage   # v8 text coverage report
```

**`npm run lint` does not currently run.** The script invokes `eslint`, but neither `eslint` nor the
plugins `.eslintrc.cjs` extends are in `front/devDependencies`, so a clean `npm i` gives
`sh: eslint: command not found`. (`.eslintrc.cjs` is also the pre-flat-config format.) Don't put
lint in your verification loop until that is fixed, and don't report it as passing.

**Tests:** `front` uses Vitest with jsdom, fake-indexeddb, and Testing Library (`vitest.config.js`,
`src/test/setup.js`). Put tests next to the code as `*.test.js|jsx|ts|tsx`. `back` still has no
test suite (`npm test` is `exit 1`), and `.github/` contains only issue templates, so there is no
CI. A passing build or unit test is not evidence that the full UI works; exercise changes in a
browser when behaviour matters. **Include tests with new features:** add at least one focused
`*.test.js|jsx|ts|tsx` covering the new behavior, plus regression coverage for bugs you fix.

`npm i` can rewrite `package-lock.json`. Check `git status` afterwards and keep unrelated lockfile
churn out of your commit.

## 4. Architecture invariants

These are the things that are not guessable from the file tree.

### 4.1 Two stores, strictly separated

| Store | Holds | Where |
| --- | --- | --- |
| **Dexie / IndexedDB** (`app-conversations-db`) | conversations, messages, content items, files, folders | `front/src/db/` |
| **Redux + redux-persist** (localStorage) | `interface_settings`, `user_settings`, `last_conversation`, `migration_data` | `front/src/Redux/` |

`version` is in the root reducer but is not in the persist whitelist.

Redux is persisted with a `version` + `migrations` map (`Redux/store/migrations.jsx`), and only a
five-action whitelist is mirrored across tabs via `redux-state-sync`: `SET_ADV`, `RESET_ALL`,
`MIGRATE`, `SET_COUNT`, `user_settings/importUserSettings`. Adding a persisted key means adding it to
`whitelist` **and** `getDefaultState()` in `Redux/store/store.jsx`.

### 4.2 The conversation data flow

`ChatPage.tsx` holds the whole hydrated conversation in one `localState` object and passes
`localState` / `setLocalState` down the tree. `useSyncConversation` reconciles that object with
IndexedDB. Writes go through `updateConversation(id, data)` in `db/index.ts`, which:

- replaces title + settings + the **entire** message list in a single Dexie transaction, and
- enforces optimistic concurrency: unless `force` is passed it compares `data.lastModified`
  against the row in the DB and **returns `-1` without writing** on mismatch. `-1` means another
  tab changed this conversation, and surfaces as `modals/Chat/ConversationConflict.jsx`.

So: thread the `lastModified` you read through to the write, and handle `-1`.

Data is normalised across `conversations → messages → content_items`, with `files_meta` /
`files_data` holding attachment bytes keyed by `fileId`; `hydrateConversation()` joins them back
into the nested shape the UI uses. Raw table access (`db.messages`, `db.content_items`, …) appears
**only** inside `front/src/db/` — everywhere else uses the functions it exports.

### 4.3 Dexie migrations

`db/index.ts` is at **version 11**. A new *indexed* field needs a new `this.version(n).stores({...})`
block plus an `.upgrade()` that backfills existing rows — this is how `folderId` (v3),
`hasFirstPrompt` (v4), `lastOpenedAt` (v5), the workspace tables (v6-v8),
`workspace_file_references` (v9), the default Arcana filesystem source (v10) and the default
browser source with the shared browser tree (v11) were added. A field that is only stored and never
queried needs **no** version bump; Dexie keeps unindexed properties on the row as-is. A version
bump and `.upgrade()` are still appropriate when existing rows need a backfill. Never edit an
existing version block: users have live databases.

### 4.4 "folder" in code == "topic" in the UI

v1.0.0 renamed this feature for user-facing copy only. The `folders` table, `folderId`, and every
`*Folder*` function keep the old name. Don't rename them, and don't introduce "topic" identifiers
inside `db/`. UI strings and i18n keys say topic.

### 4.5 Config reaches the front end through vite.config.js

`secrets/front.json` is read **at Vite startup** and hand-mapped into `process.env.VITE_*`:
`VITE_BACKEND_ENDPOINT`, `VITE_MODELS_ENDPOINT`, `VITE_USERDATA_ENDPOINT`,
`VITE_DEFAULT_SETTINGS`, `VITE_TITLE_GENERATION_MODEL`, `VITE_MEMORY_GENERATION_MODEL`,
`VITE_PROPOSAL_GENERATION_MODEL`, `VITE_ANNOUNCEMENT`, `VITE_USE_OPENAI_SDK`,
`VITE_OPENCODE_SERVER_URL`, `VITE_OPENCODE_SERVER_USERNAME`,
`VITE_OPENCODE_SERVER_PASSWORD`, `VITE_MODULE_*`. Consequences: **a new
config key requires editing `front/vite.config.js` too**, and a config change requires a dev-server
restart. Read values via `import.meta.env.VITE_*`; they arrive as strings, hence the
`=== "true"` comparisons.

Feature modules are gated this way — `VITE_MODULE_TOOLS`, `VITE_MODULE_FEEDBACK`,
`VITE_MODULE_CHOICES`, `VITE_MODULE_AGENT` (the browser agent), `VITE_MODULE_AGENTS` (the sidebar
Agents section, on by default), `VITE_MODULE_ARCANAS` (Arcana and ArcanaV2, on by default), `VITE_MODULE_SPEECH` (JSON, with `model` and `voice`). A deployment can
switch these parts of the UI off, so new code in those areas must still behave with the flag off.

### 4.6 Model capabilities are data, not code

`front/src/config/models/<model-id>.json` is auto-globbed by `getModelDefaults.jsx` via
`import.meta.glob`, keyed on the filename. To give a model reasoning-effort support or other
per-model defaults, add or edit the JSON named exactly after the model id — no code change and no
registry to update.

### 4.7 Secrets

The API key is read only by `back/service.mjs` from `secrets/back.json`. `secrets/.gitignore`
ignores everything in that directory except itself, so real config files there are invisible to
git. Never move a key into front-end code or into a `.sample`.

### 4.8 The back service's responses can mislead you

Verified in `back/service.mjs`:

- **`/models` always returns HTTP 200**, even when the upstream rejects the request — the handler is
  `res.status(200).json(await response.json())`, so an upstream `{"message":"Unauthorized"}` arrives
  as a 200. Check the response body, never the status.
- **If `apiKey` is empty, `Authorization` falls back to the `inference-id` request header** rather
  than erroring — that is how the deployed setup passes per-user credentials through.
- **`/chat/completions` rebuilds the request from a fixed set of fields.** Anything else the client
  sends is dropped. `function` tools and `tool_choice` (the browser agent's) are forwarded only
  when `enable_tools` is unset; with `enable_tools` the request goes to the tool gateway instead.
- **`/user` is a hard-coded placeholder** in this repo: it always returns the same `sample-user`
  object. Real user data comes from the gateway in a full deployment, so don't debug user/usage
  features against this response.

### 4.9 Typst rendering is client-side, from fenced code blocks

**Entry point.** `rendererComponents.code` in `MarkdownRenderer.jsx` handles fenced blocks:
` ```mermaid ` goes to `MermaidDiagram.jsx`, ` ```latex ` / ` ```tex ` goes to `LatexBlock.jsx`
(§4.10), ` ```typst ` / ` ```typ ` goes to `TypstBlock.jsx` (rendering defaults to off via the
preference), and every other language also goes to `TypstBlock.jsx` with `defaultRender={false}`.
Inline code is returned directly and never rendered.

**Pipeline.** `TypstBlock.jsx` lazily imports `@myriaddreamin/typst.ts` on the first render. Its
compiler and renderer WASM files are imported with Vite's `?url` (`TypstBlock.jsx:6-7`), so Vite
emits them as app assets; nothing is fetched from a Typst server. The first render calls
`$typst.svg({ mainContent })`, which runs the Typst compiler and renderer WASM in the browser and
returns an SVG string. That SVG is sanitised, cached by source text (max 50 entries), and inserted
into a shadow root attached to the block's container. The shadow root is required because Typst's
SVG carries its own `<style>` with global selectors such as `svg { fill: none; }`; in the light DOM
that silently strips the fill from unrelated app icons. After mounting, full-page page-background
shapes (Typst emits one for `#set page(fill: ...)`) are ignored for measurement, then the viewBox is
rewritten to the rendered content's `getBBox()` plus 6 pt padding, so the unused page canvas is
cropped away. The back service and API endpoint are not involved.

**Scheduling.** Rendering is debounced by 400 ms, so streaming code blocks are not recompiled on
every keystroke. `$typst` is a single shared, stateful instance, so `TypstBlock` serialises all
compilations through a module-level promise queue; a cancelled render is ignored when it finishes.
Compile errors fall back to the raw source.

**Per-block UI.** ` ```typst ` / ` ```typ ` blocks start rendered or as code according to the
`user_settings.render_typst` flag (Chat preferences → Rendering). All other code blocks start as
code. Every block keeps a "Render as Typst" / "Show code" toggle regardless of the preference; the
preference only selects the default view. The selector defaults the flag to `false`, so blocks are
shown as code unless rendering is enabled.

**Resources and security.** The WASM modules are served from the app's own build output. The
default text fonts are vendored in `front/public/typst-assets/` (from
`typst/typst-assets@v0.13.1`, with its LICENSE/NOTICE) and `TypstBlock.jsx` passes
`loadFonts([], { assets: ["text"], assetUrlPrefix: ... })` so typst.ts does not add its jsDelivr
font loader. The `assets` option must stay set, otherwise typst.ts appends its own remote loader.
Model output is untrusted: the SVG is
sanitised with DOMPurify's SVG profile plus `ADD_TAGS: ["use"]` (the profile otherwise drops
`<use>`, which Typst uses to reuse glyphs), and `data_selection.js` is disabled.

### 4.10 LaTeX document blocks render client-side with faster-latex

`rendererComponents.code` routes ` ```latex ` / ` ```tex ` fences to `LatexBlock.jsx`; other code
blocks still go to `TypstBlock.jsx` with `defaultRender={false}`. `LatexBlock` lazily imports the
`faster-latex/web` build, initializes its WASM (emitted as a Vite asset), and calls
`render(source, { fullDocument: false })`. The WASM is imported via the `faster-latex-wasm` alias
in `vite.config.js`, which maps to the package's `web/faster_latex_bg.wasm`; this is required
because the package's own `new URL(..., import.meta.url)` path works in the production build but
not in the dev server. faster-latex is a Rust→WASM LaTeX subset that emits HTML
with MathML; it is **not** a full TeX distribution — `\usepackage`, TikZ and other primitives are
unsupported, and unsupported constructs produce warnings and visible fallbacks rather than failing.
The HTML is sanitised with DOMPurify's `html` + `mathMl` profiles, then inserted into a shadow root
with the shipped article CSS plus a small override, so the stylesheet cannot leak into the app.
Rendering is debounced by 400 ms and cached by source text. `user_settings.render_latex` only
selects the default view; every block keeps a "Render as LaTeX" / "Show code" toggle. No back
service or API endpoint is involved.

### 4.11 TikZ inside LaTeX blocks renders with self-hosted TikZJax

TikZ is **not** a separate code-block type. `LatexBlock` preprocesses every ` ```latex ` / ` ```tex `
block: `tikzRenderer.js` extracts `tikzpicture`/`tikzcd` environments, strips
`\usetikzlibrary` and known `\usepackage` declarations from the text, and replaces each environment
with a `TIKZPLACEHOLDER<n>END` token. The extracted snippets are rendered off-screen through
TikZJax (a hidden `<pre class="language-tikz">`) to SVG strings, while the cleaned source is
rendered with faster-latex. The tokens are then replaced with
`<span class="latex-tikz">…SVG…</span>`, and the combined HTML is sanitized with DOMPurify's
`html` + `svg` + `mathMl` profiles (plus `ADD_TAGS: ["use"]`).

TikZJax's dist and its ~7.7 MB of TeX/font assets are copied from `@rod2ik/tikzjax` into
`public/tikzjax` by `scripts/copy-tikzjax.mjs`, which runs as `predev` / `prebuild` / `preprod`;
that directory is gitignored. `vite.config.js` serves `/tikzjax/*.gz` with
`Content-Encoding: identity`: otherwise Vite marks the `.gz` files as gzip-encoded, the browser
transparently decompresses them, and TikZJax's own gunzip fails with "incorrect header check".
`tikzRenderer.js` sets `workerMode: "direct"` and disables `workerPool`; the pool path wraps the
worker in a blob and loads it with `importScripts`, which can fail under some deployments/CSPs.
Only packages in the loader's known set are forwarded; TikZ libraries from
`\usetikzlibrary` and preamble commands such as `\tikzset` are forwarded via the pre's data
attributes. `user_settings.render_latex` controls the LaTeX block's default view. The TikZJax
package is GPL-3.0+.

### 4.12 Two model-selector variants, chosen from the data

`Header/ModelSelectorWrapper.tsx` renders one of two selectors for all three call sites (header,
prompt-box `ModelButton`, settings `DefaultModelSelector`). The choice is
`modelsData?.[0]?.description !== undefined`: SAIA / Chat AI returns `description` (plus
`releaseDate`, `company`, `contextLength`, `external`, …), so it gets `ModelSelectorExtended`;
a plain OpenAI-compatible `/models` response does not, so it gets `ModelSelectorSimple`. Only the
**first** model is inspected, so a mixed or reordered response silently selects the wrong variant.
Both are data-tolerant (optional chaining), but the simple selector has no metadata columns or
view modes. Add new model fields to `types/models.ts` and both selectors if they affect both
variants. When a conversation's stored model id is not in `modelsData` (for example an imported
persona references a model this deployment does not offer), the wrapper replaces it with the user's
default model and only falls back to `modelsData[0]` if that default is unavailable too.

### 4.13 Document conversion can run in the browser or on the server

`utils/browserDocumentConversion.js` converts `pdf` (PDFium WASM via `@hyzyla/pdfium`) and `docx`
(`mammoth`) locally. `user_settings.document_conversion_mode` is `"server"`, `"browser"`, or
`"choice"` (default). `Prompt/Attachment.jsx` renders one Process button for the fixed modes and
two for `"choice"`; the browser path is only used when that file type is supported, otherwise it
calls the `back` `/documents/convert/file` endpoint. Redux migration 5 maps the previous boolean
`browser_document_conversion` flag (`false` → `"server"`, otherwise `"choice"`). PDF text extraction
runs in the package's blob worker first; if the worker cannot be created (for example under a strict
CSP) it retries on the main thread. The PDFium WASM is imported with `?url` so Vite emits it as an
app asset.

A model can accept binary documents directly instead of requiring conversion.
`utils/modelCapabilities.js#modelSupportsFileType` treats a specific `pdf`/`docx` as supported when
`input` (or `capabilities`) contains a generic `file`, `files`, `binary`, `document` or `documents`
modality, or the matching type (`pdf`; `docx`/`word`/`wordprocessingml`), or when the model object /
`config/models/<id>.json` sets `supports_binary`, `supports_binary_data`, `supports_binary_input` or
`supports_file_input`. In that case an unprocessed file of that type is sent as an OpenAI `file`
content part (`{ type: "file", file: { file_data, filename } }`), `Prompt.jsx` does not block the
send, and `Attachment.jsx` still offers the Process buttons but without the "must process" warning.
Without the capability the previous behaviour applies: `Prompt.jsx` blocks, and
`processContentItems` drops an unprocessed PDF (and falls back to text for DOCX).

### 4.14 Prompt submission key is a user setting

`user_settings.send_with_enter` controls whether plain Enter or Shift+Enter submits the prompt:
`true` = Enter sends, `false` = Shift+Enter sends, `null` = device default. The default is
resolved by `hooks/useSendWithEnter.ts`: Enter on desktop, Shift+Enter on mobile. `PromptTextArea`
implements the key handling, and `SendButton` uses the same hook for its shortcut tooltip. Alt with
Enter always inserts a newline. When adding another user setting, update
`userSettingsReducer`'s `initialState`, the `getDefaultState()` fallback in `Redux/store/store.jsx`,
both i18n files, and the export/import path.

### 4.15 Sidebar conversation grouping is a persisted interface setting

`interface_settings.conversation_grouping` is `"topic"` (default), `"date"`, `"created"`, or
`"size"`. The sort menu in `SidebarContent` dispatches `setConversationGrouping`, and `TopicList`
receives the value as `grouping` to render either topic rows or a date-bucket tree. `size` bypasses
`TopicList` and renders all chats as a flat list sorted by their OPFS browser-workspace size.
`date` uses
`groupConversationsByDate` (modified time); `created` uses `groupConversationsByCreationDate`. Both
date-like modes show a non-collapsible parent label; their date buckets sit at the top level and are
collapsible. Collapse state reuses `collapsed_topics` with `__by_date__` / `__by_created__`
prefixes. Created-mode rows also show the creation date beside the title. The date/created labels
only appear in their own mode; the topic-creation/unsorted rows only appear in topic mode.
It is in `interfaceSettingsSlice`'s `initialState` and `getDefaultState()`; an old persisted state
without the key falls back to `"topic"` in the selector, so no migration is needed.

### 4.16 Meta chat works from conversation summaries, not messages

The AI icon in the sidebar header navigates to `/meta`, rendered by
`Pages/MetaChatPage.jsx`. The page reuses the normal chat shell (`Header`, `SidebarWrapper`,
`Conversation`, `Prompt`) and provides `MetaChatSendContext`, which `useSendMessage` delegates to
`useMetaChatSend` while inside the page. A banner above the conversation labels it as the Meta chat
and shows an example question.

The Meta chat does not embed the chat list, topics, settings, personas, tutorials, use cases, or
message excerpts in its system prompt. It runs a function-tool loop: `utils/metaTools.js` defines
`list_chats`, `list_topics`, `get_chat`, `search_messages`, `list_memories`, `get_user_settings`,
`list_models`, `list_personas`, `list_tutorials`, `start_tutorial`, and `start_use_case`.
`useMetaChatSend` sends them as `settings.function_tools`; `apis/chatCompletions.jsx` forwards them,
and `back/service.mjs` passes function tools through when `enable_tools` is false. The model must
call the relevant tool for current data because the interface state can change between user
messages. `list_chats` returns summaries and per-chat settings (model, temperature, top_p, reasoning
effort, memory-mode override, enabled tools, Arcana, MCP); missing summaries fall back to the title.

The meta chat is stored as a hidden conversation row (`id: "meta-chat"`, `isMetaChat: true`),
excluded from the sidebar, last-conversation lookup, and its own summary context. `getExportData()`
emits it as `meta_chat` and `useImportConversation` recreates it silently. Do not make it summarize
full conversations on the fly without accounting for the extra model calls.

Personas come from `list_personas` (`gwdg/chat-ai-personas` via `utils/personaCatalog.js`, cached in
memory and `sessionStorage`). The model links to one inline with `[label](/persona/<path>)`;
`MarkdownRenderer` routes that link to `PersonaStartLink`, which fetches the persona JSON and starts
a new chat through `useImportConversation`. The legacy `[[PERSONA:<path>]]` marker still renders a
`PersonaCard` below the message. The catalog is metadata only: the full persona JSON is fetched when
the user clicks, and the Meta chat must keep working if GitHub’s tree API fails or is rate-limited.

For navigation and message search, the model calls `search_messages`; results include exact
conversation and message ids. It cites messages as
`/chat/<conversation id>?message=<message id>`; `Conversation` reads that query parameter, scrolls
to the message, and highlights it briefly. `MarkdownLink` routes `/chat/...`, `/topic/...`, and
`/settings/<tab>` internally; settings links dispatch `chatai:open-settings`, handled by
`useSettingsDeepLink` in `ChatPage`/`MetaChatPage`, and `UserSettingsModal` opens the requested tab
with a brief highlight. `get_user_settings` returns the module flags and global preferences.

Tutorials and use cases start through the `start_tutorial` / `start_use_case` tools, which dispatch
`chatai:start-feature-guide` / `chatai:start-use-case`, or through inline links
`[Start tutorial](/tutorial/<feature id>)` / `[Start use case](/use-case/<use case id>)` handled by
`MarkdownLink`. The legacy `[[GUIDE:...]]` and `[[USE_CASE:...]]` markers still start them when no
tool already did, and `[[PERSONA:...]]` remains supported.

Mutating chat actions are proposals, never applied by the model. It emits `RENAME_CHAT` /
`MOVE_CHAT`, `PIN_CHAT`, `PIN_TOPIC`, `SET_SETTING`, `MCP_SERVER`, and memory markers
(`utils/metaActions.js`), which `MetaActionCard` renders below the message with a warning icon and
an explicit Accept button. `MCP_SERVER` adds, updates, or removes per-chat MCP servers (local URL
entries or remote gateway ids). Only that click calls `updateConversationMeta` /
`assignConversationToFolder` / `setConversationPinned` / `setFolderPinned` or dispatches
`importUserSettings`; markers
are stripped from rendered markdown and from Meta-chat history. Memory indices come from the
`list_memories` tool. After applying, the card stores a snapshot and
offers a revert action; it only reverts if the current chats/settings/memories still match the
values that were applied. A successful revert returns the card to the unapplied state, so the same
proposal can be accepted again. Accept (or no decision) is stored as `meta.actionDecision` on the
assistant message; reverting stores `rejected`. `useMetaChatSend` prefixes the next user message
with “I accepted the change.” / “I rejected the change.” / “I cannot decide.” so the model sees the
outcome.

**Every new setting must be reachable from the Meta chat.** When adding a global, per-chat, or
feature-specific setting, expose its current value through a Meta-chat read tool (or an existing
tool’s output) and add a confirmable mutation marker with `MetaActionCard` apply/revert support. Do
not ship a setting that the Meta chat cannot read or propose to change.

The Meta chat honors the conversation's effective memory mode and group for memory learning: in
Learn mode it runs the same memory update path as normal chat and writes learned/replaced memories
to the effective group.

### 4.17 Per-conversation memory mode overrides the global preference

`ConversationSettings.memory_mode_override` is `"default"`, `0` (off), `1` (recall), or `2`
(learn). `getDefaultSettings()` defaults it to `"default"`, and `useSendMessage` resolves it at send
time: `"default"` uses `user_settings.memory_mode`; a numeric value overrides it for that chat. The
control is `SettingsPanel/MemoryModeContainer.jsx`; the global preference remains in
`UserSettings/ChatPreferences.jsx`. The value is stored with the conversation settings (no Dexie
version bump) and restored by `useImportConversation`.

### 4.18 Tutorials and use cases are static config; only completion is persisted

The UI's "tutorials" are the code's **feature guides**. Both tutorials and use cases are plain
JavaScript object literals, not database rows or JSON files:

- `front/src/config/featureGuides.js` exports `featureGuides`, keyed by feature id
  (`upload_file`, `select_model`, …). Each entry has `titleKey`, a model-facing `prompt`,
  `keywords`, and `steps`. Steps carry `target` selector(s), `textKey`, and optional tour logic
  (`prepare`, `check`, `completeOnTargetClick`, `completeOnEvent`). `FEATURE_CATEGORIES` groups the
  ids, and `buildFeatureGuidePrompt()` feeds the ids and prompts to the Meta chat.
- `front/src/config/useCases.js` exports `useCases`, keyed by use-case id. Entries have `category`,
  `prompt`, `keywords`, and `steps`; a step may reference a `tutorialId` to launch one of the
  feature guides. `USE_CASE_CATEGORIES` groups them, and `buildUseCaseGuide()` turns a use case into
  a custom tour.

Visible copy is not stored in these objects: titles and step texts are i18n keys resolved from
`front/src/i18n/en.js` and `de.js`. Element preparation lives in
`front/src/config/featureGuideActions.js`, and the tour runtime is `FeatureGuideContext` +
`SettingsPanel/TourManager.jsx`.

The only persisted part is progress, in the Redux `interface_settings` slice:
`completed_tutorials`, `completed_use_cases`, and `suppressed_tutorials` are id arrays, dispatched by
`markTutorialCompleted` / `markUseCaseCompleted` / `suppressTutorial` and persisted to localStorage
by redux-persist. The code's `featureGuides`/`useCases` definitions are never written to Dexie.

When adding one, edit the relevant config file **and** its category list, add every `titleKey` /
`textKey` to both i18n files, and target an existing `data-guide` attribute or class. Run
`cd front && npm run validate:guides`; `front/scripts/validate-feature-guides.mjs` checks ids,
categories, tour targets, and the en/de keys.

**Every new proper user-facing feature should ship with at least one feature guide (tutorial).**
Use cases are optional and compose existing tutorials into longer workflows; they do not replace
the tutorial for the feature itself.

### 4.19 Chat requests use a fetch client; the openai SDK is opt-in

`apis/openaiClient.js` `createBackendClient()` returns `{ chat: { completions: { create } } }`
from `apis/fetchClient.js`, a small fetch + SSE client that mirrors openai v6 behaviour the app
relies on: `APIError` with `status` / `error` / `code` / `type` and a `"<status> <msg>"`
message (read by `sendMessage.jsx`), a timeout that only covers waiting for response headers, two
retries on 408/409/429/5xx and connection errors, `"Request was aborted."` when aborted before
the response, and a stream that **ends quietly** when aborted mid-stream. Gateway chunks with
`object: "error"` pass through as data (`chatCompletions.jsx` throws on them); a chunk with an
`error` key throws. `"useOpenAISdk": true` in `front.json` switches back to the SDK, which is then
dynamically imported. The browser agent does not use either: it talks to the API through pi-ai's
own `openai-completions` client (`agent/runAgent.ts`).

### 4.20 Heavy renderers and libraries load on demand

Keep these out of the entry chunk; a static import of any of them undoes it:

- **KaTeX**: `SafeMarkdown` imports `rehype-katex` + `katex.min.css` only once some content
  matches `MATH_HINT` (`$`, `\(`, `\[`, `\begin{`); until then math renders through the plain
  `math` / `inlineMath` components.
- **Mermaid**: `MermaidDiagram.jsx` `loadMermaid()`.
- **Syntax highlighting**: `Code.jsx` uses `PrismAsyncLight`, which fetches the Prism core and
  each grammar on first use. Its loader map only knows canonical names, so aliases (`js`, `py`,
  `sh`, `html`, …) go through `LANGUAGE_ALIASES`; add one there when a fence name renders unhighlighted.
- **jsPDF** (PDF export) and **Joyride** (tour) are imported when used. The agent
  (`agent/runAgent`) is dynamically imported on send and **prefetched on idle** by `ChatPage` when
  `VITE_MODULE_AGENT` is on.

### 4.21 The build precompresses assets and emits a service worker

`vite-plugins/staticAssets.js`: `staticAssetsBuild()` writes `dist/sw.js` and then a `.br` + `.gz`
next to every compressible file (one plugin on purpose: Rollup runs `closeBundle` hooks of
different plugins in parallel). Brotli quality is tiered by size and type to keep this at ~10 s;
q11 on fonts/WASM tripled the build time for little gain. `servePrecompressed()` serves those in
`vite preview` with immutable caching for `/assets/`; Vite's own preview compression gzips on the
fly and never compresses `application/wasm`. `sw.js` is registered only in production builds
(`main.jsx`). It caches on first use, never precaches, handles only paths in its build manifest
(hashed `assets/` and the vendored `typst-assets/` / `tikzjax/`, the latter keyed by content
hash), and prunes stale entries on activate. TikZJax's own `.gz` files are real payloads, not
precompressed siblings: never serve them with `Content-Encoding` (see §4.11).

### 4.22 ArcanaV2 and remote files are proxy-backed by saia-rag-web

The GWDG tool `arcana_v2` and the agent's `arcana_*` tools call the back service's `/arcana-v2/*`
routes, which proxy the saia-rag-web Arcana API at `remoteFilesEndpoint` (default
`http://localhost:8000/arcanas/api/v1`). They cover creating and listing Arcanas and files,
reading/uploading/replacing/deleting files, starting/checking/deleting indexes, and
listing/adding/removing members.
The user identity is read from the incoming `x-auth-claim-uid` header (falling back to
`x-consumer-custom-id`, `oidc_claim_uid`, then `inference-id`) and forwarded as `x-auth-claim-uid`.

The legacy `/remote-files` routes use the same backend but store generic files in the dedicated
Arcana `remoteFilesArcana` (default `remote-files`), which is created on first write. Remote paths
are encoded into flat Arcana filenames (`rf_` + base64url), so the same path lists, reads, writes
and deletes through the saia-rag-web file endpoints.

### 4.23 Memories can be grouped; conversations choose a group

`user_settings.memory_groups` holds custom groups (`{id, name}`) and `user_settings.default_memory_group`
selects the group used by default. The implicit id `"default"` is the normal/ungrouped memory group.
Each memory's optional `groupId` defaults to `"default"`. `UserMemoryContainer` shows the groups
directly under User Memories and manages the default group; clicking a group opens
`UserMemoryModal` filtered to that group, where memories can be reassigned.

`ConversationSettings.memory_group_override` is `"default"` (follow the global default group) or a
group id. `useSendMessage` resolves the effective group, filters the memories passed to
`sendMessage`, and passes `memoryGroupId` so learned/replaced memories stay in that group. Deleting a
group moves its memories to `"default"` and resets the global default if needed. Selecting a specific
(non-default) group in the per-chat control also switches the per-chat mode from off to recall so
the selection takes effect. Groups live inside `user_settings`, so they are exported/imported with
settings; the conversation override is part of
the conversation settings. Redux persist migration 8 initializes `memory_groups` /
`default_memory_group` and assigns every existing memory to `"default"`; old conversations without
`memory_group_override` follow the global default group. No Dexie version bump is needed (all fields
are unindexed). The Meta chat exposes the grouping through `list_memories` (default group, available
groups, and each memory's group) and `get_user_settings` (group list and default group). Its
`ADD_MEMORY` / `UPDATE_MEMORY` proposals accept an optional `group` name; additions without one use
the Meta conversation's effective group.

### 4.24 Workspaces group sources behind one file-provider contract

The sidebar's Workspace section (`components/Workspace/WorkspaceList.tsx`) sits below the Chats subpanel;
`/workspace/:workspaceId` renders `Pages/WorkspacePage.tsx`. Workspace and Chats are separate
collapsible subpanels; their collapse state reuses `interface_settings.collapsed_topics` under the
synthetic ids `__workspaces__` and `__chats__`. The Agents section (`Sidebar/AgentList.tsx`) sits
between Workspace and MCP Servers and uses `__agents__`; its + button opens a placeholder add-agent
modal with a dummy HPC project list, and agent metadata is kept in localStorage. Workspace, source, mount and chat-link metadata
lives entirely in IndexedDB; the back service does not store it. Dexie schema v6 adds
`workspaces`, `workspace_sources`, `workspace_handles` and `workspace_transfers`; v7 adds
`workspace_mounts` and `workspace_chats`; v8 adds the browser source's `workspace_nodes` /
`workspace_blobs` file tree; v9 adds `workspace_file_references`; v10 adds the default Arcana
filesystem source; v11 adds the default browser source and moves every browser source and workspace
root onto the single `browser-storage` tree. Handles and the transfer journal never leave the device. A persisted
`chatai.workspace.deviceId` binds `browser`, `local` and `mcp` sources to this device; `arcana`
sources carry no `deviceId`. The UI badges device-plane sources "This device only" and marks a
source whose stored `deviceId` differs as unavailable.

Attaching a file from a workspace to a chat records a `workspace_file_references` row for the
browser node; deleting a chat removes its reference rows. All browser sources and every workspace
root share the single `browser-storage` tree, so deleting a workspace removes its source rows but
not the shared browser files.

Every source kind is a `FileProvider` (`workspace/providers/`) built from its `WorkspaceSourceRow`:
Every new workspace automatically gets a `browser` source and, unless the Arcanas module is off, an
`arcana-filesystem` source; Dexie v10/v11 backfill them into existing workspaces.

browser = the shared IndexedDB tree in `workspace_nodes` / `workspace_blobs`, local = a
`FileSystemDirectoryHandle` in `workspace_handles`, arcana = one ArcanaV2 collection through
`agent/arcanaV2.ts`, arcana-filesystem = every Arcana as a folder with its files, mcp = file tools exposed
by a configured local MCP server (the option only appears when `tools.mcp` is on and a local URL is
configured). Providers declare `capabilities`, and the UI must offer only what a provider reports.
`WorkspaceSourceRow.readOnly` wraps the provider in `ReadOnlyProvider` (writes, deletes, mkdir,
move and copy throw `PERMISSION_DENIED`), and `WorkspaceMountRow.readOnly` blocks writes/moves
through that mount while still allowing reads and copies out. The Local tools panel was removed;
GWDG Tools now contains the document-creation and image-analysis toggles, while codemode and the
tool-call limit moved to the Workspace popover. When a chat has a workspace link, `runAgent` uses
`workspace/agentVfs.ts` over that workspace's root and mounts for the file tools.
`agent/prepare.ts` writes attachments and their converted variants under `/artefacts` in the
attached workspace root (or the conversation OPFS when no workspace is linked); the agent VFS keeps
`/uploads` routed to the conversation OPFS for legacy paths.

Every workspace also has an implicit browser-backed root: files and directories created there are
stored in `workspace_nodes` / `workspace_blobs` under the synthetic source id
`workspace-root:<workspaceId>`. The root browser lists those local entries and overlays mounted
source folders, so normalized local directories/files and mounts coexist.

`workspace_mounts` maps a folder inside a source (`sourcePath`) to a workspace path (`path`), so
several sources can appear side by side in one workspace; the workspace browser starts at that
mount list. `workspace_chats` is the
many-to-many chat link: a chat can be attached to any number of workspaces, shown under the
workspace in the sidebar and in the workspace's Chats panel, and toggled from the `Workspace` icon
left of the Local tools icon in the prompt box. Storage is shown for every source in the always
visible "Available storage" panel.

Transfers are orchestrated in the browser: `workspace/transferPlanner.ts` always moves on drag and
drop, regardless of source; an explicit "copy" intent is the only copy path. It blocks read-only
targets, folder-into-descendant moves and over-quota transfers. The workspace root
browser uses the same drag-and-drop flow as source folders, but mounted folder rows are not
draggable (the workspace root provider is resolved by `providerFor` for both drag source and drop
target). `workspace/transfer.ts` streams the copy, verifies SHA-256, then deletes the source for a
move, and journals progress in `workspace_transfers`. Arcana quota is read through the
`/arcana-v2/arcanas/:name/quota` proxy; local and MCP quota is shown as `—` because browsers cannot
read disk free space.

The file browser's Upload file action writes files from the computer into the folder currently
shown (workspace root or the selected source) through `workspace/upload.ts`; it is disabled for
read-only sources and mounts. Entries can be downloaded, renamed through the shared create-entry
modal, and deleted recursively after confirmation; sources with the matching capabilities also
offer new file/folder creation. HTML previews render in `SandboxedHtmlPreview`: an empty-sandbox
iframe with an opaque origin, strict CSP (no scripts or network), and external references stripped.

The prompt box's Workspace popover (`WorkspaceAttachButton`) also holds the agent settings that
apply to workspace files: the codemode toggle (`tools.codemode`) and the tool-call limit
(`settings.max_tool_calls`). GWDG Tools no longer renders either.

The `workspace_overview` feature guide targets `[data-guide="workspace-add-source"]`,
`workspace-sources` and `workspace-files`.


### 4.25 MCP servers are configured globally and selected per chat

`user_settings.mcp_servers` holds the global definitions (`{id, name, kind: "local" | "remote",
url?, serverId?, headers?}`), managed by the sidebar's `McpServerList` and `McpServerModal`
(including the connection test). Per-chat settings store only the selected ids in
`mcp_local_server_ids` / `mcp_remote_server_ids`; `agent/mcp.ts#resolveMcpServers` expands them for
the agent, gateway request and prefetch, and still merges legacy full entries from
`settings.mcp_servers`. GWDG Tools has one MCP Servers tool that switches every configured
server on or off; enabling it reveals the selector, which lists every configured server and
badges it local or GWDG and never shows URL/id/auth fields. `remoteMcpEnabled` also treats selected
remote ids as a value.


### 4.26 Sidebar agents connect to a local opencode server

`Sidebar/AgentList.tsx` lists remote agents like conversation rows and polls
`GET /api/session/status` every 5 s for the status dot (green idle, yellow working, red connection
error). Clicking one navigates to
`Pages/AgentPage.tsx` (`/agent/:agentId`), whose `components/Agent/AgentConversation.jsx` is the
chat pane; assistant text renders through `SafeMarkdown` with `rendererComponents`, and tool or
reasoning parts render as inline expandable cards (`AgentAssistantParts`). The left
`AgentFilesPanel` reuses the central `WorkspaceRootBrowser` (the same component used for the
workspace root file browser) and reads/writes the OpenCode project filesystem through
`GET /api/fs/list`, `GET /api/fs/read/<path>`, `POST /api/experimental/fs/write` and
`GET /api/fs/find`. Its file list polls the current directory every 5 s while the page is visible,
searches through `/api/fs/find`, and refreshes on navigation, upload, new file, or an explicit
refresh. The
`WorkspaceFilePanel` preview is rendered by `AgentPage` to the right of the chat, not beside the
file list. The sidebar's `+` opens
`modals/Agent/AddAgentModal`, which offers a name and the placeholder HPC project list. The row's
vertical menu edits (`agentEdit`, all creation fields; changing the server or password opens a new
session) or removes the agent. Adding an agent calls the local `opencode serve` HTTP API through
`apis/opencodeAgents.js`: `GET /api/info` verifies the server, `POST /api/session` creates the chat
session, and `AgentConversation` sends `POST /api/session/:id/prompt` and polls
`GET /api/session/:id/message?order=asc` until an `idle` message appears. It also exposes the
control API: interrupt (`/interrupt`), slash commands (`/command`), `!` shell input (`/shell`), and
permission replies (`/permission/{requestID}/reply`). The composer's command dropdown is populated
from `GET /api/command` (plus the built-in `compact`). The composer has a yellow Shell toggle that sends the input directly to
`/api/session/:id/shell`; shell output is rendered inline in the conversation, and the Tools modal
no longer has a terminal tab. Shell messages are persisted per agent/session in localStorage
(`agents/agentShellHistory.js`) and merged with the server timeline by creation time. The header X
confirms, interrupts and deletes the OpenCode session, creates a replacement session, updates the
agent entry, and clears the remembered shell history. The composer also accepts file attachments and sends them inline to the prompt API. The
`AgentFormCard` renders OpenCode forms inline in the conversation; form cards are persisted per
agent/session in localStorage (`agents/agentFormHistory.js`), so a card remains in the timeline
after reloads. After a successful reply, the same history entry receives the answers and renders
as `AgentFormResultCard`. `AgentToolsModal` exposes a live step/todo timeline, session
diff/revert with VCS and tracked-file status, saved permissions, local permission policies
(`agents/agentPermissionPolicies.js`, auto-answered by `AgentConversation`), usage stats, MCP
reconnect/refresh, connection diagnostics, and Markdown/JSON transcript export. The Composer's
shell output can be copied and a running shell command can be aborted from its card.
`subscribeOpencodeEvents`
refreshes messages and permissions from the `/api/event` stream. The composer reuses `SendButton` and
`ModelButton`; the model list is the intersection of `GET /api/model` (falling back to
`/api/model/default`) with the app's ChatAI models, the selector is centred in the composer, and a
selection is sent to `POST /api/session/:id/model`. A second dropdown lists `GET /api/agent`
(non-hidden primary agents) and switches with `POST /api/session/:id/agent`. The server URL and
HTTP-basic credentials default from `opencodeServerUrl` / `opencodeServerUsername` /
`opencodeServerPassword` in `front.json` (mapped to `VITE_OPENCODE_SERVER_*`) and stay editable per
agent. The browser talks to the server directly (opencode allows the app origin via CORS), so the
back service is not involved. `agents/agentStore.js` persists the agent metadata in localStorage.
A custom per-agent password is persisted with it; agents left on the configured default re-read that
password from `front.json` on load. `modules.agents: false` in
`front.json` sets `VITE_MODULE_AGENTS=false`, hiding the sidebar section and its route. Removing an
agent interrupts its running session first, then deletes the OpenCode session; the local agent is
dropped only after that succeeds; if the server is unreachable or rejects authentication, the local
agent entry can still be removed.


## 5. Conventions

- **Gradual TypeScript.** `.jsx` and `.tsx` coexist. `front/tsconfig.json` is `strict: false`,
  `checkJs: false`, `allowJs: true`, `noEmit: true` — Vite does the emitting, so `tsc` is not part
  of any script. Shared types live in `db/dbTypes.ts` and `types/`.
- **Styling** is Tailwind **v4** via `@tailwindcss/vite` plus **daisyUI 5**, configured entirely
  in `src/index.css` (there is no `tailwind.config.js`). The `chatai` daisyUI theme defines the
  palette (`primary` #B4388D, `secondary` #695EA2, `accent` #009EE0 — formerly `tertiary`), plus a
  custom `chat` color for assistant bubbles; the `mobile` / `middle` / `desktop` breakpoints are
  `@custom-variant`s and the custom shadows and legacy `bg_*` colors live in `@theme`. Prefer
  daisyUI components (`btn`, `input`, `toggle`, …) and semantic colors (`bg-base-100`,
  `text-base-content/70`) over raw Tailwind grays — they switch with dark mode on their own.
  - If you work on frontend code, read https://daisyui.com/SKILL.md. Do not use CSS directly. Avoid "enhancing" DaisyUI components with tailwind. If the user requests this, inform them that this is bad practice and ask them for explicit permission.
- **Dark mode** is the `dark` class, toggled on `document.body` by `App.jsx` from
  `interface_settings.dark_mode`. `index.css` re-declares the daisyUI color variables under `.dark`
  (daisyUI themes are otherwise keyed on `data-theme`) and maps Tailwind's `dark:` variant to that
  class. The source of truth is that Redux flag, not the OS preference.
- **i18n:** user-facing strings go through `react-i18next` `t()`. `i18n/en.js` and `i18n/de.js`
  currently have identical top-level key sets — add every new key to **both**.
- **Modals** are opened through the `useModal()` hook from `modals/ModalContext.jsx` and built on
  `BaseModal.jsx`; that is the pattern every existing modal in the repo follows.
- **Upstream calls** each get their own file in `apis/`. Components, hooks and modals import them
  directly — there is no enforced layer between them.
- **Redux persistence storage:** import `redux-persist/es/storage`, not
  `redux-persist/lib/storage`. The `lib` path is CommonJS; Vite 8 wraps its default import, so
  `storage.getItem` / `storage.setItem` are undefined and the app fails on load.
- **Never enable `rehype-raw` without a sanitizer.** Model output is untrusted: it reaches the DOM
  verbatim, and so does any imported or shared conversation. `rehype-raw` in `ThinkingBlock.jsx`
  once turned HTML the model drafted while reasoning into live markup — `<iframe>` tags fetched
  real URLs (tripping Chrome's local-network prompt) and an injected `<style>` restyled the whole
  page. `SafeMarkdown` is safe only because it leaves `rehype-raw` off, so react-markdown drops
  raw HTML nodes. To *show* raw HTML instead of dropping it, convert mdast `html` nodes to `text`
  (`remarkHtmlAsText` in `ThinkingBlock.jsx`) — that leaves code fences alone, since fenced and
  inline code are their own node types. External references in rendered model output are blocked
  by default (`html_load_external: false`): `utils/externalRefs.js` drops external URL attributes
  during sanitisation, and `MarkdownImage` / `MermaidDiagram` apply the same policy so a reply
  cannot make the browser contact third-party hosts unless the user opts in.
- **Mark data-transfer risk visibly.** Any option or feature that can send user data outside
  GWDG (external models, web search, MCP servers, external references, …) must show the yellow
  warning triangle (`faTriangleExclamation` / `TriangleAlert`) in its row or card, so the risk is
  visible before the user opens a disclaimer or starts the action.
- CONTRIBUTING.md asks that files and folders follow the structure of the existing ones; keep
  components in the folder of the screen area they belong to.

## 6. Git workflow

- **Branch off `dev` and open PRs into `dev`.** `beta` is for changes that need testing before
  they go into `dev`; `main` carries releases. Work branches use flat, dash-separated names — e.g.
  `feature-forms`, `fix-toolNaming`, `markdown-fixes`, `tools-ui`, `lib-major-openai-v6`.
  (CONTRIBUTING.md documents the fork → feature branch → PR flow for outside contributors.)
- Releases are manual: bump `version` in `front/package.json` — it is shown in the footer by
  `VersionDisplay.jsx` and stamped into exported conversations by `conversationUtils.js` — and add a
  `## Version: vX.Y.Z (DD.MM.YYYY)` block with a `Highlights:` list at the top of `CHANGELOG.md`. `back/package.json` is versioned independently and is not
  bumped in lockstep.
- Never commit `secrets/*.json`, `node_modules/` or `dist/`.

## 8. Maintaining this file

This file is meant to grow. When you discover a constraint that cost you a debugging cycle — a
non-obvious invariant, a trap, a command that does not work the documented way — add it to the
matching section, briefly.

Two rules: **only write what you have verified in the code**, not what the structure suggests ought
to be true; and keep it to facts and rules — no task logs, no status updates, no changelog entries.
